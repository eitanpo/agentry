# agentry — Product

Agent Replay: a single-binary CLI that renders a Claude Code session log into a readable, styled terminal view.

## Why

Claude Code stores each session as JSONL under `~/.claude/projects/`. Reading that raw is impractical. Routing the log through an agent's context instead strips terminal styling, forces a prompt-injection envelope, and is bounded by context size. `agentry` renders the log directly to the human's terminal: styling is native, there is no injection surface, and session size is unbounded.

## Users and usage

A developer who runs Claude Code in a project directory and wants to review a past session. The user runs `agentry` from the same directory they ran Claude in:

```
agentry                # list this project's sessions (see Listing sessions)
agentry <uuid>         # render a specific session, by id or any unambiguous prefix
agentry view [<uuid>]  # render; with no id, the most recent session
agentry list           # explicit form of the bare listing (see Listing sessions)
agentry cost           # what the sessions cost, by day, week, month, model, or session
```

With no argument, `agentry` **lists** this directory's sessions and those of every project nested under it — the default front door, identical to `agentry list`, so the bare command answers "which sessions do I have?" and the list flags (see Listing sessions) apply to it directly (`agentry --since today`). With an argument, `agentry` renders that session instead; the session id may be given **in full or as any unambiguous prefix** (`agentry 4a7c19f`), the rule `git` applies to object names; content search is on the roadmap. To render the **most recent** session without naming its id, use `agentry view` (no argument) — the most recent session by modification time, which may include one still in progress.

`agentry` is organized as verbs. The first token is treated as a verb when it names one (`view`, `search`, `list`, `cost`, `config`, `schema`), otherwise as a session id — unambiguous because ids are hex (`0-9a-f`, hyphens) and verbs are English words, so they never collide. Rendering has an explicit verb, `view`: `agentry <uuid>` and `agentry view <uuid>` render identically, and `agentry view` with no id renders the most recent session — the no-argument render path the bare command used to be. `view` owns the render flags' own help page and is discoverable in `agentry --help`.

`agentry` resolves logs from the current directory: it maps `$PWD` to the Claude project folder under the **projects root**, which is `~/.claude/projects/` unless `CLAUDE_CONFIG_DIR` names another config home, in which case it is that directory's `projects/`. Claude Code reads the same variable to decide where to write, so agentry reading it is what keeps the two pointed at one directory; a machine that sets it otherwise has every session invisible to agentry, reported as having no project rather than as a path agentry did not look in. The variable holds **one absolute directory**, never a list, and an empty value counts as unset — both rules taken from Claude Code's own binary rather than from agentry's convenience, so a value Claude Code rejects is a value agentry must not honor either. Running from a different directory targets a different project — this is intentional. Both paths resolve in the same scope: the current directory's project **and every project nested under it**. The **listing** covers that scope, so standing in a repo lists the repo's own sessions and its worktrees' in one call; the **render** path resolves a session id within it, so an id read off a listing opens from where it was read rather than only from the directory the session ran in. `agentry view` with no id follows suit, picking the most recent session in the scope rather than in the current directory alone. It still orders by file modification time where a listing orders by last-entry timestamp, so the two can name different sessions; widening the scope does not change that, and neither reading is wrong — a file touched after its last recorded turn is genuinely the most recently written. Only the listing takes scope flags (`--project`, `--all-projects`, see Listing sessions), and **an id needs none because it resolves across every project** — see the resolution order below. A listing that can show a session and a render that cannot open it would be two scopes wearing one id: the listing's row ends in the handle every other verb takes, so the handle has to work wherever the row came from. If the directory has no matching project, or the named session does not exist, `agentry` writes an error to stderr and exits with a distinct non-zero code.

**An id resolves in three widening steps, each tried only when the one before it missed**: the current directory's own project, then every project nested under it, then every project under the root. The first step answers nearly every call and pays nothing for the wider reach, since only a miss opens a file per project folder. The third is what makes an id from `--all-projects` usable, and it is also the only step that can reach a session whose recorded directory has since been deleted — the log is still there, and no directory maps to its project folder any more, so nothing narrower can find it.

**An id that resolves to nothing names the id it looked for.** "Session not found" alone leaves a caller checking whether the session exists, which is the wrong search when the id came from a word the parser took as one — a mistyped noun, a title typed in place of an id. Naming the string puts the cause on the same line as the failure.

An exact id wins over a prefix at every step, and a prefix ambiguous within a step is an error rather than a widening: the step already holds several sessions the caller might have meant, and adding more cannot decide between them. Where two steps could both answer, the narrower wins — an id read off a listing opens the session from the directory it was read in. Session ids are UUIDs, so that settles a tie that does not arise rather than a choice a caller would make.

The project folder's name is the working directory's absolute path with **every non-alphanumeric character replaced by `-`** — not only `/`, but `.` and `_` as well, so `/repo/.claude/worktrees/w` becomes `-repo--claude-worktrees-w`. Getting that rule wrong is not a near miss: the mis-spelled folder simply does not exist, and every path with a dot component reports "no Claude project for this directory" while holding sessions. That covers every worktree Claude Code creates for itself, since it puts them under `<repo>/.claude/worktrees/`. The encoding is also **lossy and must never be reversed** — `-a-b-c` could have come from `/a/b/c` or `/a/b-c`. Where agentry needs a project's real path it reads the `cwd` field the log records on its entries, which is exact and survives the directory being deleted or renamed.

## User flows

**A flow is what a specification of one verb cannot check: that the answer a caller gets is one they can act on.** Each verb below has a section saying what it prints and why, and every one of those can be right while the task the caller came with stays unfinished — a verb can hand back a correct answer in a form nothing else here accepts. A flow is written as the literal commands in the order a caller types them, what comes back from each, and what they do with it, and it is the check that the last step lands somewhere.

**Every change that adds or alters a capability adds or updates the flow it belongs to.** A capability with no flow has not been shown to be usable, only specified; and a flow whose steps cannot be run as written is a defect in whichever step fails, not a caveat to add to the flow.

**Which session was that?** The question a caller arrives with when they remember what happened and not where.

```
agentry search session "unplaced tokens" --all-projects   # sessions, and how many turns matched
agentry 4a7c19f                                           # render the one they recognize
```

The rows are what they choose from — the time, the project, the id, the title and how many turns matched — and the id is the handle every other verb takes, in full or as any unambiguous prefix, resolving in every project so a row from `--all-projects` opens. `--all-projects` is there because the caller who has forgotten which session rarely remembers which directory either. Where the question is about a session's own facts rather than its content — what it ran on, what it spent, what it produced — `agentry list` and its filters answer instead.

**Where inside this session did that happen, and how do I go read it?** The question that follows opening a session, and the one flow that spans two verbs.

```
agentry search "unplaced tokens"        # findings in this session: a locator, then the line
agentry view --turn 19 --level full     # that turn, with every body printed whole
```

Across sessions the same two steps carry the session too, since a turn number alone names nothing:

```
agentry search turn "unplaced tokens" --since 7d
agentry view 4a7c19f --turn 19 --level full
```

The hit's turn number is what the second command takes, which is why a hit carries the main thread's turn even when the passage sits inside a delegated run. **The second step must be able to show every hit the first one reported**, which is why a render of an explicitly selected turn prints result bodies whole rather than capped: the cap keeps a whole-session render scannable, and a caller who named one turn has already narrowed. A flow whose first step reports a passage its second step cannot display would leave the caller worse off than not searching — told the text exists and given no way to reach it. That holds for every part a hit can sit in — a prompt, a reply, a thought, a delegated instruction, a call's argument text, or a result body.

**What did that turn actually do, in a form I can query?** The question an agent has rather than a person, and the reason the machine forms exist.

```
agentry schema view                              # the keys, so nothing has to be guessed from a sample
agentry view --turn 19 --format json | jq '…'    # that turn, every body whole, nothing capped
```

The first step is what keeps the second from being eight exploratory `jq` calls. `--turn` narrows the machine forms the same way it narrows the render, and `meta.numTurns` with each turn's own number is what keeps a one-turn document legible as a slice of a larger session.

**What has this cost?** The question asked about a window rather than a session.

```
agentry cost                     # this session, this folder, this machine
agentry cost --by month          # every month, with the window's total
```

Bare answers the commonest form, and the flow usually ends at the first command; `--by` is for the caller who has a period in mind rather than a scope.

## Output

`agentry` prints a styled view of the session: colorized turns with per-actor glyphs, plus code blocks, thinking, tool calls, and subagents (subject to verbosity).

A turn shows the user prompt as a highlighted block enclosed in a rounded border — the prompt text prefixed with a `❯` glyph (wrapped lines hang-indent to align under the prompt) — then the assistant's reply as an indented left rail (`│`) headed by a `◆` glyph aligned with the rail — prose, thinking, and tool calls hang off the rail, which a closing rule (`╰─`) terminates. With color off, the prompt highlight degrades to plain `❯`-prefixed text.

**A block of lines printed under a header hangs off a left rail closed by a rule.** That is the turn's own chrome — `│` down the left, `╰─` beneath — and it is the rule for every multi-line block agentry prints under a header, so one shape means one thing wherever a reader meets it. **One line hangs off the closing rule instead** (`╰─ the line`), because chrome must never cost more lines than the content it bounds; two or more keep the rail, since content on the rule there would give the last line different chrome from its siblings while saying nothing different. A block with no content prints nothing at all, a bare rule being a line that bounds nothing and reads as a header that found nothing rather than one with nothing to find. A listing's `--include` blocks, a session's findings, and the rendered session's own footer sections all follow it, from the same code. `agentry cost` has no such block — its tables carry a column header rather than a section header, and its notes trail the table rather than hanging under one. **A railed row is budgeted at the widest chrome the rail can write**, which is the closing rule a lone line hangs off rather than the rail its siblings hang off: a section sizes its rows before it knows how many it will have, and a row that outruns the terminal by even one column wraps onto a line carrying none of the block's chrome — the elision mark and the rail both disappear on exactly the rows already too long to read. Every column a row spends is counted the same way, the chrome and the text and the mark that says text was cut, because a budget stated as its own number drifts from the columns printed beside it.

**A turn starts at a prompt a person typed, not at every entry Claude Code files under the user's name.** The log records harness-attached material — a loaded skill's body, a notice that a skill was loaded earlier, a note about an image being rescaled, a nudge after a malformed tool call — as user entries too, and rendering those as prompts would invent turns nobody took and let one of them become the session's title. Claude Code marks such an entry (`turnCompanion`) and its own prompt test refuses to count it, so agentry refuses it on the same marker rather than on what the text looks like. Older logs carry no marker, and for those agentry falls back to recognizing the wrappers the harness writes around injected content, which is what it did everywhere before the marker existed. The one entry that survives both tests despite being written by the harness is a compaction boundary, which stands in for the conversation it replaced and so has to keep its place in the turn sequence. One wrapper on that fallback list was never injected material: `<bash-input>` holds the characters a person typed after `!` to run a shell command in the session, so refusing it discarded a turn somebody took. It opens a turn like any other prompt. The wrappers around that command's own output stay on the list, because the harness wrote those — and the test is now the whole entry rather than a substring of it, since five local entries quote one of these wrappers inside ordinary text and none of the five was typed at a shell. The list also refuses the line Claude Code writes where a reply was cut short (`[Request interrupted by user`), which reads as a prompt and is somebody pressing escape.

**A prompt counts in either shape the log writes one.** Its text is usually a plain string, but the software development kit records the same text as a list of text blocks, and a session whose prompts all arrive that way opened no turn at all — rendering blank, with every response it made outside the per-turn tallies and inside the header. One text block among several does not count, because a tool result is filed under the user's name in that same shape, so an entry carrying any block a prompt would not is refused whatever text sits beside it.

**A slash command the caller typed prints what it said and expands what it ran.** Such a command is not a tool call — the harness runs it directly, and the main log usually keeps the typed line as the prompt and the printed result as a `local_command` system entry. That printed result renders as the turn's own text **at every level**, because it is what the caller read and the log holds no assistant reply beside it: gating it on a channel leaves a step that spent real money rendering as a bare glyph and nothing else, which is how a refused command became indistinguishable from a turn that never ran. Where the command's skill forks, its session renders as a `Skill` call standing ahead of that text, expanding under the subagents channel like any other delegation, since the call Claude Code omitted is the only thing separating the two from each other.

**A typed command opens a turn whichever entry records it.** For most commands Claude Code writes the line the caller typed as their own prompt, but for some — `/context`, `/rename`, `/config`, `/model` and `/memory` among them — it writes that line as a `local_command` system entry instead, and a few of those then write the command's report into the conversation as a further entry of its own. Reading only the first shape loses both halves: the command renders nowhere, its report becomes a turn nobody typed, and a session that typed nothing else is titled by the report's first line. So a system entry recording a typed line opens a turn exactly as the prompt shape does, and that command is the turn's prompt. The report which follows becomes the turn's own text beside what the command printed, and both are kept: the printed output is the drawing the caller read and the report is the same subject written out for the model, each naming things the other leaves out. A report is claimed only while the turn the command opened holds nothing else, and only from an entry Claude Code marked as its own writing — a prompt somebody typed after reading the report carries no such mark and opens its own turn. An entry already refused as injected material is not claimed either, so the wrappers the harness puts around a command's output go on rendering nowhere.

**A local command's output is printed the way it was printed, not reflowed.** It goes out fenced, because the command laid it out for a terminal: `/context` draws a fixed-width grid of block glyphs across twenty columns, and reflowing that as prose runs the grid into one unreadable paragraph. The terminal escapes the command wrote are stripped first — a captured output that styles its own headings would otherwise print those codes as text. The fence opens one backtick longer than the longest run inside it, so output holding a fence of its own cannot close the block early.

**A shell command the caller typed shows what it printed.** Running one with `!` leaves three things in the log — the command, its standard output and its standard error together in one entry, and any reply Claude then wrote about the result — and only the first is anything a person typed. The command becomes the turn's prompt, rendered with the `!` they typed so it is not mistaken for something they asked Claude; its output renders as the turn's own text **at every level**, fenced and stripped of terminal escapes, on the rule a slash command's output already follows and for the same reason — it is what the caller read, and the log holds no assistant reply beside it. Standard error goes in a fence of its own below, under the word `stderr`, because merging the two streams would claim an interleaving the log does not record. A command that printed nothing renders as the prompt alone rather than as an empty fence.

**Rendering these closed a hole rather than adding a channel.** Before this, a typed shell command appeared nowhere in a rendered session — not the command, not its output — and whatever Claude said about the result was charged to whichever prompt came before it. Where the command ran before the session's first prompt there was no such turn, so the reply and its tokens were dropped from the transcript altogether while still counting in the header. Every one of them follows a reply Claude had finished, another such command, or the start of the session, so the boundary always lands where the model had stopped rather than cutting a reply in two.

**That closing message is printed once.** A forked skill's last word reaches the main log as the local command's output, so one message sits in two records; the expansion drops its copy and the turn keeps it, at the depth a reader lands on rather than buried at the end of a nested stream.

Markdown links (`[text](url)`) in assistant prose render as OSC 8 terminal hyperlinks: the link text is shown in a dedicated link color and is clickable, and the raw URL is hidden. The URL is used verbatim as the href, for any scheme (`https://`, `obsidian://`, …) — agentry constructs nothing. Only assistant prose is linkified (not tool output, thinking, or prompts), and a link whose text glamour wrapped across lines stays plain. Like color, this is gated on a terminal: with color off, the link renders in glamour's default form (the text followed by the URL).

Bare URLs in assistant prose — any `scheme://` URL written without link syntax (`http://`, `https://`, `obsidian://`, `vscode://`, …) — become clickable too, the URL text itself as the link. One scheme gets a nicer label: an `obsidian://open?…&file=<path>` URI renders as an Obsidian-style wikilink — `[[<note>]]`, the file's base name with any folders and the `.md` extension dropped (a `#heading` or `#^block` anchor is kept) — linking to the full URI; so a session that cites a note shows `[[Note]]` rather than the raw `obsidian://…` string, with the vault and path preserved in the hidden href. Any other obsidian URI (or an `open` without a `file`) shows its URL text like the rest. All bare links use the same dedicated link color. A URI is recognized bare when it has the `scheme://` form — a leading letter, then letters/digits/`+`/`-`/`.`, then `://`; a scheme without `//` such as `mailto:` is not autolinked and must use `[text](url)` syntax. Trailing sentence punctuation (`.`, `,`, `;`, `:`, `!`, `?`) is excluded from the href, as is a trailing `)` with no matching `(` inside the URL — so a URL wrapped in `(…)` drops the closing paren while one that itself contains balanced parens (a Wikipedia article, say) keeps it. The same conditions apply as for markdown links: assistant prose only, gated on color, and a link whose text glamour wrapped across lines stays plain.

Color is auto-detected: styled (ANSI) when stdout is a terminal; plain, unstyled text when stdout is piped or redirected, or when `NO_COLOR` is set. `--no-color` forces plain output. Output is not paged in this version — pipe to a pager if you want one.

**Every surface draws a fact in one color, named for the job the text does rather than for its hue.** A row's own facts — when it happened, how long it took, the half of an id a reader types — are drawn one way; a count, a path label, a rail, a table's note are drawn quieter; a verbatim body is drawn brighter than the prose around it; and a title takes whatever foreground the reader has chosen, because a fixed near-white is the loudest thing on a dark background and nearly the background itself on a light one. The roles are the rule, not the codes: a surface asking for the role keeps reading correctly if the shade changes, where one asking for a shade has written the whole scheme into itself. That is what a search row and a listing row failed at — the same facts in the same columns with the same gaps, and each of the five drawn differently, which read as correct on either surface alone. Nothing carries meaning by color alone anywhere: a status has a glyph, a cut has an ellipsis, a bar has length, and an id prints whole with only its emphasis lost. **Every shade agentry picks for itself is a pair, and the terminal's own background chooses between them.** A gray chosen to read against a dark terminal sits close to the page on a light one, and the shade a quoted body was drawn in — a near-white — left a light-theme reader unable to see the tool output in a rendered session at all. The pairs are not symmetrical and cannot be: against a dark background a quoted body is drawn brighter than the prose around it, which is what marks it as quoted, while against a light one the prose is already close to black, so the body takes the strongest shade available and is legible rather than prominent. Legible on both beats prominent on one and invisible on the other. The terminal's own sixteen colors are left alone, a reader having already chosen those.

**The header's first line dates the session and names its active time, not the span between its first and last entry.** A session is not one sitting: it can run across more than one calendar day, so a bare `18:03 → 12:32` reads as an overnight run whether the work took two days or a week. The line carries the date beside each clock time when the two differ — `Sep 15 18:03 → Sep 18 12:32` — and one date when they do not — `Sep 18 09:12 → 11:40`. After the times comes the **active time**, the sum of each turn's own span, followed by the day count when the session spanned more than one: `1h04m active over 4 days`. The wall-clock span is not printed at all: it measures how long a terminal stayed open rather than how long the session worked, and can run many times longer than the active time it replaces — a session left open overnight reads as a marathon it never ran — so the figure it replaced misreported nearly every session. Nothing is lost by dropping it, since both timestamps are still on the line. A session whose log records no turn shows no active figure rather than `0m`, the rule the model and effort already follow.

**The header gives each fact a line of its own, and there are four**: when the session ran, what it ran on, how big it was, and what it spent. When and what-it-ran-on shared one line until this version, and that line could not hold both. At the 100-column width a render falls back to when its output is not a terminal, a line reading `Session · Sep 15 18:03 → Sep 18 12:32 · 1h19m active over 4 days · claude-opus-5 · high effort` could overflow to 102 columns inside a 96-column box and lose the ` · cli` that would have carried it past the edge — nothing on screen said a field was missing, so a reader learned where the session ran only by widening the terminal and rendering it again. A line that still outruns the box now **wraps inside it**: the wrap costs one line against the hundreds a session's render already runs to, and no width drops a field.

The header names the **model** the session ran on, opening the second line and standing before the effort. It resolves the way the two settings beside it do — the last value the log carries, with the whole sequence spelled out (`claude-sonnet-5→claude-opus-5`) when the session switched mid-way. Switching is not an edge case, so a header naming only the first would misreport some sessions. `<synthetic>` is excluded from that reading — it is what Claude Code writes on messages it composes itself (an API-error notice, a session-limit warning, `No response requested.`), those carry zero tokens and name no model the session ran on, and counting them would end a session on a model that never ran. A session whose log names no model at all says nothing, where it once said `unknown`: that is the rule effort and entrypoint already follow, and the word claimed a fact the log does not carry. `--format json` carries `model` and, when it changed, `models`.

The header also names the **reasoning effort** the model was run at, immediately after the model and read as a phrase — `claude-opus-5 · high effort`. Effort moves both cost and quality, so without it two sessions on the same model at very different settings are identical in every view agentry produces. A session that changed effort mid-way shows the transition the same way the entrypoint does (`xhigh→high effort`), and the resolved value is the last one, matching the session's last activity. Not every session carries the field — Claude Code added it in 2.1.212 — and one that does not says nothing rather than guessing a default. `--format json` carries `effort` and, when it changed, `efforts`.

The rendered view names **where the session ran** in its header, after the model — `app→cli` when a session was started in the desktop app and resumed from the terminal, or a single value when it never moved. The listing compresses that case to a `+` suffix because a column is four characters wide; the header has a full line to itself, so it spells the transition out. The vocabulary is the listing's (`cli`, `app`, `sdk`, `?` for an unrecognized value — see Listing sessions), and a session predating the field says nothing rather than guessing.

**The header's third line counts the session's size and separates a call that failed from one that was refused** — `30 turns · 385 tools · 2 subagents · 4 failed · 3 denied`. A refused call carries the log's own denial reason where a failed one does not, and the two ask for different things: a failure is something to go fix, a refusal is a permission rule or an automode boundary that held. A single `errors` count covering both would misreport what happened, conflating a failure someone needs to fix with a refusal that is a boundary working as intended — and the tool line at `--level detailed` already spells a refusal out in place of the error glyph, for exactly this reason. Each count is dropped when it is zero, so a session that failed nothing and was refused nothing shows neither. Both read the session's own top-level calls, matching the tool count beside them; a call made inside a subagent is not counted, the rule the per-turn tool count already follows. **The rule beneath each turn splits the same two counts**, from the same helper over that turn's own calls, so the turns' figures add up to the header's — a rule reading `5 errors` sent a reader looking for five things to fix where one of them was a permission boundary doing its job.

**The rule closing each turn says what that turn spent**, after its duration and counts — `╰─ ◆ 1m · 5 tools · 6 in / 5.2k out · cache 98% · ~$0.50`. The wording is the header's, so a reader meets one phrasing at two scales rather than two; the leading `~` marks the dollars as agentry's own price, the same mark the Cost section uses. Without it the only per-turn spend on the page is the summary table's token column, which carries no cache share and no dollars and sits far below the turn it describes — so the question "what did that step cost" was answerable only by scrolling and matching a step number.

Each field is dropped where the log does not support it: a turn that made no request shows none of the three, a turn with nothing cached or read back shows no cache share, and a turn whose models agentry holds no rate for shows no dollars rather than `~$0.00`. The dollars are priced **per model before summing**, since a turn that delegated to a cheaper model is not priced at the model its own thread ran on. Such a rule can grow wide — a long turn that also failed and was refused packs every field onto one line — so it fits the 100 a non-terminal render falls back to and wraps in an 80-column terminal rather than dropping a field, the rule the header already follows.

**A session's turns account for every response it made.** Each session's rules now sum to its header exactly, where before they could disagree. Four faults produced those disagreements, and each is stated where it belongs: a submission whose shape opened no turn, a prompt id claimed by two turns, a forked log the charging walk could not reach, and a log carrying the same entry twice. The header and the Cost section still answer for the whole session, and now the rules add up to them.

The header's **token tally counts each API response once**, not once per log entry. Claude Code writes one assistant entry per content block of a response — a reply holding a thought and three tool calls becomes four entries — and repeats that response's whole usage object on every one of them. Adding the entries up therefore multiplies a reply's tokens by how many blocks it held, and the multiplier is not constant across replies, so it distorts the per-turn ranking in the summary below as well as the totals. agentry keys the tally by the response id each entry carries (`requestId`) and counts **the entry whose output count is highest**, discarding the rest; an entry carrying no response id — one Claude Code composed itself, or one from a log old enough to predate the field — is keyed by its own entry id instead, which counts it once, exactly as it was counted before.

**The highest entry and not the first, because a response's repeats are not identical.** Claude Code writes each entry as the reply streams, so the input count and both cache counts match on every entry of one response while the output count **grows** — an early entry carries a partial figure and the last carries the finished one. Counting the first entry therefore undercounts output, and not by a rounding. Taking the highest brings the tally within a few percent of Claude Code's own accounting, which is the one external figure available to check it against. The rule applies everywhere a token figure is produced — the header, the per-turn summary, `--format json`, and the listing — so no two surfaces can disagree. Every count is abbreviated the same way wherever it is printed: exact below a thousand, then thousands (`3.1k`, `211k`), then millions (`3.1M`) and billions (`12B`) as the count reaches them, because a roll-up's figure written in thousands (`3108k`) is not read at a glance.

The header also names what the session **cost in dollars**, and **how much code it changed**, at the end of the token line — `Tokens: 494 in / 211k out  ·  cache 97%  ·  saved 40%  ·  $35.07  ·  +342/-8`. Claude Code keeps a running total of its own in the log and rewrites it as the session goes, so agentry reads the last such record rather than adding them up. A session whose log carries none — anything before Claude Code 2.1.241, and any session it has not written one for — shows no dollar figure rather than `$0.00`, the rule the model and effort beside it already follow: the log simply does not say. The figure is Claude Code's own accounting and not a price agentry computes from tokens, and this surface keeps it that way: a `$` in the header is always the record, so a session showing none is one Claude Code wrote no record for rather than one agentry declined to price. A dollar figure on every session, and what a day or a month cost across many of them, is `agentry cost` (see Rolling up cost), which prices the tokens itself and says so. It **does** include a subagent's spend. The log never says so, but Claude Code prices every request a session's process makes into one ledger, and pricing a session's main log alone against published rates comes in low against that record; adding the subagent sidecars' tokens closes most of the gap. What the figure does not cover is requests Claude Code makes without writing an entry for them — its own background work — and what it can undercount is a session whose ledger was reset partway, which zeroes the earlier legs. The two pull opposite ways, so the record and a transcript price agree closely and can differ either way on one session (see Rolling up cost).

**Beside the cache share the header names what caching saved** — `cache 97%  ·  saved 40%`. The two are a pair rather than a repetition. The cache share is how much of a request's input was served from cache; the saved share is what that took off the bill, and a session can read high on one and middling on the other, as the example does — 97% of its input came from cache, and the saving is held to 40% because output tokens carry most of what it spent. A session with nothing written to cache and nothing read back shows no cache share rather than `cache 0%`, the rule the turn rule states in the same words: a zero there would read as caching that ran and saved nothing, where the truth is that none was attempted. The case has never arisen in practice — a session with no cache counters also carries no uncached input — so what the rule buys is that the header and the turn rule cannot diverge on a session that does reach it.

**The comparison is the same tokens priced twice**, which is what makes it a fact rather than a guess. Caching does not change how many tokens a request sends — the whole context goes on every request either way — it changes the rate the resent part is charged at, a tenth of the input rate to read and 1.25 or 2 times it to write. So the second price is every cached token charged as fresh input, with the output unchanged, and the difference is the saving and nothing else. The saved share tracks the cache share — the two move together — and spreads a session further from its neighbours than the cache share alone does.

**In the header the saved share is a percentage and never a dollar figure.** The rule above holds there without exception — a `$` in the header is always Claude Code's own record — and a computed dollar saving printed beside a recorded dollar total would put an estimate and a record on one line with nothing telling them apart. The footer's Cost section does print it, as `caching saved ~$1053.72`, because there every computed figure carries the `~` that separates it from the record on the row above. `--format json` carries it as `cacheSaving` on both paths.

**The saving is priced per model rather than per session.** A session's responses are split by the model that answered before either price is taken, because the rates are not proportional across models: one tier prices cache reads at a fortieth of its own input rate where every other prices them at a tenth, so pricing a mixed-model session at its last model's rates would report a saving it did not get. A response whose model agentry holds no price for is left out of both prices rather than counted at zero, the rule the roll-up already follows, and a session with no priceable response at all shows no saved share rather than `saved 0%`. The saved share is dropped wherever the cache share beside it is dropped, since the two are one pair.

**A session caching cost more than it saved reads negative, and is not clamped.** A cache write bought for an hour costs twice the input rate, so a session that writes a large cache and then ends without reading it back pays more than the same tokens would have cost uncached: `saved -97%` says the session paid nearly double. A session reading negative is not unheard of — most such cases are non-interactive runs the listing's default already hides, and negative sessions remain rare among the ones a caller actually sees. Clamping the figure at zero would render those as sessions caching neither helped nor hurt, which is the one reading that is never true of them.

The lines added and removed come from that same record, so they appear exactly when the dollar figure does. They are **dropped when both are zero**, which is the common case, and a `+0/-0` on every one of them would spend the header's width on nothing. Nothing is lost by dropping them: the dollar figure beside them already says the record exists, so a session showing a cost and no counters changed no code. Unlike the cost, the counters are known to reach **delegated** work — a session whose main thread made no edit call itself can still record lines added by its subagents — so a session that edited only through subagents still reports what it changed. What they do not count is a file written by a shell command: a session that only wrote files via shell commands, heredocs included, and made no edit call, recorded zero lines either way. agentry's `files` channel does catch those, so a session can list files it changed and still report no lines — the two read different records and answer different questions.

The rendered view ends with an **Outputs** section naming what the session produced beyond its own transcript: one line per pull request it opened and one per artifact it published. These are the same two facts `list --include outputs` shows, read the same way and deduplicated the same way (see Listing sessions), so the two paths never disagree about what one session produced. It sits after the last turn and before the metrics summary, because an output is a result of the session rather than a property of it — the header says what the session *was*, and a pull request is what came out of it. A session that produced neither has no such section, which is the common case.

Outputs is one of seven **footer** sections, each printed only when it has content, in this order: **Files** (every file the session modified, one absolute path per line, first-seen order, truncated from the left), **Outputs**, **Tools (by identity)** (the listing's `tools` breakdown — `Skills`, `Agents`, `Bash`, `Edits`, `Denied`, `Other`, entries reading `name ×count`), **Cost** (below), **Summary (by token cost)** (the per-turn table), **Day by day** (turns and active time per local calendar day, with what that day cost, on a session that spanned more than one) and **Session** (below). Files and Outputs lead because they are what the session touched and produced; the three that follow are how it worked, so a reader who stops after two sections still has the outcomes. Files and Tools read the same records as the listing's `files` and `tools` channels, through the same code, so the two paths cannot disagree about one session.

**The footer is not gated on verbosity: every section prints at `--level minimal`.** Gating the three aggregate sections on the metrics channel, on the reasoning that an aggregate is machinery a reader did not ask for, does not hold up: a rendered session already runs to hundreds or thousands of lines, and the per-turn table and the other aggregates add only a handful more to it. The gate saved a reader nothing they would notice and cost them the section's existence, since nobody types a flag for output they have never seen. An outcome was never the argument's whole reach: thinking and tool bodies are hidden at low verbosity because they repeat the transcript at length, which a session-level aggregate does not.

What the gate stood in for is length, and **every section bounds its own instead**. Files shows ten paths and names the remainder (`… (85 more files)`), which covers the common case comfortably while still bounding an outlier. Tools shows eight entries per category and names the remainder, because an uncapped section could outrun a small session's whole transcript. Summary keeps its eight rows. Day by day needs no cap — a session spans at most a handful of days, so the section stays short on its own. Outputs needs none either, since a session rarely produces more than a few. `--format json` carries every list in full, uncapped, so a cap costs a caller nothing they cannot recover.

`--no-metrics` removes the three aggregate sections and leaves Files and Outputs, which are the outcomes. **There is no `--metrics`**: with the sections always printed it could change nothing, and a flag that changes nothing reads as a setting that failed — the reason `cost` offers two `--level` values rather than four. A caller who types it gets the usual unknown-flag error with `--no-metrics` suggested.

The **Cost** section is what the session's money went to, in labelled rows: `recorded` (Claude Code's own running total, when the log carries one), `priced` (what this log's tokens are worth at agentry's list prices), `by model`, `by agent` (the delegation the tokens were spent under, the main thread named `main` rather than left blank so the axis sums to the session), and `each` (the price per turn, per active hour, and what caching took off the bill). A model agentry holds no rate for is named on an `unpriced` row rather than counted at zero, the rule the cost roll-up already follows. Entries on an axis are ordered by dollars descending and capped at eight with the remainder named, like the tool tally above them.

**The Summary table charges a turn for every log it forked**, so a step that delegated is ranked by what it actually cost rather than by the handful of tokens its own thread wrote. Three routes reach a fork and all three are followed: an `Agent` call, a `Skill` call whose skill runs in a separate session, and **a slash command the caller typed**, which makes no tool call at all for a map keyed on one to find. Claude Code stamps a forked log's first entry with the prompt id of the message that started it, and that is what charges a typed command's fork to its step — without it a typed command's fork ranked last on zero, indistinguishable from a step where nothing ran. The tool count beside the figure still counts the turn's own calls only, matching the header and the Tools section.

**A forked log no prompt id places is charged to the turn it ran inside.** Claude Code stamps a fork with the id of the message that started it, and sometimes that id appears on no user entry in the main log at all — the submission simply is not recorded. Such a fork goes to the last turn that had started when it began, which loses nothing: its tokens, its dollars and its row in the Tools section were all missing before. A fork carrying no prompt id whatever is still placed nowhere, because nothing ties it to a turn and putting it on whichever turn spans the gap would invent an attribution rather than find one.

**A turn is charged for a forked skill a subagent started of its own accord.** Such a fork is paired to its call by name rather than by a structured id, and the walk that charges a turn followed structured ids only — so the log counted as claimed and was unreachable at the same time, and nothing charged it anywhere.

**A log can carry the same entry twice, and the repeat is dropped.** A session can replay a stretch of turns verbatim under fresh prompt ids, every repeat byte-identical to its first copy. Rendering both printed that conversation twice, ranked the repeats as steps of their own, and counted their tokens, dollars and tool calls a second time in the per-turn figures, while the session tally deduplicated them away. This is rare, but when it happens the repeats are dropped rather than double-counted.

**A reminder the harness attaches to a tool call opens no turn.** Claude Code files a re-invocation notice, a skill body or an expanded command under the user's name, marking it as its own material and naming the call it belongs to. Both marks are required: the first mark alone also appears on prompts a person actually typed, so refusing on it alone would delete real turns, while the two together correctly separate the harness's own material from what a person typed.

**A prompt id is not a turn, so each forked log is charged to exactly one.** Claude Code writes the same id on a typed command and on a shell command queued behind it, and the two are separate turns; a lookup keyed by the id answers both, which charged one forked skill's tokens twice, drew its call in both turns, and counted it twice in the Tools section. The fork goes to the earlier turn — the submission that started it — and the later one carries only its own reply. This is rare, but when two turns share an id, the fork is reached through its own tool call instead, which was never ambiguous.

**Every computed figure is marked with a leading `~`, and the record is not.** The header's rule — a `$` there is always Claude Code's own record — stands unchanged; the footer prices the same session itself and needs both figures on screen, because the record covers only a minority of sessions and, where both exist, the two can differ by a few percent either way. One mark tells them apart wherever they sit together, which is what lets the Cost section, the Day by day column and the saved-caching figure print at all. The same arithmetic and the same rate table `agentry cost` uses produce them, so a session priced in a render and priced in a roll-up agree to the cent.

**A fact belongs to the header or the footer, with one exception.** The header identifies the session: when it ran, where, on what, how big it was, what it cost. The footer describes its work. That is why the model, the effort and the totals sit above and do not appear again among the sections that follow.

The exception is the footer's last section, **Session**, which closes the render by naming the session and restating its size. It carries one labelled row each for `id`, `title` (the listing's own title ladder, so a session is called the same thing in both places), `project` (the working directory the log records, truncated from the left), `root` (the conversation root a fork shares with its parent), `log` (the JSONL agentry read, as the locator resolved it — nothing else in the output says which file the render came from), `when` (the header's dates and active time), `ran on` (its model, effort and entrypoint), `size` (the header's counts, from one helper so the two cannot differ), `spend` (the header's token line, likewise) and the two commands that reach the session again — `agentry <id>` and `claude --resume <id>`. The four header lines are restated whole rather than in part: a card that named the session but not when it ran or what it ran on would send a reader back up the scroll it exists to spare them. A row whose fact the log does not carry is dropped, the rule every optional line follows.

**Until this version a rendered session named itself nowhere at all**, so a reader who had just read one could not cite it, resume it or render it again without going back to a listing to find its id — and an agent reading the output had no handle for it either. The restatement of the header's own lines is deliberate rather than an oversight: a large session runs to thousands of lines, which puts the header out of reach exactly where a reader decides what to do with what they have read. The section is not gated on the metrics channel, since an id is how a reader acts rather than detail about the work. Both commands carry the id **in full**: a listing can shorten one because it knows every id beside it, and a single render knows none of them, so a prefix printed here could name a session the reader did not mean.

With color on, each line is an OSC 8 terminal hyperlink, following the same split assistant prose already uses. A pull request is its own URL as the link text, the way a bare URL in prose is. An artifact is its **title** as the link text with the `claude.ai` URL hidden in the href, the way a markdown link is — because an artifact id is an opaque uuid, so showing it in place of a name would be strictly worse than the name. An artifact whose record carried no title falls back to its URL as the text. With color off the section degrades the way links in prose do: the text and the URL both shown, plainly, with nothing to click.

`agentry view` **with no id resolves to the most recent session that was not a non-interactive run**, for the same reason the listing hides them: on a machine using hooks the newest session is usually a few-second headless run, so "show me my last session" would otherwise render a hook. Naming an id renders that session whatever its kind — the id is an explicit request and is never second-guessed. When a project holds nothing but non-interactive sessions, `view` renders the most recent one anyway and says so on stderr; refusing would be wrong, since sessions plainly exist.

`--from` chooses which kind of session that resolution walks back to, taking the listing's four values (`cli`, `app`, `sdk`, `all` — see Listing sessions). `agentry view --from sdk` renders the most recent non-interactive run, which is how the hook or `claude -p` call that just fired gets read back; `--from all` renders the most recent session of any kind, the pre-default behavior. A named value that matches no session here is an error, not a fallback to something else: the caller asked for one kind, so rendering another would misreport what they are reading — which also means the stderr note above belongs to the default alone. `--from` beside a session id is a usage error, since the id already names the session and the flag could only contradict it.

`--turn` renders **part of one session's transcript**: `--turn 11` one turn, `--turn 11-14` an inclusive span. It exists because a session runs to thousands of lines and a reader who knows which turn they want had no way to ask for it — the only slice available was a line range over rendered output, and line numbers belong to one flag combination and move under another. A turn number does not move: it is the same number at every level and in every format, and it is what `agentry search` prints beside each hit, so a number copied out of a search goes straight into this flag.

**The header still describes the whole session, and a line beneath it says which turns are shown** — `showing turns 11-14 of 31 turns`, with the same plain hyphen the flag takes, so the span reads back as the value that produced it. The header is not recomputed over the span: every figure in it comes off the session's own tallies, and a narrowed transcript counted from what it rendered reported one turn beside the whole session's tokens and dollars, which reads as one turn having cost the lot. The footer's aggregate sections describe the session for the same reason; the per-turn token table is the exception, listing the turns actually rendered, since a table of turns under a one-turn render is a table of that turn.

**A turn number is a selector, so it narrows the machine forms too** — the rule the listing's selectors already follow against `--format json`, where `--include` and the verbosity flags do not. The span is applied once, before the three emitters branch, so they cannot disagree about which turns a caller asked for. Two fields carry what the narrowing would otherwise delete: `meta.numTurns` is how many turns the session holds, which is no longer the length of `turns`, and each turn carries its own `turn` number, which its position in a selected array no longer gives. Both are present whether or not a caller narrowed anything, because a field that appears only under a flag is one every consumer has to branch on.

The start must name a turn that exists: `--turn 99` of a thirty-one-turn session is an error naming the count, since an empty render would not say what went wrong and the count is the one thing the caller cannot work out from nothing being printed. The end is a ceiling rather than an assertion, so `--turn 29-99` reads as "from 29 to as far as it goes" and renders to the last turn. Turns are numbered from 1, so zero and negatives are errors with no other reading, as is a span that ends before it starts. **`--turn` beside a bare listing is a usage error**, not a flag silently ignored: a listing has no transcript to select from, and ignoring it would leave a caller believing a slice applied. It is the whole render-flag family's rule rather than this flag's own — see Listing sessions, which owns it.

Session-id completion follows the same default: it offers the ids a listing would show, not every id on disk, so tabbing a UUID does not surface hook runs ahead of the work you are looking for. It reads `--from` off the command line being completed, so `agentry view --from sdk <Tab>` offers the runs that command would render rather than the ones the default shows.

`--format json` emits the full parsed session model as JSON instead of the styled view — the render path's machine-readable form, for agent consumption and piping into `jq`. It serializes the same in-memory model that drives terminal rendering: a top-level object with `meta` (`id`, `model` plus `models` when it changed mid-session, `effort` plus `efforts` on the same rule, `start`, `end`, `usage`, `costUSD` with `linesAdded` and `linesRemoved` when the log recorded them, `numTurns`, `numSubagents`, `entrypoint` plus `entrypoints`, `title`, `cwd`, `rootUuid`, `path`, `files`, `dailyActivity`, `dailyUsage`, `tools`, `failures`, `denials`, and `prs` and `artifacts` — the same fields, resolved the same way, that `list --format json` carries per session, so the two paths never disagree about where one session ran, what it touched or what it produced) and `turns`. `files`, `dailyActivity`, `tools` and `denials` are what the footer's Files, Day by day and Tools sections print, uncapped here, `dailyUsage` is the per-day, per-model, per-delegation split the Cost section prices — the same rows the listing carries, built here from sidecars the render path had already parsed rather than read off disk a second time — and `title`, `cwd`, `rootUuid` and `path` are the closing Session card's naming rows — `path` being the log file the render was read from, which the listing carries no field for. Each turn carries its `turn` number, `prompt`, `start`, `end`, `usage`, `toolCount`, `errorCount`, and an ordered `events` array; each event has a `kind` — the string `text`, `thinking`, or `tool` (not its ordinal) — with a `text` body for the first two, or a `tool` object (`name`, `args`, `identity`, `model`, `prompt`, `denial`, `result`, `isError`, `start`, `end`, and a nested `subagent` event stream when the call spawned one) for the last. `denial` is why a call was refused — `permission-rule`, `automode-blocked`, `automode-unavailable`, or `user-rejected` — and is absent on every call that actually ran, including one that ran and failed; `isError` is true either way, so `denial` is what separates "the tool was not allowed to run" from "the tool ran and returned an error". `identity` is the call's grouping label — the same value `list --include tools` groups by (the invoked program for `Bash`, the skill for `Skill`, the subagent type for `Agent`; absent for tools whose own name is their identity), so the two paths name one call the same way rather than the render path knowing less. `model` is the model a call delegated to, absent when it named none: only `Agent` carries one, and a call that omits it leaves the subagent on the session's own model. `prompt` is the instruction the delegated run received, carried whole and by `Agent` alone — absent on every other tool, none of which is given one. All three are recovered from input fields `args` discards — `args` is a one-line human summary, and for `Agent` that summary is the description — so without them the type, the model and the instructions of a delegated subagent could not be read back out of a session at all, which is what a cost audit asks of every `Agent` call and what any reading of a session whose substance is its delegations asks first. The instruction is the largest of the three and the one the description stands in for: a label written in a few words cannot say what the subagent was asked to do, so a session that delegated its work carries none of that work's terms without it. Being the complete model, it ignores the verbosity flags (`--level` and the channel toggles) and color — those shape only the text view, whereas the JSON is always the whole model. `--format` also accepts `text` (the default styled view); an unknown value is a usage error, suggesting the nearest valid format like every other enum flag. **`turns` is always an array**, empty on a session that has none — a log holding only bookkeeping entries produces one — rather than `null`. That is the rule the listing's array and the roll-up's object already follow, and it is what lets a caller iterate the document's primary collection without first branching on which of two shapes it got back. This is the render-path counterpart of `list --format json` (see Listing sessions), which serializes the lightweight per-session summaries.

`--format jsonl` emits the same facts as `--format json` one JSON value per line, and exists because a document must be read whole before any part of it is usable. A large session answers a query over a handful of its turns — or just one of them — far more cheaply as a stream, whose reader can stop once it has what it needs, than as a document, whose size does not move no matter how little of it is asked for. Most sessions do not need that: they render small enough that `json` stays the default and stays the better shape for a whole-structure question like which turn ran the most tools. A caller wanting the document back from a stream pipes through `jq -s .`; the reverse costs the full read the stream exists to avoid, which is why the stream is the format that gains rather than the one that replaces.

Every line is an **envelope around a payload** — `type`, `tool`, `sessionId`, `ordinal`, `time`, and `payload`. The envelope is what a consumer reads without knowing which tool produced the line; the payload is the part that is agentry's own. `tool` and `sessionId` ride every record rather than a header alone because the reason a line format exists is that two streams concatenate: after `cat`, a bare `ordinal` names nothing, and a stream filtered to one record type has discarded whatever header carried its provenance. `ordinal` is session-wide, starts at 1, and is present on every record, which is what makes a merged stream sortable. `schema` sits on the first record of each stream only, being constant for the run.

The record types are the verb's own. The render path emits one `meta`, then per turn a `turn` carrying that turn's prompt, timings and totals, then one `event` per event — the turn record deliberately does not nest its events, since a turn that delegated would then carry the whole delegated session, and a single line for that turn could dwarf every other line in the stream. **Nesting is carried by `depth` in document order instead**: a tool call that spawned a subagent is followed immediately by that subagent's events at one greater depth, returning to the parent's depth when the child stream ends, each event keeping the turn number it belongs to. Nothing is dropped, and walking the stream back into a tree reproduces the model the parser built. An `event` payload carries `turn`, `depth`, `index`, `kind`, and then the same `text` body or `tool` object the document form gives — the tool object without its `subagent` stream, which follows as records of its own. `index` counts an event's position among its siblings at its own depth, so it restarts inside every subagent stream and orders a sibling list rather than identifying a record; `ordinal` on the envelope is the field that is unique across the stream. The listing emits one `session` per selected session, carrying the summary the array carries per element. The roll-up emits a `report` header holding the document-level fields (`by`, `selection`, `spread`, `recorded`, `unpricedModels`, `pricesVerified`), then one `bucket` per row, then a `total`; the three-scope summary emits an `overview` header and one `scope` per panel. A merged roll-up across several sessions is the case this shape is for, since documents do not concatenate and buckets do.

Everything `--format json` ignores, `jsonl` ignores identically — the verbosity flags, the channel toggles and color — and every rule that names the machine form applies to both: the listing's default cap never applies, `--chart` is rejected beside either, and an empty listing writes nothing rather than an empty array, there being no wrapper to emit. An unknown `--format` value remains a usage error suggesting the nearest of the three names.

## Listing sessions

`agentry list` lists the sessions in the current directory's project instead of rendering one, so you can find the one you want. Bare `agentry` with no session id is the same listing — `list` is its explicit form — and every flag in this section works on the bare command too (`agentry --since today` == `agentry list --since today`). Sessions are selected by recency (most-recent activity) and printed oldest-to-newest, so the most recent sits at the bottom, nearest your prompt — the convention of `ls -ltr`, shell history, and chat logs for unpaged scrolling output. Each is one row: the time of the session's last activity — when its most recent turn ended, the same recency the list is ordered by (falling back to its start when no later timestamp is known) — its **active time** — how long its turns ran, summed from their own spans, the same figure the rendered header names and from the same sum — its turn count, a title, and and its session id in full, with the shortest prefix that is unique among the rows shown — never below 8 characters — drawn brighter than the rest of it. Pass the prefix back to `agentry <id>` to render the session, or the whole value to `claude --resume`. The title is chosen by a fallback ladder: the session's **manual title** when present — a name you chose wins over everything below, and Claude Code freezes its own summary once you set one; otherwise Claude Code's own session summary (the `ai-title` it writes into the log, latest one winning); otherwise the first user prompt, skipping a leading `/clear` (which only resets context and says nothing about the session) in favor of the next prompt; a session that is nothing but `/clear` keeps it. A typed shell command is skipped on the same rule and for the same reason — `! git status` names what someone ran, not what the session was for — and a session holding nothing else keeps it. A `/clear` typed with trailing text on the same line (Claude Code records the text as the command's arguments) is still treated as `/clear` and skipped — the trailing text describes the reset, not the session.

**A title's lines are joined, not ended at the first.** A title is a prompt wherever nothing better was recorded, and a prompt can run to many lines, so ending at the first deleted the rest of it with nothing to mark that they went: a session listed under its prompt's opening words read as a session about them. Joined, the column cuts what will not fit and that cut ends in `…`, which is the rule every other elision on this surface follows. Runs of whitespace collapse with the breaks, a title laid out for reading being a row of gaps once its lines are joined. This holds wherever a title or a prompt is drawn on one line — the listing's rows and its `--include prompts` lines, a session's closing card, the per-turn table, and a search row.

**The duration column reported the span from first entry to last until this version**, which is how long a terminal stayed open rather than how long the session worked, and could run many times longer than the actual active time — misleadingly reporting hours for what was really minutes of recorded work. Sub-minute figures keep their seconds (`8s`), since a headless run is often that short. A session whose log carries no activity records leaves the column blank rather than showing `0m`, the rule every column here follows for a fact the log does not carry.

The **manual title** rung reads two entries, not one, because Claude Code records a chosen name in two places. Renaming a session writes a `custom-title`, and naming it with `--name` at launch or `/rename` in session writes an `agent-name` — the name its statusline shows. The two usually carry the same string, but a session named only at launch has an `agent-name` and no `custom-title`, and a ladder reading only the latter falls through to the generated `ai-title` and displays a name you did not choose. Both count as manual, neither outranks the other by kind, and **the last one written to the log wins** — the same latest-wins rule each already had on its own. This matters because the two can be set at different moments: `/rename` names the session you are in, while `/clear NAME` labels the session you are leaving, so a session can receive an `agent-name` early and a `custom-title` later. File order is the only ordering available — these entries carry no timestamp.

Forked sessions are grouped. Claude Code's `--fork-session` (and the in-session `/branch`) copies a session's conversation into a new file, so a fork and its parent share the same root entry; agentry detects this by their shared root id and lists the family together — the original session's row, then each fork indented beneath it with a `└─` marker. The original is the **earliest-created file** in the family: a fork is a new file written at fork time and cannot reproduce the original's file-creation time, even though its copied content reproduces the original's in-conversation timestamps. (On platforms where a file's creation time is not readable — anything but macOS — agentry falls back to the modification time, which can mis-order a family whose sessions all stayed active.) A family takes its position in the list from its most-recently-active member. `/clear` is not a fork: it starts an empty session with a fresh root id, so it never joins a family.

A fork inherits its parent's title — Claude Code seeds the new session with the parent's `ai-title`, so until it regenerates one the two are identical and indistinguishable in the list. While a fork's title still equals its parent's, the listing instead titles it by its **first divergent prompt**: the first prompt the fork has that its parent does not — the first turn unique to the fork (a leading `/clear` is skipped, as in the title ladder, since `/clear` is already absent from the prompt list). A fork that has added no new prompt yet keeps the shared title. This is a text-table refinement only; `--format json` reports each session's real stored title.

A title that merely repeats the row's **worktree** is replaced the same way, by the session's first prompt. A launcher that derives both a worktree and `claude --name` from one argument makes the two identical by construction — a session in worktree `plan` titled `plan` — and the worktree column beside it already carries that string, so the title spends the field a row is scanned by on a duplicate. The trigger is the duplication rather than any judgement about the name: a title equal to the worktree name falls through, and one a person wrote (`Plan the migration`) stands however similar it looks. A session with no prompt recorded keeps its title, as a fork with no new prompt does. Like the fork refinement this is text-table only, so `--format json` still reports the stored title, and it deliberately departs from Claude Code's own precedence, which ranks a chosen name above a generated summary unconditionally — the listing can afford to, because it is the surface that also draws the worktree column and can see the duplication.

By default the list shows the 10 most-recent sessions. `--limit N` changes the cap and **`--limit all` removes it**. `all` rather than a sentinel number because agentry already spells an exhaustive value that way — `--from all`, `--include all` — and because `0` means literally zero on `--max-lines`, printed two lines from `--limit` in the same help output, so one value would mean none on one flag and every on its neighbour. `--limit 0` stays accepted, being what the flag took before `all` existed; a negative count or any other word is a usage error naming the nearest keyword. Two time-frame filters narrow the window, both compared against a session's last-activity time:

- `--since WHEN` — sessions active at or after WHEN.
- `--until WHEN` — sessions active at or before WHEN.

WHEN is one of: `today` or `yesterday` (local midnight of that day); a span back from now with a unit — `Nh`, `Nd`, or `Nw` (e.g. `24h`, `7d`, `2w`); or an absolute local date `YYYY-MM-DD`. An unrecognized WHEN is a usage error.

`--include CHANNELS` adds per-session detail, given as a comma-separated list of channels. All detail renders under the session's row on a left rail closed by a rule — the same chrome as a rendered turn — and the rail-and-rule bounds the block, separating one session from the next. When more than one channel is selected they share a single block (one rail, one closing rule).

**A block holding exactly one line hangs that line off the closing rule** — `╰─ Tokens: 180 in / 93k out  ·  cache 96%  ·  saved 81%  ·  $8.73  ·  +290/-0` — rather than printing it on the rail with a bare rule beneath. Chrome then never costs more lines than the content it bounds, which is the commonest shape this surface takes: one channel selected, one line to show. A block of two lines or more keeps the rail and closes on a rule of its own, because content sitting on the rule there would give the last line different chrome from its siblings for no difference in what it says. A block every selected channel leaves empty prints no line at all — a bare rule would cost a line for chrome bounding nothing, and would read as a channel that ran and found nothing rather than one with nothing to find; the row above is all that separates it from the next. `all` selects every channel. An unknown channel is a usage error. **`--include` belongs to the listing alone**: passed beside a session id it is a usage error naming the footer, which prints these same facts for one session without being asked (see Output). It was silently ignored there until this version, which left a caller believing it applied — the reason `--from` beside an id errors too. The channels:

- `prompts` — the session's user prompts, listed in order each prefixed with the `❯` glyph, `/clear` omitted (including a `/clear` carrying trailing arguments); every prompt is shown (the view is opt-in).
- `tools` — a breakdown of the session's **top-level** tool calls, grouped by identity rather than by bare tool name, because the signal is *which* commands, skills, and agents ran. Seven category lines, each shown only when non-empty: `Skills` (by skill name), `Agents` (by subagent type — named agents appear by name), `Bash` (by invoked program — the first command token, leading `VAR=` assignments stripped, reduced to its basename), `Edits` (by the base name of each file an `Edit` or `Write` targeted), `Other` (every remaining tool by its own name), `Failed` (below) and `Denied` (below). The two outcome lines come last and in that order: a failure is something to go fix and a refusal is a boundary that held, so the one asking for action is met first. Within a line, entries read `name ×count`, ordered by count descending then name. "Top-level" means the work the main thread invoked — calls inside subagents are not counted, matching the per-turn tool count. **A slash command the caller typed counts as a `Skills` entry**, though the model made no call for it: the transcript renders that fork as a `Skill` call, so a tally omitting it contradicts the page above it, and selecting sessions by the skill they used misses every session that typed one.

**A fork counts as a typed command only where the log ties it to one**: no spawn record names it, its own opening entry names a skill, and the prompt it was forked under is that skill's slash command. The third condition is what keeps the count from doubling — some unclaimed skill-opening sidecars are forked `Skill` calls in logs written before the structured link existed, already counted through the call that made them, and their prompts are ordinary prose. An alias typed under another name is not counted, since nothing in the log relates the two; the cost axis is laxer on purpose, because naming money spent needs no invocation to point at.

  `Failed` names the calls that ran and failed, by tool and what it was pointed at — `Bash/cat ×4, Bash/python3 ×2, TaskOutput ×1` — worst first. Every surface counts failures: the rendered header, the rule under each turn, and this block. None of them said **which** tool until this version, so a session reading `9 failed` reported that something went wrong and nothing about where to look, while the refusals beside it had been named all along. A refused call is not counted here: the log flags it as an error too, and the two are separated on the denial reason rather than on that flag, so the counts on this line add up to the header's `failed` figure and never to its `denied` one.

  `Edits` exists because a summary that says a session edited something and never *what* cannot tell a run that touched a `SKILL.md` from one that touched a source file or a config, though those are different kinds of work. It shows base names, the same compression `Bash` applies in reducing a command to its program; `--format json` carries each call's full path, so the table stays readable without the detail being lost.

  `Denied` names the calls that were refused and by what, reading `kind: tool/identity ×count` — `permission-rule` (a settings deny rule), `automode-blocked` and `automode-unavailable` (the auto-mode classifier), or `user-rejected` (a person said no). Without it a refused call is indistinguishable from one that ran and failed, so choosing what to add to an auto-allow list has no data source but memory. Only these four kinds are reported; a call that failed for any other reason is an ordinary error and appears in no `Denied` entry. Like every other line in this channel it counts top-level calls only — a call a subagent made and had refused is in that subagent's own sidecar, which a listing does not read.
- `files` — every file the session modified, one per line, by any means rather than only through the two tools whose arguments agentry reads. Claude Code records these itself: `file-history-snapshot` entries key `snapshot.trackedFileBackups` by path, and `file-history-delta` entries carry a `trackingPath`. Paths mix repo-relative with absolute in the log, so agentry resolves each against the session's recorded working directory and reports one absolute path per file, first-seen order. This is the session-level counterpart of the `Edits` line, which breaks the same ground down per call: a file changed by a shell command appears here and not there. Not every session carries the entries at all, and a session without them lists no files rather than claiming it changed nothing.
- `model` — one line naming what the session ran on: its model and the reasoning effort beside it, in the rendered header's phrasing (`claude-opus-5 · high effort`), with the same `→` when either changed mid-session and with the effort half absent on a session predating that field. A session whose log names neither shows no line rather than an empty one. This is also what makes the `--model` and `--effort` selectors (below) usable: a filter over a fact the output never displays leaves you guessing at its values.
- `cost` — one line naming what the session amounted to, in the rendered header's exact wording (`Tokens: 494 in / 211k out  ·  cache 97%  ·  saved 40%  ·  $35.07  ·  +342/-8`) and built by the same code, so a figure read off a listing and one read off a rendered session cannot differ. The dollar figure and the line counters are Claude Code's own running totals, read from the log rather than computed, and are absent on a session whose log carries none — every session before Claude Code 2.1.241, and plenty since, which show the token half alone. The counters are also dropped on a session that changed no lines, on the rule the header states. The saved share beside the cache share is agentry's own price rather than a record, and is absent on a session none of whose responses it holds a price for. The token half is always present and is the only place the text table states a session's tokens at all; `--format json` has carried them since before this channel existed, so the channel closes the gap between the two formats rather than adding a fact. Like `model`, this describes the session rather than enumerating its contents, so it renders above the channels that list things.
- `outputs` — what the session produced beyond its own transcript: one line per pull request it opened and one per artifact it published. A pull request shows as its URL, which already names the repository and the number; an artifact shows as its title followed by its `claude.ai` URL, falling back to the URL alone when the log recorded no title. A session that produced neither shows no line.
- `last-reply` — the session's final assistant reply, laid out the way a rendered turn lays one out: the `◆` glyph alone on its line, then the prose through the same markdown renderer at the block's width, with links becoming terminal hyperlinks where color is on. One helper serves both surfaces, so the markdown is treated identically and the two cannot drift in what a reply says. Two things do differ, both of them chrome: the block is narrower than a full-width render, so a long line wraps at a different column, and the glyph sits on the rail instead of above it, because a listing's block gives every channel one rail. Nothing is truncated and no line is dropped, which is why this channel costs far more than any other: a default ten-session listing can grow from a handful of lines to many dozens with it turned on, because a reply's own length sets the block's. A caller who wants the listing to stay scannable selects a different channel. Named for the one reply it shows, because every other channel that can hold more than one thing shows all of them: this is the set's only deliberately partial member, and its name is where that has to show rather than in a caveat read after the surprise. "Final" is the last non-blank text block the main thread wrote, the same corpus `--reply-matches` tests — subagent sidecars are not opened and thinking blocks are excluded — so the filter and this channel cannot disagree about what a reply is. It renders directly below `prompts`, where the conversation ends, and the channels that enumerate what the session did follow it. A session whose log holds no assistant text shows no line. Alone among the channels it has no `--format json` counterpart, for the reason reply text is absent there: `--include` gates no JSON key, so a key would bill every JSON caller, and a truncated field would mislead a machine consumer while a whole one reinstates the payload size that keeps reply text out of the listing.

  Each line is cut so that the half identifying the thing survives, which points the two kinds in opposite directions. A pull request truncates from the left, like the `files` channel and for the same reason: the repository and the number are at the tail, and the scheme and host at the head are what every line repeats. An artifact truncates from the right, keeping the title and letting the URL go, because a `claude.ai` artifact id is an opaque uuid that identifies nothing to a reader — the same trade the `Edits` line makes for paths, and `--format json` carries the URL in full either way.

  Claude Code writes these itself, as a `pr-link` entry when a pull request is opened and a `frame-link` entry when an artifact is published, and it writes them **for the session as a whole**: no subagent sidecar carries one. So this channel reports a pull request opened deep inside a subagent or a skill exactly as it reports one the main thread opened with a `gh` call, which is the axis every tool-call view misses.

  Both kinds are **re-recorded on later turns**, and heavily, so naive counting would overstate them. agentry reports each once, in first-seen order, keyed by its **URL**: the identity that survives everything else about it changing. It has to be the URL rather than the local file, because an artifact republished from a moved file — a scratchpad draft promoted into the repository — keeps its `claude.ai` URL and changes its path, and keying on the path would report one artifact as two. Where repeated entries disagree about a title or a path, the last one wins, matching how every other changing value in a session resolves. A title is optional and sometimes absent.

A listing covers the current directory's project **and every project nested under it**. Matching is on each project's recorded working directory compared component by component, so standing in `/a/b` does not pick up `/a/bc`.

Subtree scope is what makes a listing answer the question a repo actually raises. Claude Code gives every git worktree its own project folder, so a repo's sessions are split across one folder per worktree, and a listing confined to the folder the repo path encodes to would show none of the worktree ones — which is what a bare `agentry list` in a main checkout used to do. Standing in the repo now sweeps the worktrees Claude Code creates under `<repo>/.claude/worktrees/` along with it. What it does **not** reach is a worktree placed outside the repo — for that, name a directory that contains both with `--project`. The cost of the wider default is one pass over the project folders to read each one's recorded `cwd`, which is cheap even for a repo with many worktrees.

Two flags move the listing off the current directory. They are mutually exclusive — given together they are a usage error, because `--all-projects` already covers every project and naming one narrows nothing.

- `--all-projects` — every project under the projects root (see Output for where that is), in one call.
- `--project PATH` — the sessions of PATH and of everything nested under it, rather than the current directory's. It chooses the root, not the depth: the subtree rule is the same one the default follows. Naming a directory that holds many repos lists all of them, which is how one call replaces a loop that runs the binary once per repository.

Every listing scope — the default and both flags — reaches projects whose directory has since been deleted or renamed, because selection reads each project's recorded `cwd` rather than walking the filesystem. That is a real difference and not an edge case: many project folders on a long-lived machine have no surviving directory, so a filesystem walk would find only a fraction of them.

The **root of a subtree is the exception**, and is taken by folder name instead: standing in a directory lists its own project, and `--project PATH` lists PATH's own, whatever those sessions record as their `cwd`. The two rules disagree only for a folder holding a session that records some other path — one relocated into it, or one predating the field — and there the name is the answer that matches what the caller asked for. Widening the default scope must not drop what the narrow lookup returned, which is the same guarantee stated from the other side: no session that a listing showed before is hidden by the subtree rule. Only **nested** projects need a recorded `cwd` to be found, and in practice every project has one.

When a listing spans more than one project, each row gains a **project column** naming where the session ran, placed before the title. **A project is the repository, not the folder Claude Code files it under**: a session whose `cwd` is `<repo>/.claude/worktrees/<name>` is labelled by `<repo>`, so every session of one repo shares one label however many worktrees they were spread across. That is the scope rule of this section applied to the label — a listing already treats a repo's worktrees as the repo — and without it three worktrees of one repository read as `plan`, `docs` and `billing`, three labels naming no project and denying that the sessions belong together. It shows the shortest suffix of path components that is unique among the projects listed — `agentry` when that name is unambiguous, `me/agentry` and `acme/agentry` when it is not — because a bare directory name collides exactly where repositories are grouped under owners, and a full path does not fit beside a session id. The column is capped at a third of the space the project and title columns share, and truncates from the left (`…y-migration`) since the tail is the distinguishing end. A listing confined to one project has no such column, so single-project output is unchanged. Full paths are always available in `--format json`.

Inside one repository the same slot carries a **worktree column** instead, naming which worktree each session ran in, with `—` for one that ran in the repo's own checkout. Collapsing worktrees into the project label is what makes this necessary: within a repo the worktree is the only thing separating one line of work from another, and the sessions of five worktrees otherwise differ by nothing but their titles. The two columns cannot both appear — the project column is drawn only when a listing holds more than one project and this one only when it holds exactly one — so a row never carries two path columns and the title never pays for both. Width and cap are the project column's, and the column is drawn on the same appear-only-when-it-varies rule: a listing whose sessions all sit in the same place, whether that is the repo root or a single worktree, has no worktree column. It truncates from the **right** (`registry-migration…`), opposite the project column, because a worktree name's head is the name someone chose and its tail can be generated — a worktree Claude Code creates from the desktop app carries a 6-character hex suffix (`registry-migration-a1b2c3`), which some worktrees have and left-truncation would keep in place of the name. `--format json` carries the whole path as `cwd`, so nothing this column compresses is lost there.

Either path column, project or worktree, **keeps the characters that tell colliding labels apart**. Truncation is applied first; where two labels then render identically, the ellipsis moves inward on those two, leaving a head and a tail, and the retained end is one character longer than the longest run the colliders share there — the mirror of the distinguishing-prefix rule, `lcp + 1`, which names how many characters separate two strings. Three worktrees named `update-widget`, `update-widget2` and `update-widget3` therefore read `update…t`, `update…2` and `update…3` in an 8-wide column, where before they were three identical cells claiming to be one worktree. VS Code's editor tabs resolve colliding file names the same way, growing a candidate until it stops colliding.

Two properties keep the rule honest. The comparison is over **distinct labels**, so many rows sharing one label are not a collision — the `—` that every session in a repo's own checkout shows is left alone, and so is a worktree that several sessions ran in. And where no split fits the column, because the colliders differ too far from the retained end, **the duplicate stands**: a marker like `…#2` would be an identifier meaning nothing outside that one listing, and the session id already separates the rows. That case buys distinguishability without legibility even when it does fit — two worktrees differing in their first characters render as `widget…3` and `widget…5`, which says the rows differ and not how — so the column's width, not this rule, is what makes a label readable.

Sessions are also told apart by **where they were run**. Every entry records an `entrypoint`, and a listing otherwise mixes all of them with nothing to tell them apart, so a session you remember starting in the desktop app is indistinguishable from one you started in a terminal. agentry names the three values `cli` (the terminal), `app` (the desktop app), and `sdk` (a non-interactive run). A value agentry does not recognize shows as `?` rather than being dropped, since the set grows without notice.

`sdk` is the log's own `sdk-cli`, and the name is the log's rather than a description: **a plain `claude -p` produces it with no SDK involved**, so the condition is "not interactive", not "used the Agent SDK". Anything headless lands here — a shell script, a hook, a CI step, another agent shelling out.

**Non-interactive sessions are excluded from the listing by default.** They are the majority of what a machine accumulates and almost none of what anyone wants to read back — often one-turn runs of a few seconds with a generic title. Listing them by default buries the work a person did under the work a hook did. `--from` overrides this:

- `--from cli` / `--from app` / `--from sdk` — only that kind.
- `--from all` — every session, the pre-default behavior.

The default is exactly `cli` plus `app` plus any unrecognized value, so the four settings cover every combination worth naming. An unknown `--from` value is a usage error with a nearest-match suggestion, like every other enum flag. When the default exclusion leaves a listing empty while hidden sessions exist, agentry says so on stderr and still exits zero — an empty listing that a default silently caused is otherwise indistinguishable from a project with nothing in it.

When a listing spans more than one entrypoint, each row gains a **3-character tag** before the project column, on the same appear-only-when-it-varies rule — a listing that is all terminal sessions is unchanged. The tag is three ASCII letters rather than a glyph because a glyph needs a legend the output does not carry, and because agentry pads columns by rune count, so an ambiguous-width glyph would misalign every row that used it. It is not spelled out in full because at 100 columns `terminal`/`desktop` cut the title to 19 characters, and the title is what a row is scanned by.

A session can carry more than one entrypoint — starting in the desktop app and being resumed from the terminal writes both. Observed shape: one contiguous block of each, never interleaved, and rare — on the one occasion the two kinds tied exactly in entry count, which is why no majority rule is used. **The last value wins**, matching the row's own last-activity time, and the tag takes a `+` suffix (`cli+`) to mark that the session started elsewhere. `--format json` keeps both, so the machine-readable form never loses what the tag compresses.

A second family of flags filters the listing by **what a session did** — the calls it made and the outputs it left behind — answering "which session did X?" without reading each one. Its axes:

- `--used-tool NAME` — sessions where that tool fired, matched against the tool-use name (`Bash`, `WebFetch`, `Skill`, `Agent`, …), case-insensitive and exact. This is the "which mechanism" axis.
- `--used-skill NAME`, `--used-agent TYPE`, `--used-command PATTERN` — the identity axis: what was invoked *through* the three identity-bearing tools — a Skill call's skill, an Agent call's subagent type, a Bash command's text.
- `--used TOKEN` — a catch-all over the identity axis: matches a skill name, an agent type, or a command. It deliberately does **not** match tool names, so the two axes never collide — to filter by tool name use `--used-tool`.
- `--used-file PATH` — sessions that modified a matching file. This is a third axis, "what did the work land on", and it reads **both** records of that: the targets of `Edit` and `Write` calls, and the files Claude Code tracked itself (the `files` channel). `Edit`/`Write` carries the weight, because about half of sessions have no file-history entries at all and a tracked-record-only filter would silently never match those. The tracked record is a backstop for a change no tool argument names — a file a shell command rewrote — but it contributes only rarely, and even then can be recorded against the session's own directory rather than the worktree's. Treat it as insurance, not as the source that answers the question. `--used` does **not** cover this axis — it stays the identity catch-all — so a file is matched only by naming this flag.
- `--opened-pr TEXT` — sessions that opened a matching pull request, matched over its repository, its number, and its URL together, so `--opened-pr widget-migration` selects a repository's worth and `--opened-pr 187` picks one. This is a fourth axis, "what came out of it", and it asks a question the call-based flags cannot: a session that ran `gh pr create` on the main thread is findable with `--used-command`, but one whose pull request was opened by a subagent or a skill is not, and Claude Code records the pull request either way.
- `--published-artifact TEXT` — sessions that published a matching artifact, matched over its title, its `claude.ai` URL, and the local file it was rendered from. Same axis as `--opened-pr`, same reason.
- `--reply-matches PATTERN` — sessions where the assistant's own reply text matched. This is a fifth axis, "what the reply said", and it is the only one reading what the model wrote rather than what it called or produced. It exists for auditing instruction-following across a corpus: a rule about how a reply is written — end every reply with a Learnings block, print paths as `file://` links, name the skill you loaded — leaves its only trace in the reply, so before this flag no listing could count whether such a rule fired.

`PATTERN` is a **regular expression** ([RE2](https://github.com/google/re2/wiki/Syntax)), case-insensitive by default, and this is the one filter in the family that is not a substring match. Prose is why: the questions asked of prose are positional ("did a reply open with praise") and alternation-shaped (`great|excellent|perfect`), and a substring expresses neither. A plain word is still a valid pattern, so the simple case costs nothing; regex metacharacters are live, so a literal `(` or `?` must be escaped. Case-insensitivity is the family's rule rather than a regex convention — override it per pattern with `(?-i)`. An unparseable pattern is a usage error, named as such before any session is read.

The pattern is tested against **each assistant text block separately**, and the session matches when any one block does. Per block rather than over the session's joined text, because `^` and `$` should anchor to a reply: `--reply-matches '(?m)^\*{0,2}Learnings\b'` counts the sessions that emitted a Learnings block, where the substring `Learnings` would also count every session that merely mentioned one. Thinking blocks are excluded — reasoning is not a reply, and a rule about what a reply said must not be satisfied by a thought.

Identity-axis matches (everything but `--used-tool` and `--reply-matches`) are case-insensitive substring, so `--used-skill sonar` also catches `sonar-search` and `--used-command 'git push'` matches that phrase anywhere in a command. Substring cuts both ways: a short token over-matches (`--used-command exa` also hits `exact`), so disambiguate with a more specific pattern (`scripts/exa`) when a token is also a common substring. The same holds for a path: `--used-file list.go` catches every `list.go` in every directory, and `internal/cli/list.go` names one. The population for the `--used*` flags is the same top-level calls `--include tools` counts — calls inside subagents are not considered, with two exceptions stated where they apply: `--used-file` also reads the session's tracked-file record, and `--opened-pr` / `--published-artifact` read the session's `pr-link` and `frame-link` entries. Claude Code writes all three for the session as a whole rather than per call, so those three flags see work a subagent did as readily as work the main thread did. `--reply-matches` is top-level too, and more narrowly so: it reads the main thread's own text blocks and never opens a subagent sidecar, so a phrase a subagent wrote back into the transcript is not matched. **Every one of these flags has a `--not-` form** — `--not-used-tool`, `--not-used-skill`, `--not-used-agent`, `--not-used-command`, `--not-used-file`, `--not-used`, `--not-opened-pr`, `--not-published-artifact`, `--not-reply-matches` — which keeps exactly the sessions its positive twin would drop, matching by the same rule with the same value. The pair exists because a compliance question is usually a conjunction of a presence and an absence: `--used-command 'git commit' --not-used-skill review` is one call for "committed without loading the review skill", which otherwise takes two listings and a set difference on session ids. It is also how an instruction-following audit counts the misses rather than the hits: `--not-reply-matches '(?m)^\*{0,2}Learnings\b'` is the sessions where the block never appeared. All nine are negated rather than the obvious few, because a partial set is a trap — a reader who learns `--not-used-skill` will reasonably try `--not-used-file` and get an unknown-flag error for no reason they can see.

**A negated filter makes an absence claim, and it is only as complete as what agentry reads.** The call-based filters see top-level calls, so `--not-used-skill X` means the main thread never invoked X — a subagent may well have, in a sidecar the listing does not open. Where that distinction matters, read the session rather than trusting the filter. `--not-opened-pr` and `--not-published-artifact` do not carry that caveat, since their entries are session-level; what limits them instead is that Claude Code has to have noticed — a pull request opened by a shell command it did not recognize as one leaves no `pr-link` entry, and no filter can find what was never recorded. `--not-reply-matches` carries the sidecar caveat and one of its own: it is an absence claim about a pattern, so it counts every reply the pattern failed to describe, including one that satisfied the rule in a form the pattern did not anticipate. Widen the pattern before reading its count as a violation count.

Multiple filter flags combine with AND (a session must satisfy all); negations AND too, so a session must fail every one of them. Giving a flag and its negation the same value therefore matches nothing, and agentry reports that as an ordinary empty listing rather than a usage error — unlike `--all-projects` with `--project`, the two are not competing to decide the same thing, they simply describe no session. For OR, run separate listings. Like the `--include tools` breakdown, these read a session's tool calls, so they pair naturally: filter to the sessions that used something, then `--include tools` to see what else those sessions did.

A third family filters by **what the session ran on** — the model, and the reasoning effort beside it. These are the same two facts the rendered header names (see Output), resolved the same way, so the two paths never disagree about what a session ran on.

- `--model NAME` — sessions that ran on a matching model, case-insensitive substring. Model names nest by family and version, and the substring rule is what makes both readings available from one flag: `--model opus` covers `claude-opus-5` and `claude-opus-4-8` together, `--model opus-5` picks one of them.
- `--effort LEVEL` — sessions that ran at that reasoning effort, case-insensitive and **exact**, unlike every other identity-style filter. The levels nest as substrings, so a substring rule would make `--effort high` silently include `xhigh` — a wrong answer rather than a wide one. Claude Code's own `--effort` takes `low`, `medium`, `high`, `xhigh` and `max`; agentry does not validate against that set, because it grows without notice and a level agentry has not heard of should return no sessions rather than a usage error.

Both match against **every** value the session carried, not only the resolved one: a session that started on Sonnet and switched to Opus matches `--model sonnet` as well as `--model opus`, because it really did run both. Both lift the default `--limit` the way a time or `--used*` filter does, and both AND with every other filter. Neither has a `--not-` twin — those exist because a usage question is usually a conjunction of a presence and an absence, whereas "ran on a model other than this one" is another model's listing, not an absence.

Neither gets a column in the text table. The table has one variable column, the title — 29 characters at a 100-column terminal, once the fixed columns and the session id are taken — and a model name runs 13 to 25 characters, so a model column would spend most of the title on it. The entrypoint tag earned its column by fitting in three characters; a model name cannot be shortened that far without dropping the version, which is the half a cost audit reads (`claude-opus-5` and `claude-opus-4-8` differ by one token and are priced differently). `--include model` shows the pair under the row instead, and `--format json` carries it on every session.

A fourth family filters by **how much code the session changed** — the lines it added plus the lines it removed, as Claude Code recorded them (see Output). This is the axis every other selector misses: a session that ran fifty tools and wrote nothing looks identical to one that rewrote a package, because the tool breakdown counts calls and not their effect.

- `--min-lines N` — sessions that changed at least N lines.
- `--max-lines N` — sessions that changed at most N lines. `--max-lines 0` is the useful case: it selects the sessions that touched no code at all, which no other flag can express.

Both bounds are inclusive and both count the two counters together, so a session that added 13 and removed 6 changed 19. Given together they make a range; a floor above its ceiling is a usage error rather than an empty listing, because no session can satisfy it and a caller reading zero rows would take that for an answer about their sessions. A negative bound is a usage error for the same reason: it can only be a mistake, and accepting one would silently return the whole listing for `--min-lines` and none of it for `--max-lines`.

**A session whose log recorded no line counters matches neither bound.** It makes no claim about how much it changed, so it can neither meet a floor nor be shown to respect a ceiling — the rule `--model` already follows for a session naming no model. That is most sessions, since Claude Code has only written the record since 2.1.241 and does not write it for every session even now, so a bounded listing is a listing of the sessions it kept a record for. `--max-lines 0` therefore means "recorded, and changed nothing", never "no record".

Each summary also carries its **token tally**, as `usage` in `--format json` — input, output, the two cache counters, and `cacheCreate1h`, the share of the cache writes bought for an hour rather than five minutes, summed over the main thread and every subagent the session spawned, each API response counted once (see Output). That is the same number the render path reports as `meta.usage`, so a spend read off a listing and one read off a rendered session agree rather than differing by whatever the subagents spent. Pairing it with `model` is what answers "how much did this model cost me across every project" from a single `--all-projects --format json` call, where before it took one render per session. Two limits on that answer: a session that switched model carries one tally and no split between the models, so `models` is what marks the sessions an exact attribution has to set aside; and the tally is tokens rather than dollars, which `agentry cost` is what converts (see Rolling up cost). Reading the subagent sidecars is the listing's one non-trivial cost, since they can amount to a large share of a project tree's bytes, and it is paid on every listing because the field is unconditional — reading them serially made the widest possible listing measurably slower. **Sessions are now read in parallel**, which is what keeps the widest answer affordable as a machine fills up. The text table shows the tally only under `--include cost`, since it is a number to aggregate rather than one to scan a row by.

Beside the tally each summary carries **what caching saved**, as `cacheSaving` in `--format json`: `withCacheUSD`, what those responses cost at the rates they were billed at, and `withoutCacheUSD`, what the same tokens would have cost with nothing cached (see Output for what the pair means and how it is priced). The render path reports the same object as `meta.cacheSaving`, so the two formats cannot disagree about one session. It is two dollar figures rather than the one share the text line prints because a share of one session cannot be added to a share of another, where the two prices sum across any set of sessions and the share is taken afterwards. Both are absent on a session none of whose responses agentry holds a price for.

Beside it each summary carries **what the session cost in dollars**, as `costUSD` — Claude Code's own running total, read from the log's last such record rather than derived from the token tally. It is the field a currency answer comes from, and it is absent on a session whose log carries none, so a caller aggregating it must decide what to do about the gap rather than being handed a zero that looks like a measurement. Unlike `usage` it is main-log-only and costs no extra file reads: Claude Code's total **already counts a subagent's spend** (see Output), so a caller has nothing to add to it and adding a separately derived subagent figure would double count. Beside it, `linesAdded` and `linesRemoved` say how much code the session changed. They come from the same record, so all three keys appear together and a caller can test one to know it has the others; a zero there is a session that changed nothing, which is a different fact from the key being absent.

`--format json` emits the selected sessions as a JSON array instead of the text table — the listing's machine-readable form, for piping into `jq`. It carries the full model per session (`id`, `start`, `end`, `title`, `numTurns`, `prompts`, `tools`, `commands`, `rootUuid` — the shared root id that groups a fork family — `cwd`, the working directory the session ran in, read from the log rather than derived from the lossy folder name, `entrypoint` — the resolved value, joined by `entrypoints` listing every distinct one in first-seen order when a session carries more than one — `files`, every file the session modified as an absolute path, `failures`, one entry per `{tool, identity, count}` group of calls that ran and failed, `denials`, one entry per `{kind, tool, identity, count}` group of refused calls, `model` and `effort` — each joined by a `models` / `efforts` list on the same rule `entrypoints` follows — `usage`, `dailyUsage`, one entry per model per delegation per local calendar day as `{day, model, agent, usage}` — the same responses `usage` totals, split as finely as they can be priced, so a caller can bucket a session's spend by day or by what it was delegated to without re-reading its log, `agent` being absent on the main thread's own tokens — `dailyActivity`, one entry per local calendar day as `{day, turns, activeSeconds}`, whose turns sum to `numTurns` — `prs`, one entry per pull request the session opened as `{repository, number, url}`, and `artifacts`, one entry per artifact it published as `{title, url, path}`), in the same order the table shows (most-recent first); the JSON stays flat (fork grouping shapes only the text table).

**Assistant reply text is the one thing a session holds that this JSON deliberately omits**, and `--reply-matches` is what stands in for it. Reply text is by far the largest field a summary could carry — often several times the size of everything else a listing shows for that session. Carrying it would therefore multiply the listing's payload — and unconditionally, since `--include` shapes only the text view and gates no JSON key, so a caller who wanted `usage` would pay for reply text too. A filter answers the question a corpus audit actually asks (did a reply say X, in how many sessions) at zero payload cost, so agentry tests reply text and never ships it. To read the prose rather than test it, render the session: `agentry <id>` and `agentry <id> --format json` both carry every text event in full.

Being the model rather than a view of it, it ignores `--include` (a text-shaping flag) and color; the selectors (`--since`/`--until`/`--limit`/`--used*`) still choose which sessions appear, and an empty selection emits `[]`. **The default cap never applies to it**, so a bare `list --format json` carries every session rather than ten. The array has no chrome a truncation note could live in and a caller reading it cannot tell a capped array from a complete one, so the cap would be a wrong answer no consumer could detect; removing it is cheaper than reporting it. An explicit `--limit` still caps the array, a caller who names a number having asked for one; `--limit all` is how a caller says otherwise. **stdout is always a well-formed array**, including on the two failures that produce no sessions at all — a directory with no Claude project, and a project holding no sessions. Those still write their message to stderr and still exit non-zero; they simply also write `[]` to stdout, so a caller can pipe into `jq` unconditionally and read the exit code to tell "nothing matched" from "nothing to look in". Without that, one output contract has two shapes and every script that sweeps directories carries a guard to substitute the missing array. This applies to `list --format json` only: the render path's JSON is a single session object, and a missing session has no empty form to emit. `--format` also accepts `text` (the default); an unknown value is a usage error. The default text table renders as below.

**The cap applies to a bare listing only.** Pass any flag that selects which sessions appear — a scope, a time frame, `--model`/`--effort`, a line-count bound, or anything from the what-a-session-did family — and the cap lifts, so `agentry list --since today` shows every session from today rather than ten of them. The flags that shape rows rather than choose them leave it in force: `--include` asks for more about each session, not for more sessions, and lifting the cap for it would answer a request for detail with six hundred rows of it. The rule is the bare invocation rather than the selecting families alone, because a scope widening like `--all-projects --from all` reads as a request for everything and was capped at ten under the narrower rule — a capped listing wearing the shape of a complete one. **A cap that held sessions back says so**, on the error stream and below the table, separated from the last row by a blank line: `agentry: 672 more session(s) hidden by --limit — pass --limit all to list them`. Below rather than above, because a notice printed before the rows is a banner over content the caller has not read yet, where the same line under the last row reads as the listing's closing word — and a caller scrolled to the bottom of a long listing is exactly the one asking whether that was all of them. The count is the one thing a caller cannot work out from the output, and without it ten rows drawn from 682 reads as a complete listing — the reason the cost roll-up names its remainder rather than simply stopping at five rows. It goes to the error stream, where the headless-session note already goes, rather than into the table: the text listing is line-oriented, so a note among the rows would break a caller reading a field off every line, and the JSON array carries no default cap for a note to describe. It fires for an explicit `--limit` too, since the number of sessions left over is information the caller has no other way to get. An explicit `--limit` applies **after** the filters, so `--limit 50 --reply-matches X` is "the 50 most recent sessions that matched", not "how many of the 50 most recent matched" — a distinction that matters exactly when the count is the answer. For a rate over a window, bound the window by time (`--since`) and leave the cap lifted, or take the two listings and intersect their ids. A window that matches no session prints nothing and exits zero; a project with no sessions at all is an error, the same as in render mode (under `--format json` that error still prints `[]` to stdout — see above). The scopes follow the same split between "nothing matched" and "nothing to look in": `--project PATH` naming a path no project sits at or under is the same error as standing in a directory with no project at or under it, and `--all-projects` finding no session in any project is the error too, whereas a filter that excludes every session found is still an ordinary empty result at exit zero. `list` takes no session-id argument; the rendering flags (`--level`, `--turn`, the channel toggles) do not exist on it — they live on the render path, not as flags `list` silently ignores. **The bare command is where both sets meet, and a render flag there with no session id is a usage error naming every offending flag** — `--level and --tools belong to the render path: pass a session id, or use `agentry view` with them`. The bare command carries both sets because it lists or renders depending on its argument, so unlike `list` these flags are registered on it and did nothing at all when no id followed: a caller who asked for full detail got a listing and no sign their flag had been dropped. Every offending flag is named rather than the first, so three mistakes are fixed in one run. The reverse holds too: `--include` beside a session id is a usage error rather than a flag the render path drops.

Color follows the same rule as rendered output: styled on a terminal, plain when piped or with `NO_COLOR` / `--no-color`.

The **session id is printed whole**, with the part that tells the rows apart drawn brighter than the rest of it. The distinguishing prefix is still computed — the shortest that separates the visible rows, floored at 8 characters, which is `git`'s rule for abbreviated object names — but it now decides what is emphasized rather than what is printed. The floor is what keeps a three-row listing from emphasizing 1 character, since in practice a much shorter prefix than 8 characters would already tell sessions apart; the uniqueness check grows the prefix when the rows demand it.

**Printing the whole id is what makes the row's id usable outside agentry.** A prefix is enough for `agentry <id>`, which resolves it, and is not enough for `claude --resume`, which in print mode answers `Provided value "sess1234" is not a UUID` and refuses. A listing that printed the prefix alone therefore answered agentry's own question and left the commoner one — resume this session — needing a second command to expand what was already on screen.

**The whole id costs the title column 28 characters**, and the emphasis is what pays for them rather than truncation. At a 100-column terminal the title falls from 57 characters to 29, so a narrow terminal is where this trade is felt — fewer titles now fit whole than did before. The prefix is what a reader scans a column of rows by and the rest is what they copy, and weight is what separates the two jobs without dropping either. The title keeps its 10-character floor, so a very narrow terminal overruns rather than hiding the id.

Under `NO_COLOR`, on a monochrome terminal, and through a pipe the whole id still prints and only the emphasis is lost — the value a caller pipes out is the one they need, and `--format json` has always carried it.

The render path accepts what the listing prints: **any unambiguous prefix** resolves, a full id resolves as it always did, and a prefix matching more than one session is a usage error naming how many it matched rather than a silent pick. Resolution is scoped like every other lookup — the current directory's project first and alone, then the subtree — so a full id still costs one `stat` and pays nothing for the wider reach. A prefix printed by one listing can be ambiguous in a wider scope, and that is the error's job to say; the fix is to pass more characters, which `--format json` always has.

## Finding a passage

`agentry search` says **where a passage sits**, in one session or across many. Before it the only way to reach a passage was to render a session to a file and grep that — which costs a whole render and hands back line numbers belonging to one flag combination, so they break under another.

Three forms, because a caller arrives with one of three questions:

```
agentry search "a phrase"                    where in this session — the commonest, so the bare form
agentry search "a phrase" <session-id>       where in that session
agentry search turn "a phrase" --since 7d    which turns, across the sessions the filters select
agentry search session "a phrase" --since 7d which sessions, and how many turns matched in each
```

**The nouns are subcommands rather than a flag, because the unit changes the row type.** A turn row and a session row carry different fields and lead to different next commands, so they are two questions rather than one question with a switch — the same reading `agentry ask` takes of the same choice. The filters are the listing's own (`--since`, `--until`, `--from`, `--project`, `--all-projects`, and every `--used-*` / output filter), registered on the nouns from one table so a caller learns them once and the two verbs cannot drift apart.

**A first positional of `turn` or `session` is the noun**, which is the rule agentry already applies one level up, where a first token naming a verb is that verb rather than a session id. So `agentry search turn` is the noun with its pattern missing, and says so, rather than a search for the word *turn*. A caller who wants that word searches `agentry search -- turn`, the end-of-options form, which is the one place a positional is guaranteed to be read as itself. Guessing between the two readings was the alternative and it is worse: both are valid invocations, so a wrong guess returns a plausible answer to a question nobody asked.

**The plural is the same noun.** `agentry search sessions` and `agentry search turns` are how the question is spoken, and a caller typing one means the unit rather than a pattern that happens to spell it. Read as a pattern instead, the plural takes the word after it as a session id, so the run fails over a session nobody named and the diagnostic points at the wrong half of the command line. Four words therefore reach `--` rather than two, which is the noun rule's existing cost rather than a new one.

**A cross-session run is not capped.** The listing defaults to ten rows; these do not, because a cap on which sessions are searched hides matches the pattern asked for and no consumer can tell a capped run from a complete one. `--limit` still narrows when a caller asks.

**The bare form searches the session `view` would render.** `agentry search "unplaced tokens"` is the question a caller has while reading a session, so it resolves the same way `view` with no id does: the most recent session that was not a non-interactive run. Naming an id searches that session instead, and `--from` chooses which kind the default resolution walks back to, both exactly as they behave on the render path. `--from` beside an id is a usage error there and is one here, for the same reason: the id has already chosen the session, so the flag could only contradict it.

**The search covers the whole parsed model, not what a render would show.** A turn's prompt, assistant prose, thinking, and each tool call's argument summary, delegated instruction and result body, descending into a delegated stream where the call that spawned it sits. It ignores `--level` and the channel toggles, which is why the verb does not carry them: a search bounded by verbosity would report a passage absent when the level merely hid it, and a reader who cannot find text they know is in the log has been told the log does not hold it. That is the rule `--format json` already follows.

The pattern is the caller's own regular expression — the same compilation the listing's `--reply-matches` uses, through the same function, so one pattern typed at either flag means one thing. A malformed expression is a usage error naming the pattern.

**Case follows the pattern's own text.** A pattern whose letters are all lower case matches without regard to case; a pattern carrying an upper-case letter matches case-sensitively. Typing `learnings` finds every casing of the word, and typing `Learnings` asks for that one. This is what every tool that ignores case by default does — the file finder, the code searcher, the fuzzy finder, the pager and the journal reader each read the pattern's own casing rather than forcing a mode on it — and it is the reading a caller can predict from what they typed. Forcing insensitivity on every pattern was the older behavior and had no precedent: it left a caller who meant the capital with no way to say so short of an inline flag they had to be told about.

Two rules decide it, both needed: the pattern must contain at least one literal character, and none of its literals may be upper case. A pattern with no literals at all — `[[:upper:]]` is the case that matters — is matched as written, since folding case there would make it match the very characters it was written to exclude. Inline flags still override in both directions, `(?i)` asking for insensitive on a pattern that carries a capital and `(?-i)` asking for sensitive on one that does not, and the verb's help says so rather than leaving it to this page.

**The help names the engine, because two things a caller reaches for are not in it.** Patterns compile with Go's `regexp`, whose syntax is RE2: look-around and backreferences do not exist there and arrive as a parse error, and no flag agentry could add would change that. A boundary a caller can only discover by tripping over it reads as a defect in the search; named in the help, it is a property of the engine, which is what the tools that name theirs are doing.

**`-F` / `--fixed-strings` searches for the pattern as text rather than as an expression.** Without it a caller looking for `compilePattern(` or `a[1]` gets a parse error from a pattern they did not know they were writing, and hand-escaping punctuation is the errand every searcher spells `-F` to spare them. A literal search is still case-insensitive, the flag choosing how the pattern is read and not how it is matched. It is valid on this verb and on the listing, where it governs `--reply-matches`; on a listing that passed no pattern filter it is a usage error rather than a silent no-op, which is the rule every flag whose scope does not cover the invocation follows.

**A pattern containing a newline is a usage error here, and not on the listing.** A hit is a line, so such a pattern can never match and an empty result would read as the passage being absent from the session. The error says which line to search for instead, there being no mode here that would make the pattern work. The listing matches whole reply blocks, which do hold newlines, so the same pattern means something there and is accepted.

**A matching turn is one block: the turn, how many of its lines matched, then a few of those lines.** The noun of the verb is the turn, and the turn is what a reader goes on to render, so it is named once at the head of its own block rather than restated beside every line under it. One turn can match on hundreds of lines and commonly matches on the same text repeatedly — a pattern that occurs in a path is named again by every command that touched that path, and a pattern in a document is named again by every tool that read it — so a reader handed those lines one after another is reading the turn instead of choosing it. The block's head carries the turn number and the count of its matching lines, because the count is what says whether the turn is about the pattern or mentions it.

**A line inside the block is two rows: a locator, then the matching text beneath it.** The locator says where inside the turn the line sits; the text is indented two columns under it and wraps with a hanging indent. One row would not fit: measured over 206 real hits, the locator runs to 58 columns at its widest and 72% of findings exceed 80 columns when locator and text share a line, so they wrapped mid-token with no indent to mark the continuation. Two rows cost 20% more height rather than double, because the text was already wrapping — the change re-allocates the wrap instead of adding to it. No blank line between findings, and none between a session heading and the findings under it: the locator sits at column zero and its text at column two, and the indent is the boundary a blank line would only restate at another 27%. A blank line separates one session's block from the next, which is the only boundary the indent does not already draw.

The locator's fields are separated by ` · `. **It leads with the call's number in the turn**, which is the field that tells two calls of one tool apart — without it a turn that ran `grep` four times addressed all four the same way, and a reader sent to the second had nothing to pick it out by. The number names the innermost call the locator reaches, which for a hit in a delegated stream's own prose is the call that spawned that stream, there being no nearer call to name; a hit in the turn's prompt or in the main thread's prose sits in no call and carries no number. It is the number the rendered turn prints beside that call, from the same value. Then the locator names the calls delegated through to reach the line, joined by ` › `, then which piece of the record matched — `prompt` for the turn's own, `text`, `thinking`, `args`, `instruction` for the brief an `Agent` call delegated, or `result` — and then the line's number inside that body, written the way a compiler writes `file:line`. The number is there because a hit deep in a long body is a different errand from one at its head: it says how far into the body to look, and on a body long enough to scroll that is the difference between reading the passage and hunting for it. A turn rendered by `--turn` prints every body whole, argument text included, so the line the number names is a line that render holds. A call is named by the same label a rendered activation line gives it (`Agent[Explore@haiku]`), so one call does not read two ways depending on whether the hit sat inside it or beneath it. The turn is the main thread's, even for a hit inside a subagent: the turn is what a reader renders to go read the passage, where the subagent's own numbering names nothing they can navigate to. `agentry view --turn <n>` renders exactly that turn (see Output), which is the pair this verb exists half of — a hit that named a place nothing could then render would have sent the reader back to the whole session.

One hit per matching line rather than per match, because two matches on one line are one place to go read, and counting them twice would make a hit count read as a location count.

**Results spanning more than one session are grouped under a session heading, and that heading is what `search session` prints on its own.** The heading carries the listing's own facts: the session's **last activity** — its most recent turn's end, the same time a listing row shows — then how many of its turns matched, the project or, inside one project, the worktree, the id in full, and the title. `search turn` prints the heading with its findings hanging off a rail beneath it, the bounded-block rule the Output section states; `search session` prints the headings alone, with nothing to bound. One row type for two nouns rather than two invented ones. A run confined to one session prints no heading, each turn's row sitting at column zero with no rail, because the caller already knows which session they searched and a rail bounds a block under a header rather than a whole output.

**The rows print oldest-to-newest, and the column they print is the one they are ordered by.** The listing's order and the listing's time, for the listing's reason — the terminal leaves the reader at the bottom, so the most recent match wants to be there. Printing one time and sorting by another was the older behavior and read as unsorted: a session's start and its last activity are different moments, so a column of start times ordered by activity reverses direction on row after row, and a reader cannot tell that from rows in no order at all.

**A search row is the listing's row, in the listing's colors.** The two carry the same facts in the same columns with the same gaps, so the time, the count, the label, the id and the title are each drawn in the role the listing draws them in — the id included, whose significant prefix is emphasized here by the same rule and the same code that emphasizes it there. A reader moving between the two surfaces learns one row.

**Every field is a fixed-width column except the title, which comes last and is never cut.** The match count is what a caller chooses between sessions on, so it has to read down a column rather than sit at the end of a line whose length varies with the title beside it; keeping the title whole is what puts it last, since any column after it would be ragged instead. The count is written `matched/total` in the turns column's own form, because three of four turns matching is a different prospect from three of two hundred. A title carrying line breaks is joined into one line rather than ended at the first, so the row wraps and the reader keeps the rest of it.

**A finding's text is one row, cut to the terminal's width around the match.** A matching line can be a whole captured result — a search across one project turns up single lines of twenty-five thousand characters, which wrap to two hundred and fifty screen rows and bury every other finding in the run. So the row is cut to what the terminal holds, and the window is placed so the match sits in the middle of it, because a window cut from the head of a long line need not contain the match at all and would print characters the pattern never touched. Whichever end was cut ends in `…`. The reader loses the rest of that line from this output and the locator names where to read it: the turn number and the body's own line, which `agentry view --turn <n>` prints whole.

**A turn shows at most three of its matching lines and names how many more it holds.** Three because the sample is there to say why the turn matched rather than to be read in place of it: the first line establishes that, the next two show whether the pattern runs through the turn's own words or only through the machine output it quoted, and a fourth answers nothing the third did not. The head's count and the `…  (N more lines)` beneath the sample are what keep this a cap rather than a deletion — a reader sees that the turn holds more and how much more — and `agentry view --turn <n>` prints that turn whole, which is the verb this one exists half of. Two lines carrying identical text are one line to go read, so the sample passes over a repeat of text it has already shown and the count still counts it.

**The number of turns is not capped, and neither is the number of sessions.** A cap there would hide a match the pattern asked for, with no way for a caller to tell a capped run from a complete one. The two caps are different trades: dropping a turn reports nothing about it, where sampling a turn's lines still reports that the turn matched, how heavily, and where to read the rest.

**A run that matched nothing prints nothing and exits zero.** That is the rule a listing whose filters excluded every session already follows, and it differs from `grep`, whose exit status reports whether it matched — a caller testing for hits here tests whether the output was empty. A session that does not exist is still an error with its own non-zero code, the way it is on the render path: nothing matched and nothing to look in are different answers.

`--format json` emits the hits as one array, uncapped and ungrouped — every matching line of every turn, for a consumer that is counting rather than reading — always well-formed and `[]` where nothing matched, each hit carrying `turn`, `call`, `delegation`, `part`, `tool`, `identity`, `model`, `line` and `text` — the same facts the text lines carry, as fields rather than one string, so a consumer filtering by subagent type or by part does not parse a label back out. `search session` emits an array of session matches instead, each carrying the session's own fields and its `turns` count.

**`--format jsonl` is the form that pipes**, one record per line under the standard envelope: a `hit` for the turn forms and a `sessionMatch` for the session noun. The envelope's `sessionId` is per record, which is what makes a cross-session stream addressable — a consumer reads the session from the envelope and the turn from the payload, and the pair is the address `agentry view <id> --turn <n>` takes. A run that matched nothing writes nothing, there being no wrapper to emit. There is deliberately **no bare-id format**: a turn has no id, only a number meaningless without its session, so a list of numbers from a cross-session run would name nothing.

**`--reply-matches` stays, and answers a different question.** It filters a listing so the caller gets listing rows with every other column beside them; `search session` prints match counts for a pattern read across a session's whole content rather than its replies alone. The two share one pattern compiler, so a pattern typed at either means one thing.

## Rolling up cost

`agentry cost` prices the tokens itself and adds the dollars up over a window: what today cost, what this month cost, what one model cost, what each session cost. It answers what the per-session dollar figure cannot. Claude Code's own record covers only a minority of sessions — it has only written one since 2.1.241 — and it is a single number per session, so it can be neither extended to the sessions it has no record for, nor split across the days a session spanned.

**The figure `cost` reports is computed from the transcript and is an estimate, not a bill.** Every assistant entry names the model that answered and carries the tokens that response spent, so agentry prices each response at the same rates and by the same formula Claude Code itself uses, and attributes it to the local calendar day of the entry's timestamp. Where a session also carries Claude Code's own record, the two agree closely, both in aggregate and per session. Every `cost` output says the figure is an estimate, so no reader has to remember it.

**The two figures disagree per session in both directions, and neither is the other's error.** Computing runs **low** where Claude Code makes a request without writing an entry for it — its own background work, which the transcript never holds. It runs **high** where Claude Code's record covers only part of the session — a ledger that stops updating partway through and never catches back up to the rest of the transcript prices far above what little the record shows. So a per-session gap either way is a fact about which requests each side can see, not a disagreement about arithmetic.

The rates are **one table stamped with the date it was verified**, not a table keyed to a date. Across the models in local use, published rates have not changed over the period they have been tracked, so date-keyed rates would add a second thing to get wrong for no fact they would recover, and a stale flat table is easier to notice than a wrong dated one. The table is read out of Claude Code's own baked model catalog — the same tier names it uses (`tier_5_25`, `haiku_45`, …), so re-verifying a rate is a grep of the binary rather than a reading of eight rate rows — and checked against Anthropic's published prices. `--format json` carries the verification date, so a caller can tell how old the prices it was given are.

**Cache writes are priced at two rates and the log's flat counter hides which.** A five-minute cache write costs 1.25× the input rate, a one-hour write costs 2×, and `cache_creation_input_tokens` is their sum; only a nested field splits them. A significant share of cache-creation tokens in practice are one-hour writes rather than five-minute ones, so pricing that flat counter at the five-minute rate would meaningfully undercount cache writes. agentry reads the split and falls back to the whole counter at the five-minute rate for a log that carries none, which is the rate it can still prove.

Three charges are **left out**, and each one's absence is a documented gap rather than a rounding: a web search, billed per search rather than per token; the premium on inference pinned to one geography; and any rate a managed organization negotiated, which Claude Code records as a cost basis other than list price. None of the three appears in any session observed so far, so all three would be implemented against no example to check them by. A session that used web search is priced slightly low; one on negotiated rates is priced at list.

A model agentry holds no price for is **named rather than priced at zero**. Its tokens count in the token totals, its dollars count in nothing, and the report names the model and how many sessions used it. Models appear without notice, and a zero would read as a session that cost nothing rather than one nothing is known about.

**`agentry cost` with no flags answers three questions at once**, because the question a person asks is "what am I spending" and not "what did this directory spend all time": the session they were just in, this directory's whole history, and the machine's last thirty days. A flag combination is not an interface for the commonest question, and requiring `--all-projects --from all --since 30d` to reach the machine's figure made the widest answer the hardest to type.

```
This session  Cost calculation per session           80k        $1.42
This folder   6 sessions, all time                   3.2M      $18.90
This machine  120 sessions since Aug 12              900M     $210.55
              ▁▂▃▂▂▂▂▃▁▂▁▃▂▂▃▂▃▃▃▁▃▃▂▁▄▃▄▁▁▁  per day, peak $34.60

computed from the transcript at Sep 11 list prices — an estimate, not a bill
Claude Code recorded $205.10 for the 25 sessions it kept a record for
```

**The summary answers more than the three scopes, because the sweep that finds them has already read everything else.** Pricing the machine's window means parsing every session on the machine; the three figures are a fraction of what that parse holds, and a caller who paid for the read gets the rest of it. Four sections follow the scopes, each answering one question the three rows raise and cannot settle:

- **Day by day** — a calendar of the machine row's days, since the summary has no table for a picture to head and can therefore carry the shape that says the most;
- **Where it went** — the priciest project directories over that window;
- **What ran it** — the priciest delegations;
- **On which model** — the models those dollars ran on;
- a closing line placing the window's last day against its median and top-decile day, so "is today normal" is answered rather than left to arithmetic.

Each breakdown counts the machine's window, the widest of the three scopes, since the question the sections answer is where the money goes rather than where this directory's money goes. Each shows its five largest rows and then **names the remainder as one line** — how many rows were left and what they came to — so the visible rows plus that line account for the total. A capped list that did not name its remainder would be the failure `--limit` is refused for on the roll-up: a figure a reader cannot reconstruct.

`--level minimal` prints the three scopes and the notes alone, which is what every version before this one printed. The flag is the render path's, and **its default differs by verb because the commonest question does**: rendering a session opens on the transcript and adds detail on request, while asking what you are spending is asking for the picture rather than for three figures and a second command. Only `minimal` and `standard` are offered here — the other two name no further detail this verb has, and a value that changed nothing would read as a setting that failed.

`--chart` chooses the picture in the **Day by day** section as it does above a roll-up's rows, with one difference: the summary's own default is the **calendar**, not the sparkline the day axis picks for a table. A picture above a table heads rows that already carry the detail, where the summary's picture is the only place its days appear at all. `--chart spark` asks for the compact line under the machine row instead, `--chart line` for the braille plot, and `--chart none` for no picture.

**A sparkline under the machine row shows the shape of its window**, one cell per day from the day the row names to the last day that spent, with the peak named beside it so the marks have a scale. The three rows answer what you are spending; the sparkline answers whether it is climbing, which is the nearest question and the one a column of three figures cannot reach. The sweep that builds the machine row already prices every day, so the series costs no extra reading.

**A day that ran no session at all is a blank rather than the lowest mark.** Any day that spent draws a mark, so a day that cost real money is never rendered as a day that cost nothing. A sparkline has only those two states — its span is exactly the days it draws, so there is no third state for "outside the window" the way a calendar grid has.

The sparkline is dropped, not squeezed, when the terminal is too narrow to hold it beside the row it belongs to, and a window holding fewer than two days does not draw one: a single mark has no shape. **A share bar is deliberately not offered on these three rows.** The folder row reads all time while the machine row reads thirty days, so their lengths would compare spans nobody chose to compare; and under a named window, where all three share a span, the rows nest rather than divide — the machine contains the folder, which contains the session — so three bars would read as parts of a total the rows do not sum to.

Every session on the machine is read **once, in parallel**, and the three rows are taken from that one sweep — the scopes nest, so re-reading the narrow ones would double the only real cost of the answer, and reading them one at a time instead of in parallel costs measurably more.

Each row **names its own window**, so the three reading differently is a stated fact rather than a trap. The machine row prints the first day it counts rather than the words "last thirty days": a day is the finest bucket a response is attributed to, so a thirty-day bound counts thirty-one calendar days, and naming the date keeps that out of the reader's head.

**This session** is the most recent session in this directory's scope that was not a headless run — the same resolution `agentry view` makes with no id, and for the same reason: on a machine using hooks the newest log is usually a two-second hook run, so a panel that took the newest log outright would price a hook and label it your work. It is the one panel that skips them. **This folder** and **this machine** count every session of every kind, headless included, because those two are meant to be the bill and a hook costs real money.

A directory with no Claude project has no session and no folder row: the machine row is printed alone, and a note on stderr says the two are missing rather than showing them as zero. Nothing about the machine row depends on where it was run from.

**A row a window or a filter leaves holding no session is dropped the same way.** A row reading $0.00 would say the session was free, where the truth is that it falls outside the span asked for. The machine row is the exception and always prints, since it is what the other two are read against — `0 sessions since Aug 13` is an answer, where a $0.00 session is a wrong one.

**A flag that changes the shape or the scope turns the summary back into the roll-up; a flag that filters narrows it in place.** `--by` asks for a different shape, and `--all-projects` and `--project` name a scope, which the summary's rows already are — each of those three switches the output to the single-scope table below. `--since`, `--until` and `--from` filter the same question the summary answers, so they move its rows instead: `agentry cost --since 7d` is still this session, this folder and this machine, each counting a week. `--no-color` and `--format` change neither, since they only say how the answer is written.

Under a named window every row is bounded by it, and the machine row's own thirty-day default is **replaced rather than narrowed further** — a caller who named a window asked for that window everywhere, and intersecting the two would report a span nobody chose. The folder row, which otherwise reads "all time", names the window like the machine row does. A named `--from` likewise applies to all three, and the session row then resolves to the newest session of the kind asked for rather than the newest non-headless one.

`--by` chooses the bucket, and the rows always sum to the total:

- `--by total` (the default) — one line for the whole selection.
- `--by day` — one row per local calendar day.
- `--by week` — one row per week, labelled by its Monday.
- `--by month` — one row per calendar month.
- `--by model` — one row per model, which is what answers "what has Opus cost me".
- `--by agent` — one row per thing the tokens were delegated to, which is what answers "what is that skill costing me".
- `--by project` — one row per directory the sessions ran in, which is what answers "which repo is costing me".
- `--by session` — one row per session, with its title, which is what answers "which session cost that much".

`--by agent` names a subagent by its type and a forked skill by its invoked name with the leading slash kept, so a table mixing both says which is which. The session's own tokens are a row called **`(main thread)`** rather than an omission, so the rows sum to the total and each one's share reads off the table; the main thread is the large majority of every session, which a delegated-only table would hide. **A delegation that delegates again is charged to the call the session itself made.** A subagent or skill that spawns its own subagents writes their logs beside the session's, and each link is followed until the chain reaches the call the session chose — so a skill's row is what invoking it actually cost, including everything it ran underneath. Charging the nested work to its own name would name a row nobody invoked and nobody can decide to stop running.

A log that **no spawn record names** falls back to the skill its own opening entry declares. A slash command the caller typed forks exactly as a `Skill` call does, but nothing in the session is a tool call, so every map keyed on one misses it — and the marker line Claude Code writes into the fork naming the skill directory it loaded is the only record of what ran. Only the **opening** entry counts: a subagent can load a skill partway through, and its own name is an agent type rather than that skill.

A log that names nothing either way is **`(unattributed)`** rather than dropped, since its tokens were spent whatever the record forgot. Reading the typed forks' own names shrank that row without emptying it, since not every fork can be traced to a name.

**`--by project` groups by the directory the session ran in**, read from the log rather than from the project folder's name, which is lossy. The path is **cut at its first hidden segment**, which is what folds a repository's worktrees into the repository: a tool that checks a branch out beside the repo puts it under a dot-directory, `<repo>/.claude-worktrees/<name>`, so cutting there names the repo. A sibling repository under a shared parent is untouched, since no segment between the two is hidden.

Cutting by the rows themselves instead — folding every directory into the outermost row that contains it — was tried and is wrong: one session run from a parent folder then swallows every repository beneath it into a single row that names none of them properly. A path whose only hidden segment is its last named part keeps it, so `~/.bob` and `~/.config` stay apart rather than both collapsing onto the home directory.

Nothing is read from the filesystem, so a directory deleted or moved since the sessions ran groups the way it did then. The home directory prints as `~`, the listing's abbreviation. The column is bounded at forty characters and **cut from the left**, since paths in one column share their leading directories and differ at the end — an unbounded path can run long enough to push every figure off screen.

Three further columns say what the dollars bought: **`Turns`**, **`Active`**, and **`$/turn`**. A turn is counted in the bucket its prompt started in. Active time runs from that prompt to the last thing the assistant said in the turn, counting **any silence longer than five minutes as five minutes**.

Both halves of that rule are load-bearing. Measuring to the turn's last entry of any kind reads a resumed session's bookkeeping entries as work, which can inflate a turn to many hours long for no real activity. Leaving the silences uncapped is worse: the log cannot tell a ten-minute test run from a person who walked away mid-turn — both are one gap between two timestamps — and uncapped, a single such gap can dwarf a whole month's worth of real activity. The cap errs toward understating, which is the safe direction for a figure dollars are divided by.

**The three columns are absent on `--by model` and `--by agent`.** A turn can run on two models and delegate to two agents, so it belongs to no single row there, and a blank column is better than a number that divides wrongly. They are also absent from the no-flag summary, whose three rows answer what you are spending rather than what it bought.

Beneath the total, two more lines appear whenever turns were counted: what a turn cost on average and what an active hour cost, then the **spread** — the median cost per turn across the sessions in the window and the level the top tenth sits above. Both are needed because one average hides the shape: a mean can run well above the median, so a few very large turns carry the bill. The spread is printed only once three sessions qualify, below which a median restates one session's own figure.

**Wall-clock time is deliberately not offered.** A session sits open across days, so its span measures how long a terminal tab stayed open — summed across a month's sessions it can vastly exceed the month's own hours. Active time is the only elapsed figure the roll-up divides by.

**Cost per line changed is deliberately not offered either.** Line counts come from Claude Code's own record, which exists for only a minority of sessions, most of which changed no lines at all — and that record can cover a shorter span than the session while the computed dollars always cover the whole transcript. A column blank for most rows, whose numerator and denominator describe different periods, would mislead more than it reports.

A day begins at **local midnight**, and a session's spend splits across days by each response's own timestamp rather than landing wholly on the day the session ended. That is the whole reason a computed figure is bucketable at all: Claude Code's per-session record has no per-day form, so a session running past midnight could only ever be attributed to one day or the other, and sessions running past midnight are common enough that this matters.

Time buckets print **oldest first**, the listing's convention, so the most recent sits nearest the prompt. `--by model` and `--by session` print **most expensive first**, because that is the order the question is asked in.

**There is no `--limit`.** Every listing shows a total, and a cap would print a total that the visible rows do not account for — which is worse than a long listing, since the number a reader checks is the one they cannot reconstruct.

**A roll-up's first note says what it priced** — `priced this folder since Aug 13`, or the named path, or `every project`. Without it the figure beneath the rows reads `Total` and names no scope at all, so the same number means one directory to one reader and a whole machine to another. The summary needs no such line, because its rows say which scope each one is.

`--since` and `--until` take the listing's `WHEN` values (see Listing sessions), so `agentry cost --since 30d` is the last thirty days and `--since today` is today. They are compared against **each day of spend**, not against the session's last activity the way the listing compares them: a session that ran across the window's edge contributes only the days inside it. `--limit`, `--include` and the what-a-session-did filters do not exist on `cost`.

Scope is the listing's: the current directory's project and everything nested under it by default, `--project PATH` for another subtree, `--all-projects` for every project (see Listing sessions for all three, and for why the two flags are mutually exclusive). `--from` selects where the sessions ran, with the same default that hides non-interactive runs — a machine using hooks accumulates hundreds of them, and a cost total that silently included them would answer a different question than the listing beside it.

**Whenever that default leaves sessions unpriced, `cost` says how many on stderr** and names `--from all`, which is more than the listing owes. A listing that dropped rows still shows the rows it kept, so the reader can see it is looking at a subset; a total is one number, and one that quietly omitted sessions is simply lower than the bill. The note goes to stderr, so a figure piped into another program is still the figure alone.

**Every row carries a bar showing its share of the window's dollars.** It is the last column, so it takes whatever width the figures leave and is the first thing dropped when the terminal is too narrow — no figure ever wraps to make room for it. A row that spent anything at all draws at least one mark, so a row too small to see is never rendered as a row that spent nothing, and the total line carries no bar, since a bar covering the whole width says only that the total is the total.

The bar is a second reading of the Cost column and never the only one. Under `NO_COLOR`, on a monochrome terminal, and through a pipe the figure it repeats is still on the row, and the bar itself is drawn from block characters rather than from color, so it survives all three. Where color is available it shades the bar by rank, which adds nothing a reader needs and takes nothing away from one who cannot see it.

The text form is a table with a total line beneath it:

```
Day        Sessions      Tokens        Cost
Sep 9             2        1.1M       $3.20  ██████▎
Sep 10            4        2.6M       $7.05  ████████████████████
Sep 11            1        0.4M       $1.10  ███▉

Total             7        4.1M      $11.35
computed from the transcript at Sep 11 list prices — an estimate, not a bill
Claude Code recorded $10.80 for the 2 sessions it kept a record for
```

The last line appears only when a session **wholly inside the window** carries Claude Code's own record, and it names how many, because that is the only comparison that is exact: a record is one number for a whole session, so a session straddling the window's edge cannot contribute a share of it. Where no session in the window carries one, the line is absent rather than reading zero.

**A picture is drawn by default wherever the buckets are a span of time**, above the rows it summarizes. A caller who asked for thirty days asked to see thirty days, and making them name a second flag to see the shape of what they already selected is the same mistake as making them name three flags to reach the machine's total. The rows, the total and the notes are all kept — a picture is added to the answer, never put in place of it, so nothing a caller could read before becomes unreachable by default.

**The axis chooses the picture**, since what makes a drawing legible is the bucket, not a preference:

- `--by day` draws a **calendar** — a week per column, a weekday per row. Days are the only bucket whose squares a calendar can hold, and it is the only shape that shows the week's structure rather than only the trend.
- `--by week` and `--by month` draw a **sparkline**, one cell per bucket. Too few points for a calendar and too few for a plot with its own axis, but enough to show direction.
- `--by model`, `--by agent`, `--by project` and `--by session` draw **no picture**. Their rows have no order along the bottom of a plot, and the share bar on every row already says what a drawing would.
- The three-scope summary draws the **sparkline beneath its machine row**, described above.

`--chart` overrides that choice rather than enabling it. It takes `auto` — the default just described — plus `none`, `line` and `calendar`. `--chart none` prints the table alone, which is what every version before this one did.

`--chart line` draws a braille line plot, joining the points rather than leaving them as dots: a braille cell is two dots wide and four tall, so the plot fits four times as many points across a terminal as block characters do, and separate dots at that resolution read as scatter. The value axis is labelled down the left edge and the span named beneath, oldest at the left.

`--chart calendar` shades each square in one of four steps by which quarter of the spending days it falls in. Quarters by count rather than by dollars, since a month holding one very large day would otherwise shade every other day alike. A day inside the span that spent nothing is a dot, so an idle day and a day outside the window never read the same.

**A picture that cannot be drawn is simply absent.** One bucket is not a line and not a calendar, and a terminal too narrow for the drawing keeps the rows. Nothing is reported, because nothing was lost: the rows the picture summarizes are still on the screen.

`--chart` says how the answer is written rather than what is counted, so like `--format` and `--no-color` it leaves the three-scope summary standing instead of switching to the roll-up. The flag is rejected at parse time only where it cannot mean anything, naming both flags rather than the value alone: an explicit `line` or `calendar` on an axis that is not time, `calendar` on any roll-up axis but `--by day`, and any picture alongside a machine format, `json` or `jsonl`, whose records are the same either way. The rejection names the format the caller actually passed rather than the one it was written against.

`--format json` on the three-row summary emits `scopes`, one entry per panel as `{scope, label, since, sessions, usage, costUSD}` — `scope` being `session`, `folder` or `machine`, and `since` present on the machine panel alone — beside the same `recorded`, `unpricedModels` and `pricesVerified` the roll-up carries.

With a selector, `--format json` emits the roll-up object rather than a table: `by`, the bucket axis; `selection`, the `scope` that was priced with the `since` and `until` bounds that were named, which is what the note above prints; `buckets`, each with its `key`, `label` (a session's title, absent on every other axis), `sessions`, `usage`, `costUSD`, and — on the axes that take them — `turns` and `activeSeconds`; `total`, the same shape with no key; `spread`, the `sessions`, `medianPerTurn` and `p90PerTurn` described above, absent when too few sessions qualify; `recorded`, the `sessions` count and `costUSD` sum described above, absent when no session qualifies; `unpricedModels`, one entry per model with no price as `{model, sessions, usage}`; and `pricesVerified`, the date the rate table was checked. Like every other JSON form it ignores color, and an empty selection still emits a well-formed object with a zeroed total — a caller piping into `jq` reads the exit code to tell "nothing matched" from "nothing to look in", the rule `list --format json` already follows.

## Verbosity

`--level minimal | standard | detailed | full` is a preset over independent channels; default `minimal`. Each level is just a named set of channel defaults — per-channel overrides (`--thinking` / `--no-thinking`, `--tools`, `--tool-results`, `--subagents`, and their `--no-` forms) adjust any channel on top of the level, adding or subtracting (e.g. `--level detailed --no-thinking`).

**The levels cover the transcript alone.** The footer's aggregate sections are not among them — they print at every level and leave on `--no-metrics` (see Output), so no level turns them on and none turns them off.

The user prompt and the agent's response text are always shown — they are the irreducible transcript, not a channel. Levels layer notions of the work onto that base, breadth before depth: each level adds more *kinds* of detail until the deepest level adds the result bodies.

- **minimal** — prompts and response only.
- **standard** — + thinking.
- **detailed** — + tools (the notion that a tool fired) and + subagents (skill and subagent expansion). The shape of the work, without tool output.
- **full** — + tool-results (each tool's output body, and the instruction an `Agent` call delegated). The content of the work.

The channels:

- **thinking** — assistant reasoning blocks.
- **tools** — one line per tool call: its number in the turn, then that it fired, with name, truncated args, status, and duration. **The number leads the line because it is what a search hands a reader**: a turn that ran one tool repeatedly gives every one of those calls the same name, status and duration, so the number is the only field that says which of them a finding sat in. It counts the turn's calls in the order they print, a call before the stream it spawned, and it is assigned once where the turn is built rather than by each surface separately — a search naming the third call while a render numbered a different one would send a reader to the wrong call with nothing on either surface looking wrong. It costs no line: measured on a rendered session of fifteen thousand lines, the field fits beside the parenthetical, whose own cap bounds that line well inside the terminal. A call that was refused rather than run says so in place of its duration — `denied: permission-rule` — because the error glyph alone reads as "ran and failed", which is a different thing to go fix. An `Agent` call also names what it delegated to, bracketed after the tool name — `Agent[Explore@haiku]`, the subagent type then `@` and the model. A call that named no model shows the type alone (`Agent[Explore]`), since the subagent ran on the session's model and naming one would invent a fact the log does not carry. `Agent` is the only tool bracketed this way because it is the only one whose args hide its identity: a `Bash` line already opens with its program and a `Skill` line with its skill, while an `Agent` line carries the human description and nothing about which agent ran.
- **tool-results** — the body of each tool call: what it returned, and on an `Agent` call the instruction it was given. `tools` shows *that* a tool fired; `tool-results` shows *what the call asked for and what came back*. **A result body shows its first ten lines and names the remainder** (`… 38 more lines`), which makes it the kind of cap the CLI conventions section allows rather than a deletion. Ten because a result is machine output whose length nothing bounds — one file read or directory listing can run longer than every reply in the turn that made it put together — so uncapped bodies bury the transcript inside the output of the work instead of showing the work. **The cap lifts where the caller has named the turn**: `--turn` prints every body whole, the pressure the cap answers being a whole session's worth of them and a caller who selected one turn having already narrowed. A selected turn also prints each call's **whole argument text** as a block beneath its activation line, labelled `args`, wherever the line's parenthetical summary left something out. The parenthetical is the first line cut to a width, so a call whose arguments are a script was summarized by its first line and a search hit reported at `args:65` named a line no render would show. The label is the word `agentry search` prints for that part, so a hit's location and the block holding it read alike; the result body beneath needs no label, being the only other body a call can carry.

  **A body of more than one line is numbered, from 1 within that body.** A search hit is reported as `result:66`, and the number located nothing while the body it names was printed unnumbered — a reader was told which line held the passage and left to count sixty-six lines of captured output by eye. Numbering restarts at each body because that is what the hit counts from: one call can carry three bodies and one turn many calls, so a number continued across them would name a line no hit could ever cite. A one-line body is not numbered, its only line being the one the hit named. The numbers are drawn dim and cost the body their own width in columns, which is content wrapped one line earlier rather than content dropped.

  **A hit inside prose carries a number the render cannot show.** Assistant text and thinking are markdown, reflowed to the terminal's width, so their printed lines are not the lines a hit counted and numbering them would put a number against the wrong text. Those hits are reached by their turn, which the locator also names. Together these are what let a search hit be read where it was found — see User flows.

**The parenthetical's one elision is named.** It joins the argument's lines and cuts the result to a width, ending in `…` where the cut happened. Joining is what leaves one elision to name: ending at the first line instead deleted every line after it with no mark, so a reader came to believe a one-line call had one line — and a summary that had in fact shown a short multi-line argument whole still claimed to have left something out. The cap belongs to this surface alone in any case: `--format json` carries every result whole. The instruction prints above the result body or the expanded subagent stream, carrying the `❯` glyph a typed prompt carries, because a delegated run reads its instruction the way a session reads a prompt and the two should not need telling apart. It prints whole where a result body is capped: a result is machine output of unbounded size, where an instruction is text somebody wrote, and the first ten lines of a fifty-line brief answer nothing a reader asked. `Agent` is the only tool whose call body prints, because it is the only one whose activation line replaces the call with a label — the description is a heading of a few words, and nothing else on this surface says what the delegated run was actually told.
- **subagents** — expansion of nested work: a call that spawned a child session renders that session's inner event stream instead of a result body. This covers `Agent` calls and **forked** skills — the ones that run in a separate session, whether the model invoked the skill or the caller typed its slash command. An **inline** skill runs in the main chain, so its work already shows as ordinary turns there and the call stays a leaf (nothing to expand). Inside an expanded stream the same channels apply, so at `detailed` a forked skill expands to its tool-activation lines without their bodies.
- **metrics** — the footer's three aggregate sections: tools by identity, the per-turn token table, and day by day. It is the one channel that is on by default and has only a `--no-` form, because the sections it names print at every level (see Output). The per-turn rule beneath each turn (duration, tool count, the failed and denied counts, and what the turn spent) is not part of it and is always shown.

## CLI conventions

**A verb's bare form answers its commonest question.** The no-argument invocation is the one a person types first and remembers, so it resolves to the answer most callers want rather than to help text or the narrowest available reading: `agentry` lists this directory's sessions, `agentry view` renders the most recent one, and `agentry cost` prices this session, this folder and this machine. Flags narrow or widen that answer; they are not how it is assembled, since a caller who must combine three of them to reach the figure they want most has been handed the longest path to the most wanted result. Where a verb has no single commonest question it names the choices rather than inventing a default: `agentry completion` with no shell prints the four it can generate.

**No surface drops a fact to fit a budget agentry chose for itself.** A cap is allowed where the output names what it left out (`… (85 more files)`) and a fact is allowed to move to a roomier surface, but a line, column or level that deletes information outright needs a measurement behind it rather than a preference: a rendered session already runs to hundreds of lines, so a line spent is nothing against what is already on screen, and the fact it would have carried is what the caller came for. Where a surface cannot hold a fact, move it to one that can before dropping it — which is what the closing card does for the header's fields. Where it cannot move either, it wraps: the header's identity fields wrap inside their box on a narrow terminal, which was a drop order until the measurement showed the order deleting the entrypoint at the width every piped render uses.

Data on stdout, diagnostics on stderr. `NO_COLOR` (any non-empty value) or a non-TTY stdout disables color. `--help` and `--version` are always available, and each verb has its own `--help` listing only the flags valid in that mode. The bare command's help leads with the program version and carries both flag sets — the list flags (the bare command defaults to listing) and the render flags (for `agentry <uuid>`, which also apply to `view`, not to `list`) — grouping the render flags under their own heading so their scope stays legible, and every help screen carries usage examples. Exit codes follow `sysexits` — a missing project or session exits with a distinct non-zero code, not a generic failure.

Flags and operands may appear in any order (`agentry list --since today` and `agentry list` with flags before or after operands both parse). A mistyped verb, flag name, or enum value (e.g. `--include prompt` for `prompts`) errors to stderr, names the offending token, and suggests the nearest valid name by edit distance when one is close enough — it never auto-runs the guess and never dumps full help.

## Describing the output

`agentry schema` prints the shape of the machine-readable output: every document a `--format json` run writes, every record type a `--format jsonl` stream carries, and the envelope those lines are wrapped in. It exists because the shapes were written down in this document alone, which an agent piping `--format json` is never inside — so the keys had to be guessed from a sample, one `jq` call at a time, which is a cost paid by exactly the caller the machine formats are for.

**Every shape is read off the Go types the emitters pass**, not from a second written copy. A description that has to be maintained beside the code is wrong the first time a field is added and says nothing about being wrong; this one cannot drift, because the entry names the same value the emitter hands the encoder. The one claim reflection cannot make is a key a type permits and an emitter always clears — the stream's `event` record carries a tool object whose nested `subagent` stream is stripped, those events following as records of their own — and that key is pruned by name, with a stale path a build-time failure rather than a quiet no-op.

**The bare form prints everything and an argument narrows it**, by the verb that writes a shape or by a record's own type: `agentry schema view`, `agentry schema hit`. Both ends are offered because a caller arrives from either — they know which command they ran, or they know what a stream line said its `type` was. An unknown word is a usage error naming it and suggesting the nearest, like every other enum this program takes.

Each key prints on its own line with its type beside it, indented under the object that holds it, and the type column is aligned across the whole shape rather than per level: the indent already carries the nesting, so letting it move the types too makes one reader pay for it twice. A key absent rather than empty when the program has nothing to put there says so, which is the one thing a list of names cannot carry — a consumer has to branch on that absence. A type that holds itself, as a tool call's subagent stream holds the events its parent holds, is named and not descended into. The envelope prints only where a record does, since it wraps nothing a document run writes.

Types are named in the format's own vocabulary rather than Go's — `string`, `integer`, `number`, `boolean`, `object`, `array of …` — and a timestamp is called a string in RFC 3339, because `string` alone would not say it parses. It is deliberately not a JSON Schema document: the question this answers is what a key is called and what it holds, which is what a `jq` expression needs, where a validation document answers a question nobody asked here at several times the length.

`--format json` emits the same description as one object — `envelope`, `documents` and `records` — each shape carrying its `verb`, `name`, `kind` and `fields`. **This verb describes its own output too**, which is not a curiosity: leaving it out would reproduce one level up the gap the verb exists to close.

## Configuration

`agentry` reads an optional settings file holding **the defaults a caller would otherwise retype on every invocation**. A key may replace a default agentry already picks; no key adds a filter agentry does not already apply. The rule is mechanical: a flag whose Options row in README.md states a default is settable, and a flag whose default is no constraint at all is not — so `--level`, `--limit`, `--from`, `--format`, `--by` and `--chart` have keys, while `--since`, `--project`, `--model`, `--min-lines` and the `--used*` family have none. Changing a default changes the answer to the question the bare command was already answering; persisting a filter would instead make a bare listing drop sessions for a reason the command line does not carry and the output never names, which is the one way a settings file can make agentry lie about what it looked at.

**One file per machine, at `$XDG_CONFIG_HOME/agentry/config.json`** — `~/.config/agentry/config.json` when `XDG_CONFIG_HOME` is unset, empty or relative, which is the Base Directory Specification's own rule for an invalid value and the one agentry already applies to `CLAUDE_CONFIG_DIR`. An absent file is not an error: it means every default is the built-in one. There is no per-directory or per-project file, because agentry's answer already changes with the directory it runs in, and a second directory-shaped input would let one command print two different things with neither invocation showing why.

The file is **not** kept under `CLAUDE_CONFIG_DIR`. That variable says where Claude Code writes logs, so a caller who repoints it to read another machine's sessions would lose their own preferences in the same move.

**Shape.** Keys are flag names. A flag meaning one thing on every verb is a top-level key; a flag belonging to one verb, or meaning different things on different verbs, sits in that verb's section. `--level` is why sections exist at all: the render path's takes four values and `cost`'s takes two, so `full` is valid for one and a usage error for the other, and a single flat `level` key could only be right for one of them.

```json
{
  "format": "text",
  "from": "all",
  "view": { "level": "detailed" },
  "list": { "limit": 25 },
  "cost": { "by": "day", "chart": "line", "level": "minimal" }
}
```

| Key | Sets | Built-in default |
|---|---|---|
| `format` | `--format` on every verb | `text` |
| `from` | `--from` on `list`, `view` and `cost` | everything but `sdk` |
| `view.level` | `--level` on `view` and on the bare render path | `minimal` |
| `list.limit` | `--limit` on `list` and on the bare listing | `10` |
| `cost.by` | `--by` | `total` |
| `cost.chart` | `--chart` | `auto` |
| `cost.level` | `--level` on `cost` | `standard` |

Each value is the string its flag accepts, and a key that names a value its flag would reject is an error rather than a silently dropped line (see Errors below). `list.limit` additionally takes a JSON number — `25` and `"25"` both mean the count and `"all"` means no cap, the same two forms `--limit` itself takes. The bare command reads `view`'s section when it renders a session and `list`'s when it lists, which is the rule its flags already follow.

**Precedence is flag over file over built-in default**, and the file layer changes the default rather than the invocation. Every rule keyed on whether a flag was *passed* therefore keeps its meaning: a listing whose cap comes from `list.limit` is still a listing whose `--limit` was not passed, so a selecting flag lifts that cap exactly as it lifts the built-in ten, and `--format json` still ignores it. A caller who wants their configured cap honored alongside a selector passes `--limit` on the line, which is what passing it has always meant. There is no environment layer between flag and file: `NO_COLOR` and `CLAUDE_CONFIG_DIR` keep their existing meanings and are not config keys, the first because color is a property of the terminal being written to rather than a preference about output, the second because it names where logs live rather than how they are shown.

**Errors.** A file that cannot be read or parsed, a key or section agentry does not know, or a value its flag would reject stops the run before any session is read, writes one message naming the file, the key and the reason, and exits with `sysexits`' configuration code (`EX_CONFIG`, 78) rather than the usage code — the mistake is in a file, not on the command line, and a caller who typed nothing wrong should not be told their invocation was. An unknown key is met with the same nearest-name suggestion a mistyped flag gets. A key agentry does not know is never ignored: a settings file whose typo'd line is skipped reads as a preference that was applied and quietly was not. `--help` and `--version` still answer while the file is broken, since a caller repairing it is the one who needs to check what a key was called or quote a version in a bug report; every verb refuses until the file is fixed.

**`agentry config`** prints the file's path, whether it exists, and every settable key with three facts: its effective value, where that value came from — `config` for a key the file sets, `default` for one it does not — and what the key accepts. It answers the question a settings file creates and nothing else can: whether what is in the file is what agentry is using. It takes `--format` like every other verb and writes the same facts as one JSON object under `json` and `jsonl`.

The accepted values are spelled the way the flag's own help spells them (`minimal|standard|detailed|full`), and they are read from the same lists the flags and the file's validation use, so a key cannot offer one set and accept another. They are in the report rather than only in this document because a caller editing a JSON file has nowhere else to look: the format carries no comments, so the file cannot explain itself and the tool has to.

**`agentry config --init`** writes a starter file at that path, every key at its built-in default, and names the file it wrote. It is the other half of the same problem — a caller who has never seen the file needs one that is already valid to edit rather than a shape to copy out of a document. It refuses rather than overwrites when a file is already there, exiting with `sysexits`' can't-create code (`EX_CANTCREAT`, 73): a settings file is hand-written, and regenerating one on top of hand-written settings destroys the only copy. It is rejected alongside `--format json` or `jsonl`, naming both flags, because it writes a file instead of producing the report those shape.

One key is missing from what it writes. `from`'s default is two entrypoints at once and `--from` has no token meaning both, so no line in the file can ask for the behavior a caller already has; writing any value there would silently change it. `--init` leaves the key out and says so on stderr, naming the value it could not write, rather than shipping a file that quietly narrows what the caller sees. Every key it does write is one the file can express, so the generated file passes the same validation any hand-written one does.

## Shell completion

`agentry completion <bash|zsh|fish|powershell>` prints a completion script for that shell — the standard generator, so the setup is the one users already know (`source <(agentry completion zsh)`, or drop the script in the shell's completion directory). Beyond the verbs and flag names every completion script offers, agentry completes the two arguments worth completing:

- **enum flag values** — `--format` (`json`, `jsonl`, `text`), `--level` (`minimal`, `standard`, `detailed`, `full`), `--from` (`cli`, `app`, `sdk`, `all`), `--by` (`total`, `day`, `week`, `month`, `model`, `session`) and `--effort` (`low`, `medium`, `high`, `xhigh`, `max`) complete to their allowed values, not to filenames. `--effort` is the one whose candidates are suggestions rather than the accepted set: the filter takes any value, because Claude Code can add a level without notice and an unknown one should return no sessions rather than an error.
- **shape names** — `agentry schema`'s argument completes to the verbs that write machine-readable output and to every record type by name, built from the shapes themselves so a new record is completable the moment it is declared.
- **session ids** — the render path's positional argument, and `search`'s second one, complete to the session ids in scope, each annotated with its title (the same list `agentry list` shows), so the full UUID is a Tab, not a paste. `search`'s first argument completes to nothing at all: it is the caller's pattern, and offering session ids there would put a uuid where a pattern goes. Completion covers the same subtree the listing and the render path do, so every id it offers renders and every id that renders is offered; it never falls back to filename completion.

Completion is computed live on each Tab (a session id reflects the sessions present at that moment), so a new session is completable as soon as it exists.

Homebrew installs the scripts automatically — the cask links a bundled script into the shell's completion directory (see Distribution), so a `brew`-installed agentry tab-completes with no extra step. The `go install` and release-tarball paths have no install hook, so those users run `agentry completion <shell>` themselves; the tarball carries the pre-generated scripts for convenience.

## Scope

**MVP:** list sessions with recency and time-frame selectors (bare `agentry` or `agentry list`); resolve and render a session from the current directory (full-UUID arg → that session; `agentry view` with no id → most recent by modification time); styled terminal output with auto color detection; verbosity levels and channel overrides.

**Roadmap:** ordered by what is blocked today. The first group is where a caller still works
around agentry by hand; the second is the long-standing product surface, which no audit work
depends on. Insert a new item into the group whose description it matches rather than at the
end. (Two groups that once led this list are gone. Items a caller was working around: cross-project
listing shipped, and with it the loop that ran the binary once per repository. Content search across sessions shipped as `agentry search turn` and `agentry search session`, which read a session's whole content rather than its replies alone. Facts about a
session that a listing omitted or reported wrong: what it ran on, what it spent, and what it
produced are all in `list` now.)

- Title ladder: skip a bare slash command, not just `/clear`. A session whose first prompt is `/model` or `/effort` is titled by that command today, which describes the session no better than `/clear` does — a handful of sessions in one project read `/model`. The skip should cover any prompt that is a slash command alone, falling through to the next prompt as `/clear` already does.
- `--format md` / `-o FILE`: markdown-file export.
- Interactive session browser.
- Paging.
- homebrew-core distribution.

**Non-goals:** editing or replaying sessions; inline images; non–Claude Code log formats, until explicitly scoped.

## Log format compatibility

Claude Code's on-disk log format evolves across versions. `agentry` tracks the current format and retains support for older ones it has previously handled: a format change must not break rendering of sessions written by earlier Claude Code versions. Unrecognized fields and entry types are ignored, not treated as errors.

## Distribution

Built as a single static binary by GoReleaser. macOS installs from a personal Homebrew tap, distributed as a cask (GoReleaser deprecated formulae for pre-built binaries): `brew install eitanpo/tap/agentry`. Homebrew casks are macOS-only; on Linux install with `go install` or download a release binary. homebrew-core is a later target.

The release archive bundles pre-generated completion scripts (`completions/agentry.{bash,zsh,fish}`), and the cask links them into the shell's completion directory on install — so Homebrew users get completion (see Shell completion) with no extra step. The scripts are generated from source at build time rather than by the cask running the binary, because the binaries are unsigned and executing one at install time would fight the quarantine attribute the cask strips at install time.
