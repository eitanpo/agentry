# agentry — Product

Agent Replay: a single-binary CLI that renders a Claude Code session log into a readable, styled terminal view.

## Why

Claude Code stores each session as JSONL under `~/.claude/projects/`. Reading that raw is impractical. Routing the log through an agent's context instead strips terminal styling, forces a prompt-injection envelope, and is bounded by context size. `agentry` renders the log directly to the human's terminal: styling is native, there is no injection surface, and session size is unbounded.

## Users and usage

A developer who runs Claude Code in a project directory and wants to review a past session. The user runs `agentry` from the same directory they ran Claude in:

```
agentry                # list this project's sessions (see Listing sessions)
agentry <uuid>         # render a specific session, by id or any unambiguous prefix
agentry view [<uuid>]  # render; with no id, the most recent session
agentry list           # explicit form of the bare listing (see Listing sessions)
agentry cost           # what the sessions cost, by day, week, month, model, or session
```

With no argument, `agentry` **lists** this directory's sessions and those of every project nested under it — the default front door, identical to `agentry list`, so the bare command answers "which sessions do I have?" and the list flags (see Listing sessions) apply to it directly (`agentry --since today`). With an argument, `agentry` renders that session instead; the session id may be given **in full or as any unambiguous prefix** (`agentry 489ce01`), the rule `git` applies to object names; content search is on the roadmap. To render the **most recent** session without naming its id, use `agentry view` (no argument) — the most recent session by modification time, which may include one still in progress.

`agentry` is organized as verbs. The first token is treated as a verb when it names one (`view`, `list`, `cost`), otherwise as a session id — unambiguous because ids are hex (`0-9a-f`, hyphens) and verbs are English words, so they never collide. Rendering has an explicit verb, `view`: `agentry <uuid>` and `agentry view <uuid>` render identically, and `agentry view` with no id renders the most recent session — the no-argument render path the bare command used to be. `view` owns the render flags' own help page and is discoverable in `agentry --help`.

`agentry` resolves logs from the current directory: it maps `$PWD` to the Claude project folder under the **projects root**, which is `~/.claude/projects/` unless `CLAUDE_CONFIG_DIR` names another config home, in which case it is that directory's `projects/`. Claude Code reads the same variable to decide where to write, so agentry reading it is what keeps the two pointed at one directory; a machine that sets it otherwise has every session invisible to agentry, reported as having no project rather than as a path agentry did not look in. The variable holds **one absolute directory**, never a list, and an empty value counts as unset — both rules taken from Claude Code's own binary rather than from agentry's convenience, so a value Claude Code rejects is a value agentry must not honor either. Running from a different directory targets a different project — this is intentional. Both paths resolve in the same scope: the current directory's project **and every project nested under it**. The **listing** covers that scope, so standing in a repo lists the repo's own sessions and its worktrees' in one call; the **render** path resolves a session id within it, so an id read off a listing opens from where it was read rather than only from the directory the session ran in. `agentry view` with no id follows suit, picking the most recent session in the scope rather than in the current directory alone. It still orders by file modification time where a listing orders by last-entry timestamp, so the two can name different sessions; widening the scope does not change that, and neither reading is wrong — a file touched after its last recorded turn is genuinely the most recently written. Only the listing takes scope flags (`--project`, `--all-projects`, see Listing sessions); an id is passed in full and needs no way to say where to look. If the directory has no matching project, or the named session does not exist, `agentry` writes an error to stderr and exits with a distinct non-zero code.

Rendering tries the current directory's own project **first and alone**, and scans the nested projects only when the id is not there. The scan reads a file per project folder, so the ordinary case — an id belonging to the directory you are standing in — pays nothing for the wider reach. Where two projects in scope hold the same id, the current directory's own wins and the rest are taken in folder order; session ids are UUIDs, so this settles a tie that does not arise rather than a choice a caller would make.

The project folder's name is the working directory's absolute path with **every non-alphanumeric character replaced by `-`** — not only `/`, but `.` and `_` as well, so `/repo/.claude/worktrees/w` becomes `-repo--claude-worktrees-w`. Getting that rule wrong is not a near miss: the mis-spelled folder simply does not exist, and every path with a dot component reports "no Claude project for this directory" while holding sessions. That covers every worktree Claude Code creates for itself, since it puts them under `<repo>/.claude/worktrees/`. The encoding is also **lossy and must never be reversed** — `-a-b-c` could have come from `/a/b/c` or `/a/b-c`. Where agentry needs a project's real path it reads the `cwd` field the log records on its entries, which is exact and survives the directory being deleted or renamed.

## Output

`agentry` prints a styled view of the session: colorized turns with per-actor glyphs, plus code blocks, thinking, tool calls, and subagents (subject to verbosity).

A turn shows the user prompt as a highlighted block enclosed in a rounded border — the prompt text prefixed with a `❯` glyph (wrapped lines hang-indent to align under the prompt) — then the assistant's reply as an indented left rail (`│`) headed by a `◆` glyph aligned with the rail — prose, thinking, and tool calls hang off the rail, which a closing rule (`╰─`) terminates. With color off, the prompt highlight degrades to plain `❯`-prefixed text.

**A turn starts at a prompt a person typed, not at every entry Claude Code files under the user's name.** The log records harness-attached material — a loaded skill's body, a notice that a skill was loaded earlier, a note about an image being rescaled, a nudge after a malformed tool call — as user entries too, and rendering those as prompts would invent turns nobody took and let one of them become the session's title. Claude Code marks such an entry (`turnCompanion`) and its own prompt test refuses to count it, so agentry refuses it on the same marker rather than on what the text looks like. Older logs carry no marker, and for those agentry falls back to recognizing the wrappers the harness writes around injected content, which is what it did everywhere before the marker existed. The one entry that survives both tests despite being written by the harness is a compaction boundary, which stands in for the conversation it replaced and so has to keep its place in the turn sequence.

Markdown links (`[text](url)`) in assistant prose render as OSC 8 terminal hyperlinks: the link text is shown in a dedicated link color and is clickable, and the raw URL is hidden. The URL is used verbatim as the href, for any scheme (`https://`, `obsidian://`, …) — agentry constructs nothing. Only assistant prose is linkified (not tool output, thinking, or prompts), and a link whose text glamour wrapped across lines stays plain. Like color, this is gated on a terminal: with color off, the link renders in glamour's default form (the text followed by the URL).

Bare URLs in assistant prose — any `scheme://` URL written without link syntax (`http://`, `https://`, `obsidian://`, `vscode://`, …) — become clickable too, the URL text itself as the link. One scheme gets a nicer label: an `obsidian://open?…&file=<path>` URI renders as an Obsidian-style wikilink — `[[<note>]]`, the file's base name with any folders and the `.md` extension dropped (a `#heading` or `#^block` anchor is kept) — linking to the full URI; so a session that cites a note shows `[[Note]]` rather than the raw `obsidian://…` string, with the vault and path preserved in the hidden href. Any other obsidian URI (or an `open` without a `file`) shows its URL text like the rest. All bare links use the same dedicated link color. A URI is recognized bare when it has the `scheme://` form — a leading letter, then letters/digits/`+`/`-`/`.`, then `://`; a scheme without `//` such as `mailto:` is not autolinked and must use `[text](url)` syntax. Trailing sentence punctuation (`.`, `,`, `;`, `:`, `!`, `?`) is excluded from the href, as is a trailing `)` with no matching `(` inside the URL — so a URL wrapped in `(…)` drops the closing paren while one that itself contains balanced parens (a Wikipedia article, say) keeps it. The same conditions apply as for markdown links: assistant prose only, gated on color, and a link whose text glamour wrapped across lines stays plain.

Color is auto-detected: styled (ANSI) when stdout is a terminal; plain, unstyled text when stdout is piped or redirected, or when `NO_COLOR` is set. `--no-color` forces plain output. Output is not paged in this version — pipe to a pager if you want one.

The header names the **model** the session ran on, after the duration and before the effort. It resolves the way the two settings beside it do — the last value the log carries, with the whole sequence spelled out (`claude-sonnet-5→claude-opus-5`) when the session switched mid-way. Switching is not an edge case: 13 of 250 local sessions did it, so a header naming only the first would misreport one session in twenty. `<synthetic>` is excluded from that reading — it is what Claude Code writes on messages it composes itself (an API-error notice, a session-limit warning, `No response requested.`), those carry zero tokens and name no model the session ran on, and counting them would end a session on a model that never ran. A session whose log names no model at all says nothing, where it once said `unknown`: that is the rule effort and entrypoint already follow, and the word claimed a fact the log does not carry. `--format json` carries `model` and, when it changed, `models`.

The header also names the **reasoning effort** the model was run at, immediately after the model and read as a phrase — `claude-opus-5 · high effort`. Effort moves both cost and quality, so without it two sessions on the same model at very different settings are identical in every view agentry produces. A session that changed effort mid-way shows the transition the same way the entrypoint does (`xhigh→high effort`), and the resolved value is the last one, matching the session's last activity. Only about half of sessions carry the field at all — Claude Code added it in 2.1.212 — and one that does not says nothing rather than guessing a default. `--format json` carries `effort` and, when it changed, `efforts`.

The rendered view names **where the session ran** in its header, after the model — `app→cli` when a session was started in the desktop app and resumed from the terminal, or a single value when it never moved. The listing compresses that case to a `+` suffix because a column is four characters wide; the header has a full line to itself, so it spells the transition out. The vocabulary is the listing's (`cli`, `app`, `sdk`, `?` for an unrecognized value — see Listing sessions), and a session predating the field says nothing rather than guessing.

The header's **token tally counts each API response once**, not once per log entry. Claude Code writes one assistant entry per content block of a response — a reply holding a thought and three tool calls becomes four entries — and repeats that response's whole usage object on every one of them. Adding the entries up therefore multiplies a reply's tokens by how many blocks it held: measured across 22 local sessions the inflation ran from 1.75× to 3.11×, averaging 2.34×, and it is not a constant, so it distorts the per-turn ranking in the summary below as well as the totals. agentry keys the tally by the response id each entry carries (`requestId`) and counts **the entry whose output count is highest**, discarding the rest; an entry carrying no response id — one Claude Code composed itself, or one from a log old enough to predate the field — is keyed by its own entry id instead, which counts it once, exactly as it was counted before.

**The highest entry and not the first, because a response's repeats are not identical.** Claude Code writes each entry as the reply streams, so the input count and both cache counts match on every entry of one response while the output count **grows** — an early entry carries a partial figure and the last carries the finished one. Counting the first entry therefore undercounts output, and not by a rounding: measured over all 71,556 response groups in the local logs, 11,535 of them (16%) disagree, every disagreement in the output count alone, and first entries total 20.8% less output than highest ones. One session reported 1,396,336 output tokens where its highest entries hold 3,108,698 — 55% low, against a Claude Code cost record for that same session naming 3,274,666. Taking the highest brings the tally within a few percent of Claude Code's own accounting, which is the one external figure available to check it against, and an earlier revision of this section asserted the repeats were identical on a sample that held no disagreeing group. The rule applies everywhere a token figure is produced — the header, the per-turn summary, `--format json`, and the listing — so no two surfaces can disagree. Every count is abbreviated the same way wherever it is printed: exact below a thousand, then thousands (`3.1k`, `211k`), then millions (`3.1M`) and billions (`12B`) as the count reaches them, because a roll-up's figure written in thousands (`3108k`) is not read at a glance.

The header also names what the session **cost in dollars**, and **how much code it changed**, at the end of the token line — `Tokens: 494 in / 211k out  ·  cache 97%  ·  saved 40%  ·  $35.07  ·  +342/-8`. Claude Code keeps a running total of its own in the log and rewrites it as the session goes, so agentry reads the last such record rather than adding them up. A session whose log carries none — anything before Claude Code 2.1.241, and any session it has not written one for — shows no dollar figure rather than `$0.00`, the rule the model and effort beside it already follow: the log simply does not say. The figure is Claude Code's own accounting and not a price agentry computes from tokens, and this surface keeps it that way: a `$` in the header is always the record, so a session showing none is one Claude Code wrote no record for rather than one agentry declined to price. A dollar figure on every session, and what a day or a month cost across many of them, is `agentry cost` (see Rolling up cost), which prices the tokens itself and says so. It **does** include a subagent's spend. The log never says so, but Claude Code prices every request a session's process makes into one ledger, and pricing the 71 locally recorded sessions from published rates agrees: their main logs alone come to $2,200 against the $3,043 those records report, and to $3,159 once the subagent sidecars are added. What the figure does not cover is requests Claude Code makes without writing an entry for them — its own background work — and what it can undercount is a session whose ledger was reset partway, which zeroes the earlier legs. The two pull opposite ways, so the record and a transcript price agree within 4% across the corpus and can differ either way on one session (see Rolling up cost).

**Beside the cache share the header names what caching saved** — `cache 97%  ·  saved 40%`. The two are a pair rather than a repetition. The cache share is how much of a request's input was served from cache; the saved share is what that took off the bill, and a session can read high on one and middling on the other, as the example does — 97% of its input came from cache, and the saving is held to 40% because output tokens carry most of what it spent.

**The comparison is the same tokens priced twice**, which is what makes it a fact rather than a guess. Caching does not change how many tokens a request sends — the whole context goes on every request either way — it changes the rate the resent part is charged at, a tenth of the input rate to read and 1.25 or 2 times it to write. So the second price is every cached token charged as fresh input, with the output unchanged, and the difference is the saving and nothing else. Measured over 305 local sessions on 2026-09-12 the saved share runs 60% at the tenth percentile, 79% at the median and 88% at the highest, where the cache share over the same sessions runs 84% at the tenth percentile and 96% at the median: the two move together and the saved share spreads a session further from its neighbours.

**The saved share is computed, so it is a percentage and never a dollar figure.** The rule above holds without exception — a `$` in the header is always Claude Code's own record — and a computed dollar saving printed beside a recorded dollar total would put an estimate and a record on one line with nothing telling them apart. What the saving came to in dollars is `cacheSaving` in `--format json`, on both the render path and the listing, where a figure carries no risk of being read as the record beside it.

**The saving is priced per model rather than per session.** A session's responses are split by the model that answered before either price is taken, because the rates are not proportional across models: one tier prices cache reads at a fortieth of its own input rate where every other prices them at a tenth, so pricing a mixed-model session at its last model's rates would report a saving it did not get. A response whose model agentry holds no price for is left out of both prices rather than counted at zero, the rule the roll-up already follows, and a session with no priceable response at all shows no saved share rather than `saved 0%`. The saved share is dropped wherever the cache share beside it is dropped, since the two are one pair.

**A session caching cost more than it saved reads negative, and is not clamped.** A cache write bought for an hour costs twice the input rate, so a session that writes a large cache and then ends without reading it back pays more than the same tokens would have cost uncached: `saved -97%` says the session paid nearly double. Locally 66 of 552 sessions read negative on 2026-09-12, 59 of them non-interactive runs the listing's default already hides; among the 305 the default shows, 7 do, and the median is still 79%. Clamping the figure at zero would render those as sessions caching neither helped nor hurt, which is the one reading that is never true of them.

The lines added and removed come from that same record, so they appear exactly when the dollar figure does. They are **dropped when both are zero**, which is the common case — two thirds of local sessions carrying a record changed no lines at all, and a `+0/-0` on every one of them would spend the header's width on nothing. Nothing is lost by dropping them: the dollar figure beside them already says the record exists, so a session showing a cost and no counters changed no code. Unlike the cost, the counters are known to reach **delegated** work — a local session whose main thread made no edit call, and whose subagents made 29, recorded 22 lines added — so a session that edited only through subagents still reports what it changed. What they do not count is a file written by a shell command: a local session that ran 115 shell writes, heredocs included, and made no edit call recorded zero lines either way. agentry's `files` channel does catch those, so a session can list files it changed and still report no lines — the two read different records and answer different questions.

The rendered view ends with an **Outputs** section naming what the session produced beyond its own transcript: one line per pull request it opened and one per artifact it published. These are the same two facts `list --include outputs` shows, read the same way and deduplicated the same way (see Listing sessions), so the two paths never disagree about what one session produced. It sits after the last turn and before the metrics summary, because an output is a result of the session rather than a property of it — the header says what the session *was*, and a pull request is what came out of it. A session that produced neither has no such section, which is the common case: 42 of 250 local sessions opened a pull request and 6 published an artifact.

Unlike the metrics summary below it, the section is **not gated on a verbosity channel** — it renders at `--level minimal` too. An output is an outcome, not working detail: thinking and tool bodies are hidden at low verbosity because they are the machinery, and a link to the pull request the session opened is the opposite of machinery. It costs nothing on the sessions that produced nothing, since those show no section at all.

With color on, each line is an OSC 8 terminal hyperlink, following the same split assistant prose already uses. A pull request is its own URL as the link text, the way a bare URL in prose is. An artifact is its **title** as the link text with the `claude.ai` URL hidden in the href, the way a markdown link is — because an artifact id is an opaque uuid, so showing it in place of a name would be strictly worse than the name. An artifact whose record carried no title falls back to its URL as the text. With color off the section degrades the way links in prose do: the text and the URL both shown, plainly, with nothing to click.

`agentry view` **with no id resolves to the most recent session that was not a non-interactive run**, for the same reason the listing hides them: on a machine using hooks the newest session is usually a few-second headless run, so "show me my last session" would otherwise render a hook. Naming an id renders that session whatever its kind — the id is an explicit request and is never second-guessed. When a project holds nothing but non-interactive sessions, `view` renders the most recent one anyway and says so on stderr; refusing would be wrong, since sessions plainly exist.

`--from` chooses which kind of session that resolution walks back to, taking the listing's four values (`cli`, `app`, `sdk`, `all` — see Listing sessions). `agentry view --from sdk` renders the most recent non-interactive run, which is how the hook or `claude -p` call that just fired gets read back; `--from all` renders the most recent session of any kind, the pre-default behavior. A named value that matches no session here is an error, not a fallback to something else: the caller asked for one kind, so rendering another would misreport what they are reading — which also means the stderr note above belongs to the default alone. `--from` beside a session id is a usage error, since the id already names the session and the flag could only contradict it.

Session-id completion follows the same default: it offers the ids a listing would show, not every id on disk, so tabbing a UUID does not surface hook runs ahead of the work you are looking for. It reads `--from` off the command line being completed, so `agentry view --from sdk <Tab>` offers the runs that command would render rather than the ones the default shows.

`--format json` emits the full parsed session model as JSON instead of the styled view — the render path's machine-readable form, for agent consumption and piping into `jq`. It serializes the same in-memory model that drives terminal rendering: a top-level object with `meta` (`id`, `model` plus `models` when it changed mid-session, `effort` plus `efforts` on the same rule, `start`, `end`, `usage`, `costUSD` with `linesAdded` and `linesRemoved` when the log recorded them, `numSubagents`, `entrypoint` plus `entrypoints`, and `prs` and `artifacts` — the same fields, resolved the same way, that `list --format json` carries per session, so the two paths never disagree about where one session ran or what it produced) and `turns`. Each turn carries its `prompt`, `start`, `end`, `usage`, `toolCount`, `errorCount`, and an ordered `events` array; each event has a `kind` — the string `text`, `thinking`, or `tool` (not its ordinal) — with a `text` body for the first two, or a `tool` object (`name`, `args`, `identity`, `model`, `denial`, `result`, `isError`, `start`, `end`, and a nested `subagent` event stream when the call spawned one) for the last. `denial` is why a call was refused — `permission-rule`, `automode-blocked`, `automode-unavailable`, or `user-rejected` — and is absent on every call that actually ran, including one that ran and failed; `isError` is true either way, so `denial` is what separates "the tool was not allowed to run" from "the tool ran and returned an error". `identity` is the call's grouping label — the same value `list --include tools` groups by (the invoked program for `Bash`, the skill for `Skill`, the subagent type for `Agent`; absent for tools whose own name is their identity), so the two paths name one call the same way rather than the render path knowing less. `model` is the model a call delegated to, absent when it named none: only `Agent` carries one, and a call that omits it leaves the subagent on the session's own model. Both are recovered from input fields `args` discards — `args` is a one-line human summary, and for `Agent` that summary is the description — so without them the type and model of a delegated subagent could not be read back out of a session at all, which is the question a cost audit asks of every `Agent` call. Being the complete model, it ignores the verbosity flags (`--level` and the channel toggles) and color — those shape only the text view, whereas the JSON is always the whole model. `--format` also accepts `text` (the default styled view); an unknown value is a usage error, suggesting the nearest valid format like every other enum flag. This is the render-path counterpart of `list --format json` (see Listing sessions), which serializes the lightweight per-session summaries.

## Listing sessions

`agentry list` lists the sessions in the current directory's project instead of rendering one, so you can find the one you want. Bare `agentry` with no session id is the same listing — `list` is its explicit form — and every flag in this section works on the bare command too (`agentry --since today` == `agentry list --since today`). Sessions are selected by recency (most-recent activity) and printed oldest-to-newest, so the most recent sits at the bottom, nearest your prompt — the convention of `ls -ltr`, shell history, and chat logs for unpaged scrolling output. Each is one row: the time of the session's last activity — when its most recent turn ended, the same recency the list is ordered by (falling back to its start when no later timestamp is known) — its duration (first prompt to last output), its turn count, a title, and and its session id in full, with the shortest prefix that is unique among the rows shown — never below 8 characters — drawn brighter than the rest of it. Pass the prefix back to `agentry <id>` to render the session, or the whole value to `claude --resume`. The title is chosen by a fallback ladder: the session's **manual title** when present — a name you chose wins over everything below, and Claude Code freezes its own summary once you set one; otherwise Claude Code's own session summary (the `ai-title` it writes into the log, latest one winning); otherwise the first user prompt, skipping a leading `/clear` (which only resets context and says nothing about the session) in favor of the next prompt; a session that is nothing but `/clear` keeps it. A `/clear` typed with trailing text on the same line (Claude Code records the text as the command's arguments) is still treated as `/clear` and skipped — the trailing text describes the reset, not the session.

The **manual title** rung reads two entries, not one, because Claude Code records a chosen name in two places. Renaming a session writes a `custom-title`, and naming it with `--name` at launch or `/rename` in session writes an `agent-name` — the name its statusline shows. The two usually carry the same string, but a session named only at launch has an `agent-name` and no `custom-title`, and a ladder reading only the latter falls through to the generated `ai-title` and displays a name you did not choose. Both count as manual, neither outranks the other by kind, and **the last one written to the log wins** — the same latest-wins rule each already had on its own. This matters because the two can be set at different moments: `/rename` names the session you are in, while `/clear NAME` labels the session you are leaving, so a session can receive an `agent-name` early and a `custom-title` later. File order is the only ordering available — these entries carry no timestamp.

Forked sessions are grouped. Claude Code's `--fork-session` (and the in-session `/branch`) copies a session's conversation into a new file, so a fork and its parent share the same root entry; agentry detects this by their shared root id and lists the family together — the original session's row, then each fork indented beneath it with a `└─` marker. The original is the **earliest-created file** in the family: a fork is a new file written at fork time and cannot reproduce the original's file-creation time, even though its copied content reproduces the original's in-conversation timestamps. (On platforms where a file's creation time is not readable — anything but macOS — agentry falls back to the modification time, which can mis-order a family whose sessions all stayed active.) A family takes its position in the list from its most-recently-active member. `/clear` is not a fork: it starts an empty session with a fresh root id, so it never joins a family.

A fork inherits its parent's title — Claude Code seeds the new session with the parent's `ai-title`, so until it regenerates one the two are identical and indistinguishable in the list. While a fork's title still equals its parent's, the listing instead titles it by its **first divergent prompt**: the first prompt the fork has that its parent does not — the first turn unique to the fork (a leading `/clear` is skipped, as in the title ladder, since `/clear` is already absent from the prompt list). A fork that has added no new prompt yet keeps the shared title. This is a text-table refinement only; `--format json` reports each session's real stored title.

A title that merely repeats the row's **worktree** is replaced the same way, by the session's first prompt. A launcher that derives both a worktree and `claude --name` from one argument makes the two identical by construction — a session in worktree `plan` titled `plan` — and the worktree column beside it already carries that string, so the title spends the field a row is scanned by on a duplicate. The trigger is the duplication rather than any judgement about the name: a title equal to the worktree name falls through, and one a person wrote (`Plan the migration`) stands however similar it looks. A session with no prompt recorded keeps its title, as a fork with no new prompt does. Like the fork refinement this is text-table only, so `--format json` still reports the stored title, and it deliberately departs from Claude Code's own precedence, which ranks a chosen name above a generated summary unconditionally — the listing can afford to, because it is the surface that also draws the worktree column and can see the duplication.

By default the list shows the 10 most-recent sessions. `--limit N` changes the cap; `--limit 0` removes it. Two time-frame filters narrow the window, both compared against a session's last-activity time:

- `--since WHEN` — sessions active at or after WHEN.
- `--until WHEN` — sessions active at or before WHEN.

WHEN is one of: `today` or `yesterday` (local midnight of that day); a span back from now with a unit — `Nh`, `Nd`, or `Nw` (e.g. `24h`, `7d`, `2w`); or an absolute local date `YYYY-MM-DD`. An unrecognized WHEN is a usage error.

`--include CHANNELS` adds per-session detail, given as a comma-separated list of channels. All detail renders under the session's row on a left rail closed by a rule — the same chrome as a rendered turn — and the rail-and-rule bounds the block, separating one session from the next. When more than one channel is selected they share a single block (one rail, one closing rule).

**A block holding exactly one line hangs that line off the closing rule** — `╰─ Tokens: 180 in / 93k out  ·  cache 96%  ·  saved 81%  ·  $8.73  ·  +290/-0` — rather than printing it on the rail with a bare rule beneath. Chrome then never costs more lines than the content it bounds, which is the commonest shape this surface takes: one channel selected, one line to show. A block of two lines or more keeps the rail and closes on a rule of its own, because content sitting on the rule there would give the last line different chrome from its siblings for no difference in what it says. A block a channel leaves empty still prints the bare rule, which is what separates that session's row from the next. `all` selects every channel. An unknown channel is a usage error. The channels:

- `prompts` — the session's user prompts, listed in order each prefixed with the `❯` glyph, `/clear` omitted (including a `/clear` carrying trailing arguments); every prompt is shown (the view is opt-in).
- `tools` — a breakdown of the session's **top-level** tool calls, grouped by identity rather than by bare tool name, because the signal is *which* commands, skills, and agents ran. Six category lines, each shown only when non-empty: `Skills` (by skill name), `Agents` (by subagent type — named agents appear by name), `Bash` (by invoked program — the first command token, leading `VAR=` assignments stripped, reduced to its basename), `Edits` (by the base name of each file an `Edit` or `Write` targeted), `Denied` (below), and `Other` (every remaining tool by its own name). Within a line, entries read `name ×count`, ordered by count descending then name. "Top-level" means the calls the main thread made — calls inside subagents are not counted, matching the per-turn tool count.

  `Edits` exists because a summary that says a session edited something and never *what* cannot tell a run that touched a `SKILL.md` from one that touched a source file or a config, though those are different kinds of work. It shows base names, the same compression `Bash` applies in reducing a command to its program; `--format json` carries each call's full path, so the table stays readable without the detail being lost.

  `Denied` names the calls that were refused and by what, reading `kind: tool/identity ×count` — `permission-rule` (a settings deny rule), `automode-blocked` and `automode-unavailable` (the auto-mode classifier), or `user-rejected` (a person said no). Without it a refused call is indistinguishable from one that ran and failed, so choosing what to add to an auto-allow list has no data source but memory. Only these four kinds are reported; a call that failed for any other reason is an ordinary error and appears in no `Denied` entry. Like every other line in this channel it counts top-level calls only — a call a subagent made and had refused is in that subagent's own sidecar, which a listing does not read.
- `files` — every file the session modified, one per line, by any means rather than only through the two tools whose arguments agentry reads. Claude Code records these itself: `file-history-snapshot` entries key `snapshot.trackedFileBackups` by path, and `file-history-delta` entries carry a `trackingPath`. Paths mix repo-relative with absolute in the log, so agentry resolves each against the session's recorded working directory and reports one absolute path per file, first-seen order. This is the session-level counterpart of the `Edits` line, which breaks the same ground down per call: a file changed by a shell command appears here and not there. About 110 of 257 local sessions carry the entries at all, and a session without them lists no files rather than claiming it changed nothing.
- `model` — one line naming what the session ran on: its model and the reasoning effort beside it, in the rendered header's phrasing (`claude-opus-5 · high effort`), with the same `→` when either changed mid-session and with the effort half absent on a session predating that field. A session whose log names neither shows no line rather than an empty one. This is also what makes the `--model` and `--effort` selectors (below) usable: a filter over a fact the output never displays leaves you guessing at its values.
- `cost` — one line naming what the session amounted to, in the rendered header's exact wording (`Tokens: 494 in / 211k out  ·  cache 97%  ·  saved 40%  ·  $35.07  ·  +342/-8`) and built by the same code, so a figure read off a listing and one read off a rendered session cannot differ. The dollar figure and the line counters are Claude Code's own running totals, read from the log rather than computed, and are absent on a session whose log carries none — every session before Claude Code 2.1.241, and plenty since, which show the token half alone. The counters are also dropped on a session that changed no lines, on the rule the header states. The saved share beside the cache share is agentry's own price rather than a record, and is absent on a session none of whose responses it holds a price for. The token half is always present and is the only place the text table states a session's tokens at all; `--format json` has carried them since before this channel existed, so the channel closes the gap between the two formats rather than adding a fact. Like `model`, this describes the session rather than enumerating its contents, so it renders above the channels that list things.
- `outputs` — what the session produced beyond its own transcript: one line per pull request it opened and one per artifact it published. A pull request shows as its URL, which already names the repository and the number; an artifact shows as its title followed by its `claude.ai` URL, falling back to the URL alone when the log recorded no title. A session that produced neither shows no line.

  Each line is cut so that the half identifying the thing survives, which points the two kinds in opposite directions. A pull request truncates from the left, like the `files` channel and for the same reason: the repository and the number are at the tail, and the scheme and host at the head are what every line repeats. An artifact truncates from the right, keeping the title and letting the URL go, because a `claude.ai` artifact id is an opaque uuid that identifies nothing to a reader — the same trade the `Edits` line makes for paths, and `--format json` carries the URL in full either way.

  Claude Code writes these itself, as a `pr-link` entry when a pull request is opened and a `frame-link` entry when an artifact is published, and it writes them **for the session as a whole**: no subagent sidecar carries one. So this channel reports a pull request opened deep inside a subagent or a skill exactly as it reports one the main thread opened with a `gh` call, which is the axis every tool-call view misses.

  Both kinds are **re-recorded on later turns**, and heavily — 963 `pr-link` entries across the development corpus reduce to 67 once each session's own are deduplicated. agentry reports each once, in first-seen order, keyed by its **URL**: the identity that survives everything else about it changing. It has to be the URL rather than the local file, because an artifact republished from a moved file — a scratchpad draft promoted into the repository — keeps its `claude.ai` URL and changes its path, and keying on the path would report one artifact as two. Where repeated entries disagree about a title or a path, the last one wins, matching how every other changing value in a session resolves. A title is optional (21 of 66 local entries carry none).

A listing covers the current directory's project **and every project nested under it**. Matching is on each project's recorded working directory compared component by component, so standing in `/a/b` does not pick up `/a/bc`.

Subtree scope is what makes a listing answer the question a repo actually raises. Claude Code gives every git worktree its own project folder, so a repo's sessions are split across one folder per worktree, and a listing confined to the folder the repo path encodes to would show none of the worktree ones — which is what a bare `agentry list` in a main checkout used to do. Standing in the repo now sweeps the worktrees Claude Code creates under `<repo>/.claude/worktrees/` along with it. What it does **not** reach is a worktree placed outside the repo — for that, name a directory that contains both with `--project`. The cost of the wider default is one pass over the project folders to read each one's recorded `cwd`: locally, 0.45s to 0.67s on a repo with nine worktrees.

Two flags move the listing off the current directory. They are mutually exclusive — given together they are a usage error, because `--all-projects` already covers every project and naming one narrows nothing.

- `--all-projects` — every project under the projects root (see Output for where that is), in one call.
- `--project PATH` — the sessions of PATH and of everything nested under it, rather than the current directory's. It chooses the root, not the depth: the subtree rule is the same one the default follows. Naming a directory that holds many repos lists all of them, which is how one call replaces a loop that runs the binary once per repository.

Every listing scope — the default and both flags — reaches projects whose directory has since been deleted or renamed, because selection reads each project's recorded `cwd` rather than walking the filesystem. That is a real difference and not an edge case: on the development machine 37 of 63 project folders had no surviving directory, so a filesystem walk finds fewer than half of them.

The **root of a subtree is the exception**, and is taken by folder name instead: standing in a directory lists its own project, and `--project PATH` lists PATH's own, whatever those sessions record as their `cwd`. The two rules disagree only for a folder holding a session that records some other path — one relocated into it, or one predating the field — and there the name is the answer that matches what the caller asked for. Widening the default scope must not drop what the narrow lookup returned, which is the same guarantee stated from the other side: no session that a listing showed before is hidden by the subtree rule. Only **nested** projects need a recorded `cwd` to be found, and every project in the development corpus has one (72 of 72).

When a listing spans more than one project, each row gains a **project column** naming where the session ran, placed before the title. **A project is the repository, not the folder Claude Code files it under**: a session whose `cwd` is `<repo>/.claude/worktrees/<name>` is labelled by `<repo>`, so every session of one repo shares one label however many worktrees they were spread across. That is the scope rule of this section applied to the label — a listing already treats a repo's worktrees as the repo — and without it three worktrees of one repository read as `plan`, `ngnix` and `jfrog-usage`, three labels naming no project and denying that the sessions belong together. It shows the shortest suffix of path components that is unique among the projects listed — `agentry` when that name is unambiguous, `me/agentry` and `wix-private/agentry` when it is not — because a bare directory name collides exactly where repositories are grouped under owners, and a full path does not fit beside a session id. The column is capped at a third of the space the project and title columns share, and truncates from the left (`…y-migration`) since the tail is the distinguishing end. A listing confined to one project has no such column, so single-project output is unchanged. Full paths are always available in `--format json`.

Inside one repository the same slot carries a **worktree column** instead, naming which worktree each session ran in, with `—` for one that ran in the repo's own checkout. Collapsing worktrees into the project label is what makes this necessary: within a repo the worktree is the only thing separating one line of work from another, and the sessions of five worktrees otherwise differ by nothing but their titles. The two columns cannot both appear — the project column is drawn only when a listing holds more than one project and this one only when it holds exactly one — so a row never carries two path columns and the title never pays for both. Width and cap are the project column's, and the column is drawn on the same appear-only-when-it-varies rule: a listing whose sessions all sit in the same place, whether that is the repo root or a single worktree, has no worktree column. It truncates from the **right** (`ecr-gar-single-registry…`), opposite the project column, because a worktree name's head is the name someone chose and its tail can be generated — a worktree Claude Code creates from the desktop app carries a 6-character hex suffix (`ecr-gar-single-registry-f399e1`), which 6 of the 9 worktrees on the development machine have and left-truncation would keep in place of the name. `--format json` carries the whole path as `cwd`, so nothing this column compresses is lost there.

Either path column, project or worktree, **keeps the characters that tell colliding labels apart**. Truncation is applied first; where two labels then render identically, the ellipsis moves inward on those two, leaving a head and a tail, and the retained end is one character longer than the longest run the colliders share there — the mirror of the distinguishing-prefix rule, `lcp + 1`, which names how many characters separate two strings. Three worktrees named `update-cloudsmith`, `update-cloudsmith2` and `update-cloudsmith3` therefore read `update…h`, `update…2` and `update…3` in an 8-wide column, where before they were three identical cells claiming to be one worktree. VS Code's editor tabs resolve colliding file names the same way, growing a candidate until it stops colliding.

Two properties keep the rule honest. The comparison is over **distinct labels**, so many rows sharing one label are not a collision — the `—` that every session in a repo's own checkout shows is left alone, and so is a worktree that several sessions ran in. And where no split fits the column, because the colliders differ too far from the retained end, **the duplicate stands**: a marker like `…#2` would be an identifier meaning nothing outside that one listing, and the session id already separates the rows. That case buys distinguishability without legibility even when it does fit — two worktrees differing in their first characters render as `varnis…3` and `varnis…5`, which says the rows differ and not how — so the column's width, not this rule, is what makes a label readable.

Sessions are also told apart by **where they were run**. Every entry records an `entrypoint`, and a listing otherwise mixes all of them with nothing to tell them apart, so a session you remember starting in the desktop app is indistinguishable from one you started in a terminal. agentry names the three values `cli` (the terminal), `app` (the desktop app), and `sdk` (a non-interactive run). A value agentry does not recognize shows as `?` rather than being dropped, since the set grows without notice.

`sdk` is the log's own `sdk-cli`, and the name is the log's rather than a description: **a plain `claude -p` produces it with no SDK involved**, so the condition is "not interactive", not "used the Agent SDK". Anything headless lands here — a shell script, a hook, a CI step, another agent shelling out.

**Non-interactive sessions are excluded from the listing by default.** They are the majority of what a machine accumulates and almost none of what anyone wants to read back: on the development machine they were 89 of 251 sessions, and the five most recent in one project were all one-turn runs of a few seconds titled `ok`. Listing them by default buries the work a person did under the work a hook did. `--from` overrides this:

- `--from cli` / `--from app` / `--from sdk` — only that kind.
- `--from all` — every session, the pre-default behavior.

The default is exactly `cli` plus `app` plus any unrecognized value, so the four settings cover every combination worth naming. An unknown `--from` value is a usage error with a nearest-match suggestion, like every other enum flag. When the default exclusion leaves a listing empty while hidden sessions exist, agentry says so on stderr and still exits zero — an empty listing that a default silently caused is otherwise indistinguishable from a project with nothing in it.

When a listing spans more than one entrypoint, each row gains a **3-character tag** before the project column, on the same appear-only-when-it-varies rule — a listing that is all terminal sessions is unchanged. The tag is three ASCII letters rather than a glyph because a glyph needs a legend the output does not carry, and because agentry pads columns by rune count, so an ambiguous-width glyph would misalign every row that used it. It is not spelled out in full because at 100 columns `terminal`/`desktop` cut the title to 19 characters, and the title is what a row is scanned by.

A session can carry more than one entrypoint — starting in the desktop app and being resumed from the terminal writes both. Observed shape: one contiguous block of each, never interleaved, and rare (2 of 251 sessions, one of them an exact tie in entry counts, which is why no majority rule is used). **The last value wins**, matching the row's own last-activity time, and the tag takes a `+` suffix (`cli+`) to mark that the session started elsewhere. `--format json` keeps both, so the machine-readable form never loses what the tag compresses.

A second family of flags filters the listing by **what a session did** — the calls it made and the outputs it left behind — answering "which session did X?" without reading each one. Its axes:

- `--used-tool NAME` — sessions where that tool fired, matched against the tool-use name (`Bash`, `WebFetch`, `Skill`, `Agent`, …), case-insensitive and exact. This is the "which mechanism" axis.
- `--used-skill NAME`, `--used-agent TYPE`, `--used-command PATTERN` — the identity axis: what was invoked *through* the three identity-bearing tools — a Skill call's skill, an Agent call's subagent type, a Bash command's text.
- `--used TOKEN` — a catch-all over the identity axis: matches a skill name, an agent type, or a command. It deliberately does **not** match tool names, so the two axes never collide — to filter by tool name use `--used-tool`.
- `--used-file PATH` — sessions that modified a matching file. This is a third axis, "what did the work land on", and it reads **both** records of that: the targets of `Edit` and `Write` calls, and the files Claude Code tracked itself (the `files` channel). `Edit`/`Write` carries the weight, because about half of sessions have no file-history entries at all and a tracked-record-only filter would silently never match those. The tracked record is a backstop for a change no tool argument names — a file a shell command rewrote — but on the development corpus it contributed exactly one path out of thousands, and that one was a worktree file recorded against the session's own directory rather than the worktree's. Treat it as insurance, not as the source that answers the question. `--used` does **not** cover this axis — it stays the identity catch-all — so a file is matched only by naming this flag.
- `--opened-pr TEXT` — sessions that opened a matching pull request, matched over its repository, its number, and its URL together, so `--opened-pr artifactory-migration` selects a repository's worth and `--opened-pr 187` picks one. This is a fourth axis, "what came out of it", and it asks a question the call-based flags cannot: a session that ran `gh pr create` on the main thread is findable with `--used-command`, but one whose pull request was opened by a subagent or a skill is not, and Claude Code records the pull request either way.
- `--published-artifact TEXT` — sessions that published a matching artifact, matched over its title, its `claude.ai` URL, and the local file it was rendered from. Same axis as `--opened-pr`, same reason.
- `--reply-matches PATTERN` — sessions where the assistant's own reply text matched. This is a fifth axis, "what the reply said", and it is the only one reading what the model wrote rather than what it called or produced. It exists for auditing instruction-following across a corpus: a rule about how a reply is written — end every reply with a Learnings block, print paths as `file://` links, name the skill you loaded — leaves its only trace in the reply, so before this flag no listing could count whether such a rule fired.

`PATTERN` is a **regular expression** ([RE2](https://github.com/google/re2/wiki/Syntax)), case-insensitive by default, and this is the one filter in the family that is not a substring match. Prose is why: the questions asked of prose are positional ("did a reply open with praise") and alternation-shaped (`great|excellent|perfect`), and a substring expresses neither. A plain word is still a valid pattern, so the simple case costs nothing; regex metacharacters are live, so a literal `(` or `?` must be escaped. Case-insensitivity is the family's rule rather than a regex convention — override it per pattern with `(?-i)`. An unparseable pattern is a usage error, named as such before any session is read.

The pattern is tested against **each assistant text block separately**, and the session matches when any one block does. Per block rather than over the session's joined text, because `^` and `$` should anchor to a reply: `--reply-matches '(?m)^\*{0,2}Learnings\b'` counts the sessions that emitted a Learnings block, where the substring `Learnings` would also count every session that merely mentioned one. Thinking blocks are excluded — reasoning is not a reply, and a rule about what a reply said must not be satisfied by a thought.

Identity-axis matches (everything but `--used-tool` and `--reply-matches`) are case-insensitive substring, so `--used-skill sonar` also catches `sonar-search` and `--used-command 'git push'` matches that phrase anywhere in a command. Substring cuts both ways: a short token over-matches (`--used-command exa` also hits `exact`), so disambiguate with a more specific pattern (`scripts/exa`) when a token is also a common substring. The same holds for a path: `--used-file list.go` catches every `list.go` in every directory, and `internal/cli/list.go` names one. The population for the `--used*` flags is the same top-level calls `--include tools` counts — calls inside subagents are not considered, with two exceptions stated where they apply: `--used-file` also reads the session's tracked-file record, and `--opened-pr` / `--published-artifact` read the session's `pr-link` and `frame-link` entries. Claude Code writes all three for the session as a whole rather than per call, so those three flags see work a subagent did as readily as work the main thread did. `--reply-matches` is top-level too, and more narrowly so: it reads the main thread's own text blocks and never opens a subagent sidecar, so a phrase a subagent wrote back into the transcript is not matched. **Every one of these flags has a `--not-` form** — `--not-used-tool`, `--not-used-skill`, `--not-used-agent`, `--not-used-command`, `--not-used-file`, `--not-used`, `--not-opened-pr`, `--not-published-artifact`, `--not-reply-matches` — which keeps exactly the sessions its positive twin would drop, matching by the same rule with the same value. The pair exists because a compliance question is usually a conjunction of a presence and an absence: `--used-command 'git commit' --not-used-skill review` is one call for "committed without loading the review skill", which otherwise takes two listings and a set difference on session ids. It is also how an instruction-following audit counts the misses rather than the hits: `--not-reply-matches '(?m)^\*{0,2}Learnings\b'` is the sessions where the block never appeared. All nine are negated rather than the obvious few, because a partial set is a trap — a reader who learns `--not-used-skill` will reasonably try `--not-used-file` and get an unknown-flag error for no reason they can see.

**A negated filter makes an absence claim, and it is only as complete as what agentry reads.** The call-based filters see top-level calls, so `--not-used-skill X` means the main thread never invoked X — a subagent may well have, in a sidecar the listing does not open. Where that distinction matters, read the session rather than trusting the filter. `--not-opened-pr` and `--not-published-artifact` do not carry that caveat, since their entries are session-level; what limits them instead is that Claude Code has to have noticed — a pull request opened by a shell command it did not recognize as one leaves no `pr-link` entry, and no filter can find what was never recorded. `--not-reply-matches` carries the sidecar caveat and one of its own: it is an absence claim about a pattern, so it counts every reply the pattern failed to describe, including one that satisfied the rule in a form the pattern did not anticipate. Widen the pattern before reading its count as a violation count.

Multiple filter flags combine with AND (a session must satisfy all); negations AND too, so a session must fail every one of them. Giving a flag and its negation the same value therefore matches nothing, and agentry reports that as an ordinary empty listing rather than a usage error — unlike `--all-projects` with `--project`, the two are not competing to decide the same thing, they simply describe no session. For OR, run separate listings. Like the `--include tools` breakdown, these read a session's tool calls, so they pair naturally: filter to the sessions that used something, then `--include tools` to see what else those sessions did.

A third family filters by **what the session ran on** — the model, and the reasoning effort beside it. These are the same two facts the rendered header names (see Output), resolved the same way, so the two paths never disagree about what a session ran on.

- `--model NAME` — sessions that ran on a matching model, case-insensitive substring. Model names nest by family and version, and the substring rule is what makes both readings available from one flag: `--model opus` covers `claude-opus-5` and `claude-opus-4-8` together, `--model opus-5` picks one of them.
- `--effort LEVEL` — sessions that ran at that reasoning effort, case-insensitive and **exact**, unlike every other identity-style filter. The levels nest as substrings, so a substring rule would make `--effort high` silently include `xhigh` — a wrong answer rather than a wide one. Claude Code's own `--effort` takes `low`, `medium`, `high`, `xhigh` and `max`; agentry does not validate against that set, because it grows without notice and a level agentry has not heard of should return no sessions rather than a usage error.

Both match against **every** value the session carried, not only the resolved one: a session that started on Sonnet and switched to Opus matches `--model sonnet` as well as `--model opus`, because it really did run both. Both lift the default `--limit` the way a time or `--used*` filter does, and both AND with every other filter. Neither has a `--not-` twin — those exist because a usage question is usually a conjunction of a presence and an absence, whereas "ran on a model other than this one" is another model's listing, not an absence.

Neither gets a column in the text table. The table has one variable column, the title — 29 characters at a 100-column terminal, once the fixed columns and the session id are taken — and a model name runs 13 to 25 characters, so a model column would spend most of the title on it. The entrypoint tag earned its column by fitting in three characters; a model name cannot be shortened that far without dropping the version, which is the half a cost audit reads (`claude-opus-5` and `claude-opus-4-8` differ by one token and are priced differently). `--include model` shows the pair under the row instead, and `--format json` carries it on every session.

A fourth family filters by **how much code the session changed** — the lines it added plus the lines it removed, as Claude Code recorded them (see Output). This is the axis every other selector misses: a session that ran fifty tools and wrote nothing looks identical to one that rewrote a package, because the tool breakdown counts calls and not their effect.

- `--min-lines N` — sessions that changed at least N lines.
- `--max-lines N` — sessions that changed at most N lines. `--max-lines 0` is the useful case: it selects the sessions that touched no code at all, which no other flag can express.

Both bounds are inclusive and both count the two counters together, so a session that added 13 and removed 6 changed 19. Given together they make a range; a floor above its ceiling is a usage error rather than an empty listing, because no session can satisfy it and a caller reading zero rows would take that for an answer about their sessions. A negative bound is a usage error for the same reason: it can only be a mistake, and accepting one would silently return the whole listing for `--min-lines` and none of it for `--max-lines`.

**A session whose log recorded no line counters matches neither bound.** It makes no claim about how much it changed, so it can neither meet a floor nor be shown to respect a ceiling — the rule `--model` already follows for a session naming no model. That is most sessions, since Claude Code has only written the record since 2.1.241 and does not write it for every session even now, so a bounded listing is a listing of the sessions it kept a record for. `--max-lines 0` therefore means "recorded, and changed nothing", never "no record".

Each summary also carries its **token tally**, as `usage` in `--format json` — input, output, the two cache counters, and `cacheCreate1h`, the share of the cache writes bought for an hour rather than five minutes, summed over the main thread and every subagent the session spawned, each API response counted once (see Output). That is the same number the render path reports as `meta.usage`, so a spend read off a listing and one read off a rendered session agree rather than differing by whatever the subagents spent. Pairing it with `model` is what answers "how much did this model cost me across every project" from a single `--all-projects --format json` call, where before it took one render per session. Two limits on that answer: a session that switched model carries one tally and no split between the models, so `models` is what marks the sessions an exact attribution has to set aside (13 of 250 locally); and the tally is tokens rather than dollars, which `agentry cost` is what converts (see Rolling up cost). Reading the subagent sidecars is the listing's one non-trivial cost, since they run to roughly 60% of a project tree's bytes, and it is paid on every listing because the field is unconditional: over 250 local sessions the widest possible listing went from 2.40s to 2.96s when each session was read in turn. **Sessions are now read in parallel**, which is what keeps the widest answer affordable as a machine fills up: the same listing over 647 sessions takes 0.54s. The text table shows the tally only under `--include cost`, since it is a number to aggregate rather than one to scan a row by.

Beside the tally each summary carries **what caching saved**, as `cacheSaving` in `--format json`: `withCacheUSD`, what those responses cost at the rates they were billed at, and `withoutCacheUSD`, what the same tokens would have cost with nothing cached (see Output for what the pair means and how it is priced). The render path reports the same object as `meta.cacheSaving`, so the two formats cannot disagree about one session. It is two dollar figures rather than the one share the text line prints because a share of one session cannot be added to a share of another, where the two prices sum across any set of sessions and the share is taken afterwards. Both are absent on a session none of whose responses agentry holds a price for.

Beside it each summary carries **what the session cost in dollars**, as `costUSD` — Claude Code's own running total, read from the log's last such record rather than derived from the token tally. It is the field a currency answer comes from, and it is absent on a session whose log carries none, so a caller aggregating it must decide what to do about the gap rather than being handed a zero that looks like a measurement. Unlike `usage` it is main-log-only and costs no extra file reads: Claude Code's total **already counts a subagent's spend** (see Output), so a caller has nothing to add to it and adding a separately derived subagent figure would double count. Beside it, `linesAdded` and `linesRemoved` say how much code the session changed. They come from the same record, so all three keys appear together and a caller can test one to know it has the others; a zero there is a session that changed nothing, which is a different fact from the key being absent.

`--format json` emits the selected sessions as a JSON array instead of the text table — the listing's machine-readable form, for piping into `jq`. It carries the full model per session (`id`, `start`, `end`, `title`, `numTurns`, `prompts`, `tools`, `commands`, `rootUuid` — the shared root id that groups a fork family — `cwd`, the working directory the session ran in, read from the log rather than derived from the lossy folder name, `entrypoint` — the resolved value, joined by `entrypoints` listing every distinct one in first-seen order when a session carries more than one — `files`, every file the session modified as an absolute path, `denials`, one entry per `{kind, tool, identity, count}` group of refused calls, `model` and `effort` — each joined by a `models` / `efforts` list on the same rule `entrypoints` follows — `usage`, `dailyUsage`, one entry per model per delegation per local calendar day as `{day, model, agent, usage}` — the same responses `usage` totals, split as finely as they can be priced, so a caller can bucket a session's spend by day or by what it was delegated to without re-reading its log, `agent` being absent on the main thread's own tokens — `dailyActivity`, one entry per local calendar day as `{day, turns, activeSeconds}`, whose turns sum to `numTurns` — `prs`, one entry per pull request the session opened as `{repository, number, url}`, and `artifacts`, one entry per artifact it published as `{title, url, path}`), in the same order the table shows (most-recent first); the JSON stays flat (fork grouping shapes only the text table).

**Assistant reply text is the one thing a session holds that this JSON deliberately omits**, and `--reply-matches` is what stands in for it. Reply text is by far the largest field a summary could carry: across the 59 sessions of one local project it runs to 2.8 MB, against 776 KB for that project's entire 50-session listing as it stands. Carrying it would therefore roughly quadruple every listing — and unconditionally, since `--include` shapes only the text view and gates no JSON key, so a caller who wanted `usage` would pay for reply text too. A filter answers the question a corpus audit actually asks (did a reply say X, in how many sessions) at zero payload cost, so agentry tests reply text and never ships it. To read the prose rather than test it, render the session: `agentry <id>` and `agentry <id> --format json` both carry every text event in full.

Being the model rather than a view of it, it ignores `--include` (a text-shaping flag) and color; the selectors (`--since`/`--until`/`--limit`/`--used*`) still choose which sessions appear, and an empty selection emits `[]`. **stdout is always a well-formed array**, including on the two failures that produce no sessions at all — a directory with no Claude project, and a project holding no sessions. Those still write their message to stderr and still exit non-zero; they simply also write `[]` to stdout, so a caller can pipe into `jq` unconditionally and read the exit code to tell "nothing matched" from "nothing to look in". Without that, one output contract has two shapes and every script that sweeps directories carries a guard to substitute the missing array. This applies to `list --format json` only: the render path's JSON is a single session object, and a missing session has no empty form to emit. `--format` also accepts `text` (the default); an unknown value is a usage error. The default text table renders as below.

When a time filter, **any flag from the what-a-session-did family**, `--model`/`--effort`, or `--min-lines`/`--max-lines` is given and `--limit` is not, the cap is lifted — `agentry list --since today` shows every session from today, not just ten. An explicit `--limit` applies **after** the filters, so `--limit 50 --reply-matches X` is "the 50 most recent sessions that matched", not "how many of the 50 most recent matched" — a distinction that matters exactly when the count is the answer. For a rate over a window, bound the window by time (`--since`) and leave the cap lifted, or take the two listings and intersect their ids. A window that matches no session prints nothing and exits zero; a project with no sessions at all is an error, the same as in render mode (under `--format json` that error still prints `[]` to stdout — see above). The scopes follow the same split between "nothing matched" and "nothing to look in": `--project PATH` naming a path no project sits at or under is the same error as standing in a directory with no project at or under it, and `--all-projects` finding no session in any project is the error too, whereas a filter that excludes every session found is still an ordinary empty result at exit zero. `list` takes no session-id argument; the rendering flags (`--level`, channel toggles) do not exist on it — they live on the render path, not as flags `list` silently ignores.

Color follows the same rule as rendered output: styled on a terminal, plain when piped or with `NO_COLOR` / `--no-color`.

The **session id is printed whole**, with the part that tells the rows apart drawn brighter than the rest of it. The distinguishing prefix is still computed — the shortest that separates the visible rows, floored at 8 characters, which is `git`'s rule for abbreviated object names — but it now decides what is emphasized rather than what is printed. The floor is what keeps a three-row listing from emphasizing 1 character, since 8 hex characters separated all 443 sessions on the development machine and even 4 collided on none; the uniqueness check grows the prefix when the rows demand it.

**Printing the whole id is what makes the row's id usable outside agentry.** A prefix is enough for `agentry <id>`, which resolves it, and is not enough for `claude --resume`, which in print mode answers `Provided value "82265559" is not a UUID` and refuses. A listing that printed the prefix alone therefore answered agentry's own question and left the commoner one — resume this session — needing a second command to expand what was already on screen.

**The whole id costs the title column 28 characters**, and the emphasis is what pays for them rather than truncation. At a 100-column terminal the title falls from 57 characters to 29, where 160 of 321 local session titles fit whole against 304 before, so a narrow terminal is where this trade is felt. The prefix is what a reader scans a column of rows by and the rest is what they copy, and weight is what separates the two jobs without dropping either. The title keeps its 10-character floor, so a very narrow terminal overruns rather than hiding the id.

Under `NO_COLOR`, on a monochrome terminal, and through a pipe the whole id still prints and only the emphasis is lost — the value a caller pipes out is the one they need, and `--format json` has always carried it.

The render path accepts what the listing prints: **any unambiguous prefix** resolves, a full id resolves as it always did, and a prefix matching more than one session is a usage error naming how many it matched rather than a silent pick. Resolution is scoped like every other lookup — the current directory's project first and alone, then the subtree — so a full id still costs one `stat` and pays nothing for the wider reach. A prefix printed by one listing can be ambiguous in a wider scope, and that is the error's job to say; the fix is to pass more characters, which `--format json` always has.

## Rolling up cost

`agentry cost` prices the tokens itself and adds the dollars up over a window: what today cost, what this month cost, what one model cost, what each session cost. It answers what the per-session dollar figure cannot. Claude Code's own record covers 71 of 314 local sessions — it has only written one since 2.1.241 — and it is a single number per session, so it can be neither extended to the other 243 nor split across the days a session spanned, which 29 of the 71 did.

**The figure `cost` reports is computed from the transcript and is an estimate, not a bill.** Every assistant entry names the model that answered and carries the tokens that response spent, so agentry prices each response at the same rates and by the same formula Claude Code itself uses, and attributes it to the local calendar day of the entry's timestamp. Over the 71 local sessions that also carry Claude Code's own record the two agree closely in aggregate — $3,159 computed against $3,043 recorded, 103.8% — and per session the median lands at 98.1%, with 42 of the 68 non-zero records inside 5%. Every `cost` output says the figure is an estimate, so no reader has to remember it.

**The two figures disagree per session in both directions, and neither is the other's error.** Computing runs **low** where Claude Code makes a request without writing an entry for it — its own background work, which the transcript never holds; the 10th percentile of the ratio is 80.4%. It runs **high** where Claude Code's record covers only part of the session, which 8 of the 68 show: one local session's log carries exactly two cost records, both at its very end and both reading $5.35, over 4,252 lines of work the transcript prices at $119.51, and another's ledger falls from $182.40 to $107.12 partway through and ends there. So a per-session gap either way is a fact about which requests each side can see, not a disagreement about arithmetic.

The rates are **one table stamped with the date it was verified**, not a table keyed to a date. Across the models in local use no rate changed between 2026-07-02 and 2026-09-11, so date-keyed rates would add a second thing to get wrong for no fact they would recover, and a stale flat table is easier to notice than a wrong dated one. The table is read out of Claude Code's own baked model catalog — the same tier names it uses (`tier_5_25`, `haiku_45`, …), so re-verifying a rate is a grep of the binary rather than a reading of eight rate rows — and checked against Anthropic's published prices. `--format json` carries the verification date, so a caller can tell how old the prices it was given are.

**Cache writes are priced at two rates and the log's flat counter hides which.** A five-minute cache write costs 1.25× the input rate, a one-hour write costs 2×, and `cache_creation_input_tokens` is their sum; only a nested field splits them. Across the local corpus 59% of cache-creation tokens are one-hour writes — 500,674,493 of 851,676,548 — so pricing that flat counter at the five-minute rate would undercount cache writes by close to a fifth. agentry reads the split and falls back to the whole counter at the five-minute rate for a log that carries none, which is the rate it can still prove.

Three charges are **left out**, and each one's absence is a documented gap rather than a rounding: a web search, billed per search rather than per token; the premium on inference pinned to one geography; and any rate a managed organization negotiated, which Claude Code records as a cost basis other than list price. No local session carries any of the three — `web_search_requests` is zero on all 128,723 entries that have the field, every entry's inference geography is unpinned, and this machine has no negotiated rates — so all three would be implemented against no example to check them by. A session that used web search is priced slightly low; one on negotiated rates is priced at list.

A model agentry holds no price for is **named rather than priced at zero**. Its tokens count in the token totals, its dollars count in nothing, and the report names the model and how many sessions used it. Models appear without notice, and a zero would read as a session that cost nothing rather than one nothing is known about.

**`agentry cost` with no flags answers three questions at once**, because the question a person asks is "what am I spending" and not "what did this directory spend all time": the session they were just in, this directory's whole history, and the machine's last thirty days. A flag combination is not an interface for the commonest question, and requiring `--all-projects --from all --since 30d` to reach the machine's figure made the widest answer the hardest to type.

```
This session  Cost calculation per session          100M       $65.70
This folder   8 sessions, all time                  512M      $349.62
This machine  301 sessions since 2026-08-12         8.1B     $6049.13
              ▁▂▃▂▂▂▂▃▁▂▁▃▂▂▃▂▃▃▃▁▃▃▂▁▄▃▄▁▁▁  per day, peak $435.37

computed from the transcript at 2026-09-11 list prices — an estimate, not a bill
Claude Code recorded $3043.02 for the 71 sessions it kept a record for
```

**The summary answers more than the three scopes, because the sweep that finds them has already read everything else.** Pricing the machine's window means parsing every session on the machine; the three figures are a fraction of what that parse holds, and a caller who paid for the read gets the rest of it. Four sections follow the scopes, each answering one question the three rows raise and cannot settle:

- **Day by day** — a calendar of the machine row's days, since the summary has no table for a picture to head and can therefore carry the shape that says the most;
- **Where it went** — the priciest project directories over that window;
- **What ran it** — the priciest delegations;
- **On which model** — the models those dollars ran on;
- a closing line placing the window's last day against its median and top-decile day, so "is today normal" is answered rather than left to arithmetic.

Each breakdown counts the machine's window, the widest of the three scopes, since the question the sections answer is where the money goes rather than where this directory's money goes. Each shows its five largest rows and then **names the remainder as one line** — how many rows were left and what they came to — so the visible rows plus that line account for the total. A capped list that did not name its remainder would be the failure `--limit` is refused for on the roll-up: a figure a reader cannot reconstruct.

`--level minimal` prints the three scopes and the notes alone, which is what every version before this one printed. The flag is the render path's, and **its default differs by verb because the commonest question does**: rendering a session opens on the transcript and adds detail on request, while asking what you are spending is asking for the picture rather than for three figures and a second command. Only `minimal` and `standard` are offered here — the other two name no further detail this verb has, and a value that changed nothing would read as a setting that failed.

`--chart` chooses the picture in the **Day by day** section as it does above a roll-up's rows, with one difference: the summary's own default is the **calendar**, not the sparkline the day axis picks for a table. A picture above a table heads rows that already carry the detail, where the summary's picture is the only place its days appear at all. `--chart spark` asks for the compact line under the machine row instead, `--chart line` for the braille plot, and `--chart none` for no picture.

**A sparkline under the machine row shows the shape of its window**, one cell per day from the day the row names to the last day that spent, with the peak named beside it so the marks have a scale. The three rows answer what you are spending; the sparkline answers whether it is climbing, which is the nearest question and the one a column of three figures cannot reach. The sweep that builds the machine row already prices every day, so the series costs no extra reading.

**A day that ran no session at all is a blank rather than the lowest mark.** Any day that spent draws a mark, so a day that cost real money is never rendered as a day that cost nothing. A sparkline has only those two states — its span is exactly the days it draws, so there is no third state for "outside the window" the way a calendar grid has.

The sparkline is dropped, not squeezed, when the terminal is too narrow to hold it beside the row it belongs to, and a window holding fewer than two days does not draw one: a single mark has no shape. **A share bar is deliberately not offered on these three rows.** The folder row reads all time while the machine row reads thirty days, so their lengths would compare spans nobody chose to compare; and under a named window, where all three share a span, the rows nest rather than divide — the machine contains the folder, which contains the session — so three bars would read as parts of a total the rows do not sum to.

Every session on the machine is read **once, in parallel**, and the three rows are taken from that one sweep — the scopes nest, so re-reading the narrow ones would double the only real cost of the answer. Measured over 647 local sessions the summary takes 1.5s against the 4.1s the same sweep took one session at a time.

Each row **names its own window**, so the three reading differently is a stated fact rather than a trap. The machine row prints the first day it counts rather than the words "last thirty days": a day is the finest bucket a response is attributed to, so a thirty-day bound counts thirty-one calendar days, and naming the date keeps that out of the reader's head.

**This session** is the most recent session in this directory's scope that was not a headless run — the same resolution `agentry view` makes with no id, and for the same reason: on a machine using hooks the newest log is usually a two-second hook run, so a panel that took the newest log outright would price a hook and label it your work. It is the one panel that skips them. **This folder** and **this machine** count every session of every kind, headless included, because those two are meant to be the bill and a hook costs real money.

A directory with no Claude project has no session and no folder row: the machine row is printed alone, and a note on stderr says the two are missing rather than showing them as zero. Nothing about the machine row depends on where it was run from.

**A row a window or a filter leaves holding no session is dropped the same way.** A row reading $0.00 would say the session was free, where the truth is that it falls outside the span asked for. The machine row is the exception and always prints, since it is what the other two are read against — `0 sessions since 2026-08-13` is an answer, where a $0.00 session is a wrong one.

**A flag that changes the shape or the scope turns the summary back into the roll-up; a flag that filters narrows it in place.** `--by` asks for a different shape, and `--all-projects` and `--project` name a scope, which the summary's rows already are — each of those three switches the output to the single-scope table below. `--since`, `--until` and `--from` filter the same question the summary answers, so they move its rows instead: `agentry cost --since 7d` is still this session, this folder and this machine, each counting a week. `--no-color` and `--format` change neither, since they only say how the answer is written.

Under a named window every row is bounded by it, and the machine row's own thirty-day default is **replaced rather than narrowed further** — a caller who named a window asked for that window everywhere, and intersecting the two would report a span nobody chose. The folder row, which otherwise reads "all time", names the window like the machine row does. A named `--from` likewise applies to all three, and the session row then resolves to the newest session of the kind asked for rather than the newest non-headless one.

`--by` chooses the bucket, and the rows always sum to the total:

- `--by total` (the default) — one line for the whole selection.
- `--by day` — one row per local calendar day.
- `--by week` — one row per week, labelled by its Monday.
- `--by month` — one row per calendar month.
- `--by model` — one row per model, which is what answers "what has Opus cost me".
- `--by agent` — one row per thing the tokens were delegated to, which is what answers "what is that skill costing me".
- `--by project` — one row per directory the sessions ran in, which is what answers "which repo is costing me".
- `--by session` — one row per session, with its title, which is what answers "which session cost that much".

`--by agent` names a subagent by its type and a forked skill by its invoked name with the leading slash kept, so a table mixing both says which is which. The session's own tokens are a row called **`(main thread)`** rather than an omission, so the rows sum to the total and each one's share reads off the table; the main thread is the large majority of every local session, which a delegated-only table would hide. **A delegation that delegates again is charged to the call the session itself made.** A subagent or skill that spawns its own subagents writes their logs beside the session's, and each link is followed until the chain reaches the call the session chose — so a skill's row is what invoking it actually cost, including everything it ran underneath. Charging the nested work to its own name would name a row nobody invoked and nobody can decide to stop running.

A log that **no spawn record names at all** is named **`(unattributed)`** rather than dropped, since its tokens were spent whatever the record forgot. That is the floor rather than an edge case: 169 of 1,507 local sidecar logs, 11%, carry no record naming them, which was 1.9% of a month's dollars.

**`--by project` groups by the directory the session ran in**, read from the log rather than from the project folder's name, which is lossy. The path is **cut at its first hidden segment**, which is what folds a repository's worktrees into the repository: a tool that checks a branch out beside the repo puts it under a dot-directory, `<repo>/.claude-worktrees/<name>`, so cutting there names the repo. A sibling repository under a shared parent is untouched, since no segment between the two is hidden.

Cutting by the rows themselves instead — folding every directory into the outermost row that contains it — was tried and is wrong: one session run from a parent folder then swallows every repository beneath it, which locally merged three repos into a single $3,552 row. A path whose only hidden segment is its last named part keeps it, so `~/.bob` and `~/.config` stay apart rather than both collapsing onto the home directory.

Nothing is read from the filesystem, so a directory deleted or moved since the sessions ran groups the way it did then. The home directory prints as `~`, the listing's abbreviation. The column is bounded at forty characters and **cut from the left**, since paths in one column share their leading directories and differ at the end — locally a session run inside a temporary directory carried a 140-character path that pushed every figure off screen. Locally this axis carries the largest single finding in the tool: one repository is $2,604 of a $6,221 month, which no other axis separates out.

Three further columns say what the dollars bought: **`Turns`**, **`Active`**, and **`$/turn`**. A turn is counted in the bucket its prompt started in. Active time runs from that prompt to the last thing the assistant said in the turn, counting **any silence longer than five minutes as five minutes**.

Both halves of that rule are load-bearing. Measuring to the turn's last entry of any kind reads a resumed session's bookkeeping entries as work, which made one local 27-turn session 386 hours long. Leaving the silences uncapped is worse: the log cannot tell a ten-minute test run from a person who walked away mid-turn — both are one gap between two timestamps — and uncapped, one local turn measured 168 hours while days averaging over an hour a turn carried 73% of a month's supposed activity. The cap errs toward understating, which is the safe direction for a figure dollars are divided by, and it brought the local month from 1,050 hours to 198.

**The three columns are absent on `--by model` and `--by agent`.** A turn can run on two models and delegate to two agents, so it belongs to no single row there, and a blank column is better than a number that divides wrongly. They are also absent from the no-flag summary, whose three rows answer what you are spending rather than what it bought.

Beneath the total, two more lines appear whenever turns were counted: what a turn cost on average and what an active hour cost, then the **spread** — the median cost per turn across the sessions in the window and the level the top tenth sits above. Both are needed because one average hides the shape: locally the mean turn costs $2.53 against a median of $0.71, so a few very large turns carry the bill. The spread is printed only once three sessions qualify, below which a median restates one session's own figure.

**Wall-clock time is deliberately not offered.** A session sits open across days, so its span measures how long a terminal tab stayed open: the local corpus holds 5,324 session-hours inside a 720-hour month. Active time is the only elapsed figure the roll-up divides by.

**Cost per line changed is deliberately not offered either.** Line counts come from Claude Code's own record, which exists for a minority of sessions — 77 of 398 locally, two thirds of those changing no lines — and that record can cover a shorter span than the session while the computed dollars always cover the whole transcript. A column blank for nine rows in ten, whose numerator and denominator describe different periods, would mislead more than it reports.

A day begins at **local midnight**, and a session's spend splits across days by each response's own timestamp rather than landing wholly on the day the session ended. That is the whole reason a computed figure is bucketable at all: Claude Code's per-session record has no per-day form, so a session running past midnight could only ever be attributed to one day or the other, and 29 of the 71 locally recorded sessions run past one, as do 123 of all 314.

Time buckets print **oldest first**, the listing's convention, so the most recent sits nearest the prompt. `--by model` and `--by session` print **most expensive first**, because that is the order the question is asked in.

**There is no `--limit`.** Every listing shows a total, and a cap would print a total that the visible rows do not account for — which is worse than a long listing, since the number a reader checks is the one they cannot reconstruct.

**A roll-up's first note says what it priced** — `priced this folder since 2026-08-13`, or the named path, or `every project`. Without it the figure beneath the rows reads `Total` and names no scope at all, so the same number means one directory to one reader and a whole machine to another. The summary needs no such line, because its rows say which scope each one is.

`--since` and `--until` take the listing's `WHEN` values (see Listing sessions), so `agentry cost --since 30d` is the last thirty days and `--since today` is today. They are compared against **each day of spend**, not against the session's last activity the way the listing compares them: a session that ran across the window's edge contributes only the days inside it. `--limit`, `--include` and the what-a-session-did filters do not exist on `cost`.

Scope is the listing's: the current directory's project and everything nested under it by default, `--project PATH` for another subtree, `--all-projects` for every project (see Listing sessions for all three, and for why the two flags are mutually exclusive). `--from` selects where the sessions ran, with the same default that hides non-interactive runs — a machine using hooks accumulates hundreds of them, and a cost total that silently included them would answer a different question than the listing beside it.

**Whenever that default leaves sessions unpriced, `cost` says how many on stderr** and names `--from all`, which is more than the listing owes. A listing that dropped rows still shows the rows it kept, so the reader can see it is looking at a subset; a total is one number, and one that quietly omitted sessions is simply lower than the bill — locally by $426 of $10,244, across 246 headless runs. The note goes to stderr, so a figure piped into another program is still the figure alone.

**Every row carries a bar showing its share of the window's dollars.** It is the last column, so it takes whatever width the figures leave and is the first thing dropped when the terminal is too narrow — no figure ever wraps to make room for it. A row that spent anything at all draws at least one mark, so a row too small to see is never rendered as a row that spent nothing, and the total line carries no bar, since a bar covering the whole width says only that the total is the total.

The bar is a second reading of the Cost column and never the only one. Under `NO_COLOR`, on a monochrome terminal, and through a pipe the figure it repeats is still on the row, and the bar itself is drawn from block characters rather than from color, so it survives all three. Where color is available it shades the bar by rank, which adds nothing a reader needs and takes nothing away from one who cannot see it.

The text form is a table with a total line beneath it:

```
Day               Sessions      Tokens        Cost
2026-09-09               3        4.1M      $12.44  ████████▎
2026-09-10               5        9.7M      $31.02  ████████████████████
2026-09-11               2        1.8M       $6.10  ███▉

Total                   10       15.6M      $49.56
computed from the transcript at 2026-09-11 list prices — an estimate, not a bill
Claude Code recorded $54.02 for the 4 sessions it kept a record for
```

The last line appears only when a session **wholly inside the window** carries Claude Code's own record, and it names how many, because that is the only comparison that is exact: a record is one number for a whole session, so a session straddling the window's edge cannot contribute a share of it. Where no session in the window carries one, the line is absent rather than reading zero.

**A picture is drawn by default wherever the buckets are a span of time**, above the rows it summarizes. A caller who asked for thirty days asked to see thirty days, and making them name a second flag to see the shape of what they already selected is the same mistake as making them name three flags to reach the machine's total. The rows, the total and the notes are all kept — a picture is added to the answer, never put in place of it, so nothing a caller could read before becomes unreachable by default.

**The axis chooses the picture**, since what makes a drawing legible is the bucket, not a preference:

- `--by day` draws a **calendar** — a week per column, a weekday per row. Days are the only bucket whose squares a calendar can hold, and it is the only shape that shows the week's structure rather than only the trend.
- `--by week` and `--by month` draw a **sparkline**, one cell per bucket. Too few points for a calendar and too few for a plot with its own axis, but enough to show direction.
- `--by model`, `--by agent`, `--by project` and `--by session` draw **no picture**. Their rows have no order along the bottom of a plot, and the share bar on every row already says what a drawing would.
- The three-scope summary draws the **sparkline beneath its machine row**, described above.

`--chart` overrides that choice rather than enabling it. It takes `auto` — the default just described — plus `none`, `line` and `calendar`. `--chart none` prints the table alone, which is what every version before this one did.

`--chart line` draws a braille line plot, joining the points rather than leaving them as dots: a braille cell is two dots wide and four tall, so the plot fits four times as many points across a terminal as block characters do, and separate dots at that resolution read as scatter. The value axis is labelled down the left edge and the span named beneath, oldest at the left.

`--chart calendar` shades each square in one of four steps by which quarter of the spending days it falls in. Quarters by count rather than by dollars, since a month holding one very large day would otherwise shade every other day alike. A day inside the span that spent nothing is a dot, so an idle day and a day outside the window never read the same.

**A picture that cannot be drawn is simply absent.** One bucket is not a line and not a calendar, and a terminal too narrow for the drawing keeps the rows. Nothing is reported, because nothing was lost: the rows the picture summarizes are still on the screen.

`--chart` says how the answer is written rather than what is counted, so like `--format` and `--no-color` it leaves the three-scope summary standing instead of switching to the roll-up. The flag is rejected at parse time only where it cannot mean anything, naming both flags rather than the value alone: an explicit `line` or `calendar` on an axis that is not time, `calendar` on any roll-up axis but `--by day`, and any picture alongside `--format json`, whose object is the same either way.

`--format json` on the three-row summary emits `scopes`, one entry per panel as `{scope, label, since, sessions, usage, costUSD}` — `scope` being `session`, `folder` or `machine`, and `since` present on the machine panel alone — beside the same `recorded`, `unpricedModels` and `pricesVerified` the roll-up carries.

With a selector, `--format json` emits the roll-up object rather than a table: `by`, the bucket axis; `selection`, the `scope` that was priced with the `since` and `until` bounds that were named, which is what the note above prints; `buckets`, each with its `key`, `label` (a session's title, absent on every other axis), `sessions`, `usage`, `costUSD`, and — on the axes that take them — `turns` and `activeSeconds`; `total`, the same shape with no key; `spread`, the `sessions`, `medianPerTurn` and `p90PerTurn` described above, absent when too few sessions qualify; `recorded`, the `sessions` count and `costUSD` sum described above, absent when no session qualifies; `unpricedModels`, one entry per model with no price as `{model, sessions, usage}`; and `pricesVerified`, the date the rate table was checked. Like every other JSON form it ignores color, and an empty selection still emits a well-formed object with a zeroed total — a caller piping into `jq` reads the exit code to tell "nothing matched" from "nothing to look in", the rule `list --format json` already follows.

## Verbosity

`--level minimal | standard | detailed | full` is a preset over independent channels; default `minimal`. Each level is just a named set of channel defaults — per-channel overrides (`--thinking` / `--no-thinking`, `--tools`, `--tool-results`, `--subagents`, `--metrics`, and their `--no-` forms) adjust any channel on top of the level, adding or subtracting (e.g. `--level detailed --no-thinking`).

The user prompt and the agent's response text are always shown — they are the irreducible transcript, not a channel. Levels layer notions of the work onto that base, breadth before depth: each level adds more *kinds* of detail until the deepest level adds the result bodies.

- **minimal** — prompts and response only.
- **standard** — + thinking; + metrics.
- **detailed** — + tools (the notion that a tool fired) and + subagents (skill and subagent expansion). The shape of the work, without tool output.
- **full** — + tool-results (each tool's output body). The content of the work.

The channels:

- **thinking** — assistant reasoning blocks.
- **tools** — one line per tool call: that it fired, with name, truncated args, status, and duration. A call that was refused rather than run says so in place of its duration — `denied: permission-rule` — because the error glyph alone reads as "ran and failed", which is a different thing to go fix. An `Agent` call also names what it delegated to, bracketed after the tool name — `Agent[Explore@haiku]`, the subagent type then `@` and the model. A call that named no model shows the type alone (`Agent[Explore]`), since the subagent ran on the session's model and naming one would invent a fact the log does not carry. `Agent` is the only tool bracketed this way because it is the only one whose args hide its identity: a `Bash` line already opens with its program and a `Skill` line with its skill, while an `Agent` line carries the human description and nothing about which agent ran.
- **tool-results** — the result body of each tool call. `tools` shows *that* a tool fired; `tool-results` shows *what it returned*.
- **subagents** — expansion of nested work: a call that spawned a child session renders that session's inner event stream instead of a result body. This covers `Agent` calls and **forked** skills — the ones that run in a separate session. An **inline** skill runs in the main chain, so its work already shows as ordinary turns there and the call stays a leaf (nothing to expand). Inside an expanded stream the same channels apply, so at `detailed` a forked skill expands to its tool-activation lines without their bodies.
- **metrics** — the session summary table (per-turn token and tool breakdown). The per-turn footer (duration, tool count, errors) is always shown, independent of this channel.

## CLI conventions

**A verb's bare form answers its commonest question.** The no-argument invocation is the one a person types first and remembers, so it resolves to the answer most callers want rather than to help text or the narrowest available reading: `agentry` lists this directory's sessions, `agentry view` renders the most recent one, and `agentry cost` prices this session, this folder and this machine. Flags narrow or widen that answer; they are not how it is assembled, since a caller who must combine three of them to reach the figure they want most has been handed the longest path to the most wanted result. Where a verb has no single commonest question it names the choices rather than inventing a default: `agentry completion` with no shell prints the four it can generate.

Data on stdout, diagnostics on stderr. `NO_COLOR` (any non-empty value) or a non-TTY stdout disables color. `--help` and `--version` are always available, and each verb has its own `--help` listing only the flags valid in that mode. The bare command's help leads with the program version and carries both flag sets — the list flags (the bare command defaults to listing) and the render flags (for `agentry <uuid>`, which also apply to `view`, not to `list`) — grouping the render flags under their own heading so their scope stays legible, and every help screen carries usage examples. Exit codes follow `sysexits` — a missing project or session exits with a distinct non-zero code, not a generic failure.

Flags and operands may appear in any order (`agentry list --since today` and `agentry list` with flags before or after operands both parse). A mistyped verb, flag name, or enum value (e.g. `--include prompt` for `prompts`) errors to stderr, names the offending token, and suggests the nearest valid name by edit distance when one is close enough — it never auto-runs the guess and never dumps full help.

## Shell completion

`agentry completion <bash|zsh|fish|powershell>` prints a completion script for that shell — the standard generator, so the setup is the one users already know (`source <(agentry completion zsh)`, or drop the script in the shell's completion directory). Beyond the verbs and flag names every completion script offers, agentry completes the two arguments worth completing:

- **enum flag values** — `--format` (`json`, `text`), `--level` (`minimal`, `standard`, `detailed`, `full`), `--from` (`cli`, `app`, `sdk`, `all`), `--by` (`total`, `day`, `week`, `month`, `model`, `session`) and `--effort` (`low`, `medium`, `high`, `xhigh`, `max`) complete to their allowed values, not to filenames. `--effort` is the one whose candidates are suggestions rather than the accepted set: the filter takes any value, because Claude Code can add a level without notice and an unknown one should return no sessions rather than an error.
- **session ids** — the render path's positional argument completes to the session ids in scope, each annotated with its title (the same list `agentry list` shows), so the full UUID is a Tab, not a paste. Completion covers the same subtree the listing and the render path do, so every id it offers renders and every id that renders is offered; it never falls back to filename completion.

Completion is computed live on each Tab (a session id reflects the sessions present at that moment), so a new session is completable as soon as it exists.

Homebrew installs the scripts automatically — the cask links a bundled script into the shell's completion directory (see Distribution), so a `brew`-installed agentry tab-completes with no extra step. The `go install` and release-tarball paths have no install hook, so those users run `agentry completion <shell>` themselves; the tarball carries the pre-generated scripts for convenience.

## Scope

**MVP:** list sessions with recency and time-frame selectors (bare `agentry` or `agentry list`); resolve and render a session from the current directory (full-UUID arg → that session; `agentry view` with no id → most recent by modification time); styled terminal output with auto color detection; verbosity levels and channel overrides.

**Roadmap:** ordered by what is blocked today. The first group is where a caller still works
around agentry by hand; the second is the long-standing product surface, which no audit work
depends on. Insert a new item into the group whose description it matches rather than at the
end. (Two groups that once led this list are gone. Items a caller was working around: cross-project
listing shipped, and with it the loop that ran the binary once per repository. Facts about a
session that a listing omitted or reported wrong: what it ran on, what it spent, and what it
produced are all in `list` now.)

- Session selection beyond an id: content search (a `search` verb).
- Title ladder: skip a bare slash command, not just `/clear`. A session whose first prompt is `/model` or `/effort` is titled by that command today, which describes the session no better than `/clear` does — three `access-log-arm-*` sessions read `/model`. The skip should cover any prompt that is a slash command alone, falling through to the next prompt as `/clear` already does.
- `--include reply`: the session's last assistant reply beneath its row. The text is already parsed for `--reply-matches`, so this is display only; whether it also earns a JSON key is open, since the size argument that omits reply text there is about every reply rather than one.
- `--format md` / `-o FILE`: markdown-file export.
- Interactive session browser.
- Paging.
- homebrew-core distribution.

**Non-goals:** editing or replaying sessions; inline images; non–Claude Code log formats, until explicitly scoped.

## Log format compatibility

Claude Code's on-disk log format evolves across versions. `agentry` tracks the current format and retains support for older ones it has previously handled: a format change must not break rendering of sessions written by earlier Claude Code versions. Unrecognized fields and entry types are ignored, not treated as errors.

## Distribution

Built as a single static binary by GoReleaser. macOS installs from a personal Homebrew tap, distributed as a cask (GoReleaser deprecated formulae for pre-built binaries): `brew install eitanpo/tap/agentry`. Homebrew casks are macOS-only; on Linux install with `go install` or download a release binary. homebrew-core is a later target.

The release archive bundles pre-generated completion scripts (`completions/agentry.{bash,zsh,fish}`), and the cask links them into the shell's completion directory on install — so Homebrew users get completion (see Shell completion) with no extra step. The scripts are generated from source at build time rather than by the cask running the binary, because the binaries are unsigned and executing one at install time would fight the quarantine attribute the cask's post-install hook strips.
